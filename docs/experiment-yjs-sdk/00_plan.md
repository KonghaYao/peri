# SDK Yjs 存储与通信实验

状态：实施与实验记录；当前行为以代码、测试与 SDK README 为准。

用户授权：重新设计 SDK 的 Yjs 展示存储及通信，模拟 10,000+ 工具调用、巨大工具载荷与超长流式输出，完成实现、验证并提交。本次不改变 Rust canonical Session Store 或 ACP 协议。

## 问题与验收

- 投影每次工具更新扫描历史、流式更新重复写状态，是否导致随历史长度增长的工作量？
- 视图每次更新全量遍历、复制工具对象，能否改成按变更失效和复用不可变快照？
- 大工具载荷能否以有版本的按需读取保留全文，同时限制热 Y.Doc 与默认网络的体积？
- 通信能否按时间和字节预算批处理增量、使用 Yjs V2 二进制、断线按状态向量补齐，并明确慢消费者的恢复方式？
- 完成、取消、回放、compact/rewind、文档切换与销毁不能丢数据或产生幽灵消息。

成功标准：针对同一生成器，12,000 工具的热文档快照显著小于原始载荷；流式更新无需重读未改变工具；至少 16 MiB 文本精确往返；终态、按需全文及断线重同步行为有契约测试；采集绝对耗时、字节、帧数及内存，不以机器相关耗时作为单元测试门槛。

## 实验方法

固定 Bun/Yjs 版本、确定性内容、隔离进程；基线提交 `567640f1837771442628970a56ce68c5a8f8e256`。实验串行运行，避免同时构建或跑压力测试。第一轮保留基线及原始 JSON，第二轮相同生成器验证候选；针对新边界另补失败与生命周期测试。

场景：

1. 12,000 个工具，分布于多个 assistant message；每个输入约 1 KiB、输出约 8 KiB（结构化 rawOutput 与文本），另外独立测 1 MiB 大结果。记录投影时间、两文档快照字节、复制应用时间、进程内存。
2. 上述历史后的 128 次异步流式更新，每次让视图发布；记录中位数/p95/总耗时及快照数量。
3. 16 MiB 文本，16,384 × 1 KiB 分片；记录增量总字节、帧数、应用时间、最终文本长度/校验和，包含完成 flush。
4. 冷快照、断线后增量、重复/乱序更新、慢消费者和大载荷按需读取。第一轮未支持的能力标记为不适用。

资源上限：单个基线场景超过 120 秒或 RSS 超过 2 GiB 时记录截断及已完成规模，不能把截断当作全量完成。每轮至少三次独立进程采样（重场景若超限，解释后减少）；全部原始测量保留。
