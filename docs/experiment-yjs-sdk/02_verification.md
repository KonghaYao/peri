## 逐维度评估

### 数据完整性：PASS

逐一核对 [候选](raw/candidate/summary.json)、[增强基线](raw/baseline-enhanced/summary.json)、[流式补充基线](raw/baseline-stream-supplement/summary.json) 与 [小规模契约验证](raw/baseline-contracts/summary.json)：12 个候选样本、12 个补充基线样本、1 个契约样本均与各自 summary 完全一致，均 `status=passed`、`exitCode=0`、无中止原因，终态耗时和进程峰值 RSS 未超预算。正式场景各有三个独立进程，未以小规模契约场景替代 12k 工具采样。

候选 12k 工具样本均验证 12,000 个工具和 1,200 个历史 assistant；12,000 次按需读取均成功，读取 JSON 合计 98,964,890 bytes。view 的初始历史和 128 次更新后历史均验证完整，首工具非空且 128/128 次保持对象身份；附加真实工具名称更新验证了缓存失效及旧快照不变。正式流式样本均还原 16,777,216 bytes，SHA-256 与预期一致，接收文档的公开视图为 completed。

重新计算中位数、比例及 probe 的均值/样本标准差，均与报告给定精度相符。view 原始 128 个延迟的总和、上中位数及 nearest-rank p95 也与 JSON 一致。

### 方法正确性：PASS，限于已记录的本地适配器路径

生成器指纹与第一轮一致，Bun 1.4.2、Yjs 13.6.33 和依赖锁指纹一致。新 harness 给基线和候选使用同一套公开视图断言，补采了工具、视图、大结果与新增流式时间区间；主比较不再混用第一轮较轻的验证工作量。

报告的主要比值应继续使用增强基线：工具投影 **1,740.883 → 142.269 ms**，视图每个样本的单次延迟中位数再取中位数为 **22.101 → 0.337 ms**。第一轮的 1,872.72 ms / 23.290 ms 属于旧 harness，不能悄悄换成主比较组来扩大改善幅度。

`endToEndMs` 起点位于 user 通知之前，终点覆盖 completed、候选显式 flush、等待 close 和全部副本 apply，排除了冷快照和最终全文验证。候选不再用只覆盖部分同步刷新的 `projectionMs` 代替完成时间。计时仍包含确定性文本生成、采样检查和相应适配器工作，因此是该 harness 的进程内路径耗时。

适配器存在明确差异：基线通过 demo JSON/base64 帧，接收端 `Buffer.from(base64)` 后 apply；候选构造等价 JSON/base64 用于字节计数，但直接把原始二进制帧传给 `SessionDocReplica.applyUpdate`，没有再做 base64 解码。两组可以用于比较这两条已定义路径，不能解释成相同 HTTP/SSE 客户端链路的耗时。`performance.now()` 测得的是墙钟时间，不是 `process.cpuUsage()` 意义的 CPU time；后续报告应统一使用“完整耗时”或“本地端到端耗时”。

三个进程样本适合描述本机大幅差异；未随机交错的执行顺序、GC 和机器负载仍限制小幅差异的归因。经验 p95 来自每次连续的 128 次更新，不是生产用户延迟分布。stream 为同步紧循环，265 帧主要由字节阈值形成，不能据此证明任意真实到达节奏下的 16 ms 刷新效果。

### 结论合理性：PASS

以下是独立复算后可以保留的观察：

| 比较 | 基线中位数 | 候选中位数 | 可支持的结论 |
| --- | ---: | ---: | --- |
| 12k 工具投影 | 1,740.883 ms | 142.269 ms | 本工作量约 12.24 倍加速 |
| 128 次视图总耗时 | 2,883.206 ms | 52.194 ms | 本工作量约 55.24 倍加速 |
| 主编码热快照 | 115,984,977 bytes（V1） | 23,059,321 bytes（V2） | schema、载荷位置与编码共同变化后减少 80.12% |
| 两边均用 V1 的热快照 | 115,984,977 bytes | 24,719,251 bytes | 减少 78.69%，不能将全部缩减归因于 V2 |
| 流式完整耗时 | 186.797 ms | 226.443 ms | **增加 21.22%**，本轮未证明纯流式耗时改善 |
| 流式帧数 | 16,389 | 265 | 当前紧循环下减少 98.38% |
| 等价 JSON body | 25,189,286 bytes | 22,408,849 bytes | 减少 11.04%；未计 HTTP/SSE/TCP 头 |
| tools 完整场景峰值 RSS | 1,456.531 MiB | 1,281.875 MiB | 此场景下降 11.99% |
| view 完整场景峰值 RSS | 971.703 MiB | 1,072.172 MiB | **增加 10.34%** |

冷热数据没有丢失，也不能混成总存储节省：候选热 V2 快照 23,059,321 bytes，加上全部引用 JSON 98,964,890 bytes，为 **122,024,211 bytes**，比基线完整快照高约 **5.21%**。这只是两个编码量的算术相加，既非 heap footprint，也非全部实际网络流量。1 MiB 场景的 2,779 bytes 热快照之外，仍读取了 1,048,634 bytes 完整结果 JSON。

RSS 包含运行时、源文档、接收文档、编码缓冲、公开视图和验证期间临时对象；候选 tools 还额外执行同文档 V1 编码。报告不能将 RSS 的变化直接归因于单个 Y.Doc 或缓存，也不能将热快照下降 80.12% 写成内存下降 80.12%。当前报告保留了 view RSS 回归，边界正确。

### 可复现性：PASS

[benchmark README](../../npm-packages/@peri-sdk/benchmarks/README.md) 已补基线提交导出、锁定安装和第一轮 harness 归档方式；第二轮报告提供候选源码及 harness 解压重建步骤，不再仅依赖现存 `/tmp` 目录。正式复现须使用本轮归档 harness 和对应冻结源码；当前工作区之后继续变化，不能直接代替本轮输入。

## 编码策略 probe 的证据边界

四种策略各三个进程，均校验 16 MiB 文本与同一摘要。convert 的耗时中位数 **162.031 ms**，v2 为 **215.236 ms**，下降约 24.72%，二者为相同的 **16,787,958 bytes / 265 帧**。这足以支持将“V1 收集并合并后转 V2”送入下一轮正式测量。

该 probe 没走 `SessionDocSync`、demo adapter、网络和慢消费者；公开视图配对的是副本 chat 与源 session，不能证明 session 终态已复制。生成器与计时区间也与正式 stream 场景不同，不能把 162.031 ms 与正式基线 186.797 ms 直接计算“最终方案收益”。direct 三次耗时 125.634–171.425 ms 的波动较大，小幅差异没有显著性证据。

## 第一轮反馈及后续准入

第一轮要求的公开历史完整性、非空工具、真实更新失效、completed 断言、完整 flush 计时、冷热字节拆分和环境重建步骤均已补齐。补充基线使用同一增强 harness，纠正了仅拿第一轮较轻工作量比较全场景内存的问题。

本轮归档已有广播重入保护，但还没有后续每订阅者缓冲区隔离、全部销毁入口 guard 和根集合替换的缓存处理；这些修复及新的编码策略必须由第三轮冻结版本的行为测试和正式测量验收。当前契约测试通过不能回填成旧冻结版本也通过。第三轮至少应保留相同生成器、完整校验和原始数据，再检查流式耗时回归是否解决及新增隔离复制的成本；负面指标与局限继续保留。
