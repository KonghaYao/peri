# WorkState 性能重设计：保留 schema17 存储契约

状态：分阶段实施。2026-10-07 的回退恢复 `69e93429` 之前的持久化契约；子 Agent 与 workflow 的纯 revision 读取已改用 SQLite/Turso 共用的 `load_work_revision` 投影，工作通知改用 `load_work_availability`。其余全量状态热点尚未拆解，性能问题未宣称解决。

## 问题与证据

- 记录化 WorkState 的迁移对约 6 GiB、850,144 条历史消息做全量反序列化、哈希、外置载荷和消息行更新。一次独占事务没有可恢复的进度；历史消息解码失败会使全部工作回滚。
- 实际数据库的两次尝试分别运行约 76 分钟和 55 分钟，进程通常占用约一个 CPU 核、RSS 约 40–50 MiB，WAL 超过 4 GiB。原库保持 schema17，`quick_check` 为 `ok`。
- 失败记录属于旧 `tool` 消息，反序列化报 `missing field category`。因此不能将全部历史消息可由当前类型解码作为启动或迁移前提。

## Astra 建议的边界

1. 恢复 `messages.content`、原 Work JSON、命令和回执的 schema17 格式；新建库与已有库使用同一契约。读写格式同时恢复，不能只改表名或版本号。
2. Work 仍归会话执行领域。运行时对外提供小型摘要、按身份读取活动记录和有界待处理页；消息正文按需读取。TUI 消费摘要及变化通知，不因渲染循环加载整个 WorkState。
3. 缓存仅持有可丢弃的摘要或活动记录，以会话和 revision 校验，并限制总字节数。数据库仍是唯一持久化事实源。
4. 保留旧事务、幂等和未完成执行的恢复语义。对不能证明完成的工具、投递或命令，不推断为完成。

## 实施顺序

1. 在旧存储契约上测量 Work JSON 的读取、解析、写入和 TUI 消费路径，记录 CPU 时间、RSS、SQL 次数、WAL 增量与状态大小。
2. 将摘要与按需查询设为领域接口，在存储 adapter 内实现；查询同时限制条数与返回字节数。避免在接纳、渲染和轮询时复制整个状态。
3. 为热路径加入有界缓存和失效规则；在重启、取消、关闭、父子执行及未完成投递场景验证权威数据仍来自存储。
4. 仅在证据表明旧聚合 JSON 写放大仍不可接受时，另行设计仅针对 Work 的持久化调整。不得把消息历史转换与 Work 性能调整绑在同一迁移中。

原 `transition_work`、新 `WorkCommand`、`PayloadRef` 和新实体不能原样接旧库：未投影的请求和工具参数不在 `messages.content` 中，新旧对象 revision 不同，命令序列化也影响摘要、重放及回执匹配。第一阶段保留旧 reducer 与写入协议，仅把查询和调用者逐个改成小投影。

## 验收

- 旧 schema17 库可直接打开；打开不扫描或重写全部历史消息，表结构、版本和消息内容不变。
- 新建库、既有库及远端 adapter 的存储语义一致；旧历史消息的个别解码错误仅在读取该记录时报告。
- 消息追加、历史读取、压缩、撤回、未完成执行与投递、取消、关闭、重开和重启恢复通过契约验证。
- 在大库副本上记录启动时间、峰值 RSS、CPU 时间、WAL 增量和 SQL 次数；另测大 Work JSON 的读写成本。旧单行聚合在物理写入上仍可能放大，不能在未测量前承诺固定资源上界。
