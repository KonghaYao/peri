# Peri 子代理系统的三种并行模式——Fork、Background 和 SubAgent 的设计取舍

> **[Peri Code](https://github.com/konghayao/peri)** — 用 Rust 写的开源 Coding Agent，兼容 Claude Code 生态。<https://github.com/KonghaYao/peri>

有一次我们让 Peri 把一个历史 issue 归档流程拆成了 4 个独立子任务——扫描 issue 目录、提取经验教训、更新 CLAUDE.md、更新 spec/global 索引——四个任务由四个子代理并行执行，主代理汇总结果后一次性写入。整个过程从串行的 8 分钟缩短到 2.5 分钟，而四个子代理之间的上下文全部隔离，互不污染。

Peri 的子代理系统提供了三种并行模式——**Fork 模式**（继承主代理完整上下文的分身）、**Background 模式**（独立运行、结果异步回传的后台任务）、**SubAgent 模式**（完全隔离上下文的专用代理）。三种模式不是三个等级的能力递进，而是三种隔离级别和通信方式，分别对应不同的协作场景——什么时候用哪个、以及为什么不是四种或两种。

## Fork 模式继承主代理完整上下文

Fork 模式会创建一个主代理的完整副本——包括全部对话历史、系统提示词、工具集——然后在这个副本上执行子任务。结果通过**结构化输出**（Scope、Result、Key files、Files changed 四个固定字段）回传给主代理。

典型的使用场景是代码审查——主代理刚完成一轮重构，需要检查代码质量。Fork 出来的审查代理可以访问完整的对话历史，知道改了什么、为什么改、哪些是刻意留的设计决策。如果不 Fork 而是另起一个独立代理，审查代理只能看到最终代码，不知道设计意图，审查质量会下降。

Fork 模式的代价是 token 消耗——完整上下文复制意味着子代理的初始上下文和主代理一样大。如果主代理已经聊了 100 轮，Fork 一个子代理就是再烧一轮完整的上下文，开 5 个 Fork 子代理等于把同一份上下文烧了 6 次。

## Background 模式异步执行，结果通过消息队列回传

Background 模式启动一个独立代理在后台运行，主代理继续执行其他任务而不等待它完成。子代理完成后，结果通过**消息队列**（Peri 内部的统一异步消息通道）回传给主代理，触发主代理在下一个推理轮次中处理。

这种模式的核心优势是时间并行——主代理不需要阻塞等待子任务完成。典型场景是同时让三个子代理分别检查项目的三个模块的编译状态，主代理在这期间可以继续处理用户的消息。Background 模式的一个关键设计约束是子代理不支持实时交互——子代理运行期间不能向用户提问，因为它没有用户界面通道，只有一个消息队列的写入端。如果子代理需要用户确认（如是否删除某个文件），它只能标记为需要人工确认然后退出，等用户通过主代理界面响应后重新启动。

## SubAgent 模式上下文完全隔离

SubAgent 模式创建一个全新的代理，不使用主代理的任何上下文。它只接收一段任务描述（prompt）和一个预定义的代理类型（如 coder、code-reviewer、explorer），依据该代理类型的专用配置执行。

这种模式的核心价值是**上下文隔离**——子代理的工作不污染主代理的上下文窗口。如果主代理在执行一个 200 轮的复杂重构，每次代码审查都用 Fork 模式的话，审查代理的上下文会带进来 200 轮重构对话的 token，其中 95% 对审查任务没用。SubAgent 模式只传审查需要的信息（代码 diff + 项目规范），上下文干净、token 用量低。

SubAgent 模式还有一个衍生好处是代理类型的能力专精——coder 代理有写文件的能力但禁止读项目文档（防止被误导），code-reviewer 代理只能读文件不能写（安全只读），explorer 代理速度快但分析深度有限。每种代理类型的工具集和能力边界由代理定义文件（`.claude/agents/{type}.md`）精确控制，不像 Fork 模式继承主代理的全部工具。

## 通过隔离程度决定 token 成本和准确性

三种模式的选择说到底是在隔离程度、token 成本和准确性之间做权衡。Fork 模式隔离程度最低、token 成本最高、但准确性最高（有完整上下文）。SubAgent 模式隔离程度最高、token 成本最低、但准确性依赖任务描述的完整度。Background 模式在两者之间——隔离程度中等（独立上下文但结果回传），优势是时间并行。决策树比散文描述更直观：

```
子任务是否需要主代理的对话历史？
├── 需要 → Fork 模式
└── 不需要 → 是否需要主代理等待结果？
    ├── 不需要 → Background 模式
    └── 需要 → SubAgent 模式
```

三类任务在 Peri 的实际使用中占比大约是 Fork 15%、Background 25%、SubAgent 60%——大部分子任务是纯工具型，不需要主代理的上下文。

开头的 issue 归档例子中——四个子任务互不依赖、每个都是纯工具型操作（读取文件、提取信息、生成内容），所以用了四个 SubAgent 并行执行。如果用的是四个 Fork，token 成本会翻好几倍；如果用的是四个 Background，主代理需要在消息队列里等四个结果全部回来才能汇总，反而比同步等待更慢。
