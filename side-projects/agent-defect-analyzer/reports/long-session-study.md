# 超长会话场景调研（内部记录）

> 数据源：`~/.peri/threads/threads.db`（活跃库，快照 2026-08-09）｜分析脚本：`src/long_session_study.ts`（可重跑复现，输出 `src/data/long-session-study.json`）｜本文件为内部记录：方法、口径、反证与局限完整披露，供分析追溯。

## 1. 调查方法

### 1.1 数据源与覆盖范围

- 主库 `threads.db`：8,105 线程 / 304,923 消息；主会话（`parent_thread_id IS NULL AND hidden=0`）3,210 个，时间跨度 2026-06-06 ~ 2026-08-09。
- 旁证：`~/.peri/metrics/*.jsonl` 事件流（保留窗口 2026-06-19 起），仅用于 `trap.compact_trigger` 事件匹配。
- 只读访问（bun:sqlite readonly），未写入任何生产数据。

### 1.2 口径声明

- **超长会话（Long）**：主会话且 `message_count >= 500` → 42 个（占主会话 1.3%，占总消息 14.5%）。
- **基准（Base）**：其余主会话 → 3,168 个（含 1,021 个 message_count=0 的空会话，单独披露计数）。
- 计数单位：**按会话**为主，消息级为辅；缺陷密度统一按"每 100 消息"归一化，分母为会话 message_count（0 消息会话计 0）。
- `message_count` 与 messages 表实际行数逐会话核对一致（0 差异）。
- 消息解析：content 为 JSON；`content[].tool_use` 与旧字段 `tool_calls` 为同 id 冗余写入（抽样 2,000 条验证数量与 id 全等），按 content 优先去重，无重复计数。

### 1.3 净化

| 排除类别 | 计数 | 识别规则 |
| --- | --- | --- |
| excluded 消息 | 17,747 | `excluded=1`（full compact 排除，不参与行为/缺陷统计；投影计数除外，见 1.4） |
| system 角色消息 | 398 | `role=system` |
| 注入的 system-reminder | 2,295 条 user 消息含 | user 文本剥离 `<system-reminder>...</system-reminder>` 块后统计 |
| 剥离后为空 | 1,033 | 剥离后无文本（纯注入/占位） |
| 解析失败 | 0 | JSON 解析失败数 |

### 1.4 compact 字段语义（代码确认）

- `excluded=1`：full compact 排除（`compact_v2/full.rs` 写入），消息保留在库中但不送入 LLM。
- `truncated=1`：micro/smart compact 标记（`compact_v2/micro.rs`、`smart.rs` 经 `set_flags_projection` 写入），常伴随 projection。
- `projection` 非空：投影 directive（含 policy_version + entries）。**投影消息可能同时被 excluded**（全库 3,794 条投影中 1,635 条 excluded，43%）。脚本投影计数在 excluded 过滤之前执行，避免漏计。
- 投影消息保持原 rowid（位置不变），故"首条投影的会话内序号"= 最早被压缩消息的位置，而非首次 compact 发生时刻。

## 2. 核心发现

### A. 行为画像：长会话是"一条指令、多轮自动执行"的机器

| 指标 | 超长（42） | 基准（3,168） |
| --- | --- | --- |
| 消息构成 user/assistant/tool | 848 / 9,040 / 9,893（4.3% / 45.5% / 49.8%） | 10,456 / 76,146 / 84,040（6.1% / 44.6% / 49.3%） |
| 墙钟时长 P50 | 4h43m（avg 6h13m） | <1m（一半会话 ≤1 分钟） |
| user 消息数 P50 / avg | 16 / 20（**约每 31 条消息用户才说一句**） | — |
| user 单条文本 P50 / P90 | 63B / 206B | — |
| 工具调用/会话 P50 | 255.5（avg 235.5，共 9,893 次） | — |
| 每 100 消息工具调用 P50 | 47 | 25 |
| 去重工具种类 P50 | 9 | 1（P90=8） |
| 子 agent 数 P50 / avg / max | 3.5 / 7.3 / 68 | 0 |
| Top 工具（总调用） | Read 2,615 > Bash 2,595 > Edit 2,083 > Grep 1,259 > TodoWrite 393 > AgentResult 288 > Agent 203 > Write 195 | — |

观察：长会话以工具往返为主（tool 消息占一半），用户参与度极低；Read/Bash/Edit/Grep 四件套占工具调用 85.6%。子 agent 平均 7.3 个——长会话是"编排型"任务（Agent 工具 203 次）。

### B. compact 生命周期：机制 7 月下旬上线，此前长会话"裸奔"

**机制上线分界（直接观测）**：
- 7/21 前创建的长会话（24 个）：**全部**无 excluded/truncated/projection 痕迹。
- 7/21 及之后创建（18 个）：全部有 compact 痕迹（12 个 excluded>0，6 个 projection>0，8 个 truncated>0）。
- 与仓库 spec 时间线吻合：smart-compact 设计与实现 issue（2026-07-18 设计与 2026-07-22 实现，2026-08-11 已随归档清理删除，现由 compact_v2 策略实现承担）。

**上下文规模对比（机制推演 → 已用数据验证）**：

| 组 | 最终可见上下文 P50 | P90 | max |
| --- | --- | --- | --- |
| 无 compact 长会话（23 个，消息未压缩） | 1,130KB（≈283K token） | 1,622KB | 1,716KB |
| 有 compact 长会话（19 个） | 318KB（≈80K token） | 562KB | 806KB |

- 压缩比例（消息数口径）：P50=73%、P90=95%、max=96%。
- 无 compact 会话的 1.1MB 平均上下文超出常见模型窗口（128K~200K token），**说明此前超长会话必然经历隐式截断/遗忘或超窗风险**。
- 累积可见文本轨迹（每 100 消息）：153KB → 260 → 367 → 455 → 546 → 561 → 723 → 784 → **705 → 604 → 656KB**（均值，超长会话全组）；单会话 max 在 700 条消息时达 1,174KB，随后回落——compact 生效的"锯齿"形态（直接观测）。

**compact 痕迹分布（长会话内）**：
- 含投影会话 6/42，平均投影 50.9 条（P90=107，max=810）；投影消息中 56.3% 同时被 excluded。
- 最早被压缩消息位置：P50=第 2.5 条（2 个会话第 2~3 条消息即被投影——即最早的历史在后续 compact 中被压缩），P90=444。
- truncated 平均 47.5 条/会话（P90=280，max=621）；excluded 平均 249 条/会话（P90=552，max=2,506）。
- 极端案例：`019f9497`（660 消息，架构分析）trunc=621，**94% 消息被截断**，仅 39 条保留。
- metrics `trap.compact_trigger`：长会话 23 次 / 5 个会话（12%），基准 215 次 / 49 个会话（1.5%）——长会话触发概率约为基准的 8 倍（但该事件流仅覆盖近期，见局限）。

### C. 缺陷模式：密度普遍高于基准，但假阳性已排除

启发式（修正后）与每 100 消息密度：

| 缺陷 | 定义 | 超长 | 基准 | 倍数 |
| --- | --- | --- | --- | --- |
| 连续失败链 | 同工具连续 error ≥2 | 0.39（105 次） | 0.15（584） | 2.6× |
| 真死循环 | 非轮询工具同参数连续 ≥3 | 0.13（35） | 0.03（83） | 4.3× |
| 写型迭代 | Edit/Write/Bash 同参数连续 ≥3 | 0.03（7） | 0.02（56） | 1.5× |
| 非搜索振荡 | 非 Read/Grep/Glob/LineEdit 交替 ≥4 | 0.18（52） | 0.10（445） | 1.8× |
| 超大出参 | tool 输出 >100KB | 0.00（1） | 0.02（69） | — |
| 超大入参 | 入参 >50KB | 0.00（1） | 0.00（5） | — |
| 低工具多样性 | 工具 ≤2 种 | 0/42 | 1,904/3,168 | — |

反证记录（启发式初版假阳性，案例验证后修正）：
- 初版 deadLoop=0.51/100，其中 0.38 为 `AgentResult` 重复调用——实为 bg 任务轮询（案例 `019f126f`：同 task_id 轮询 3 次），属正常行为，已从死循环中排除。
- 初版 oscillation=0.82/100，案例 `019ea51f` 显示 Read→Grep→Read→Grep 为典型搜索工作流、Read→LineEdit 交替为读改迭代，属正常；已限定为非搜索工具交替后降至 0.18。
- 写型迭代（Edit 同参数 ×3，案例 `019f2a3d` rowid 141270-141300）实为 UI 微调中的试探性编辑（"Wait, I need to..."→Edit→失败→再试），介于正常迭代与浪费之间，弱信号单列。

结论：超长会话的失败重试、重复调用密度是基准的 2~4 倍，但绝对水平低（每 100 消息 0.13~0.39 次），且高比例可归因为轮询/搜索/迭代的正常形态；真缺陷（写型重复、失败链）存在但非主导。

### D. 结局：超长会话几乎都"正常收尾"

| 结尾类型 | 超长（42） | 基准（3,168） |
| --- | --- | --- |
| assistant 文本 | 39（93%） | 1,886（60%） |
| tool 结果（非 error） | 3（7%） | 118（4%） |
| user 提问后无响应 | 0 | 108（3%） |
| tool error 结尾 | 0 | 35（1%） |
| 无消息（空会话） | 0 | 1,021（32%） |

- 超长会话无一条以 tool error 或"用户提问无响应"结尾——**能撑到 500+ 条的会话几乎都是成功任务**（幸存者偏差：失败任务不会长，见局限）。
- 3 个以 tool 结果结尾的会话（`019f26d4`、`019fa426`、`019fe475`）is_error=false，即工具正常返回后会话中断/结束。
- `agent_status` 字段全部为 `active`（会话结束后未更新），**无区分度，弃用**。

## 5. 局限

1. **幸存者偏差**：≥500 消息会话天然是"能跑完"的任务；失败/放弃的任务不会长。超长会话"结局健康"不能推及普通会话。
2. **metrics 窗口**：`trap.compact_trigger` 事件流仅覆盖 2026-06-19 之后（且 trap 机制本身 8 月才上线），compact 触发次数低估；DB 内痕迹（excluded/truncated/projection）为主口径。
3. **compact 前后对比的混杂**：无 compact 组全部创建于 7/21 前（模型、工具集、任务类型可能不同），"上下文规模差"包含机制因素与时期因素，无法完全分离。
4. **缺陷启发式边界**：同参数判定基于 JSON 前 200 字符截断；真死循环/迭代试错边界模糊，弱信号单列处理。
5. **上下文规模估算**：用"非 truncated 消息的 content 字节累积"近似 LLM 实际上下文，未计 system prompt、工具 schema、压缩指令本身的 token。
6. **agent_status 字段无区分度**（全 active），结局仅能由最后一条消息推断。
7. 投影消息的 `entries` 内容未逐一核验（policy_version/策略细节在 `compact_v2/projection.rs`，本报告仅统计数量）。

## 7. 人力定性评估（subagent 三组并行，13 会话抽样）

> 方法：从 42 个超长会话分层抽样 13 个（compact 前 6 + compact 后 7；覆盖开发/设计/bug 排查/分析四类），导出完整可见消息序列（`src/export_sessions.ts`，/tmp/long-sessions/），3 个 code-reviewer subagent 并行逐会话精读，输出统一模板评估。所有判定均有 [#n] 消息序号引文。

### 7.1 成功率

| 结论 | 会话 | 判定依据 |
| --- | --- | --- |
| 完成（8） | 019f257b、019f2a3d、019f9497、019fad4c、019fbd31、019fb6de、019fccee、019fdb17 | 用户明确验收/授权提交（"good,完美"#569、"提交代码"#793、commit 汇报 #880/#1600） |
| 部分完成（3） | 019ea51f、019f1c4e、019f259c | 核心交付达成但子任务未闭环（per-agent 关联未做 #508、输入框新回归 #727、table 泛型回退 #1134） |
| 无法判断（1） | 019f26d4 | 用户全程放手且从未验收（"/handoff" 暂停 #942） |
| 进行中（1） | 019fe475 | 末尾仍在修复链（#2680），验收判据未达成 |

- 完成率 8/13（62%）；计入"有交付物"则 11/13（85%）；**零失败**——与定量"93% 以 assistant 文本结尾、0 tool error 结尾"互证：能撑到 500+ 消息的会话几乎都是成功任务（幸存者偏差成立）。
- 未完成/未闭环的 4 个，断点均为"新需求追加"或"修复引入新回归"，无一因 Agent 放弃。

### 7.2 用户心路历程（13 会话共性）

**参与模式分两类，与任务类型强相关**：
- 视觉/审美任务（TUI 设计、渲染打磨）：**手把手调试型**——高频短指令、贴终端截图/输出验收（019f2a3d 贴 4 次、019f259c 贴渲染输出），情绪起伏最大（"good,完美"与"你为何不遵守"#523 高频交替）。
- 分析/重构/bug 排查（重活）：**放权型**——"继续"×N、22 小时零干预（019fb6de 可见仅 7 条用户消息）、10.5~18.5 小时马拉松仅插话几次。

**情绪规律**：
- **用户对"慢"和"挂"的容忍度显著低于对"错"**：C 组三会话的全部抱怨针对等待时间（"你的 test 特别慢"、"卡死了"），无一针对修复方向。
- 信任消耗三杀手（按伤害排序）：① 声称完成但实际未生效（"example 一点都没有改到"#918——用户被迫自行验证）；② 同一症状反复修（闪退修 4 次、高度问题 5+ 轮）；③ 重构反复改动同一模块（"输入框又被改了,已经被改了好多次了"#677）。
- 信任重建机制：快速认错+回滚（被否后立即回滚 #499-#505）、量化验证证据（"1136 pass, 0 fail"、commit hash）、采纳用户技术方案（blockquote 反色方案 #402）。
- 用户是顶级协作者：主动喂诊断材料（贴日志 #406、贴复现命令 #1111、给根因假设 #928），每次反馈都是高信噪比增量——这是会话能持续 500+ 条的关键结构性因素之一。

### 7.3 Agent 反应模式（13 会话共性）

- **工作风格两极**：直接执行（视觉迭代"改-跑-用户看-再改"）vs 流程控制（多人协作流水线 00-context→explorer×2→plan×2→gate→coder×2→reviewer×2→verify、TDD、三轮 code-review 循环收敛到零阻断）。
- **根因定位很少打转**：插桩证据链（三点调试日志→字节对比→CRDT LWW 冲突）、假设排除法（Rewind 三假设逐排除）、架构契约否决（TUI 驱动方案因违反契约一轮内否决）。**真正的打转在工具/环境层**：旧二进制连跑数轮（靠日志时间戳识破）、workspace 路径 8 轮（"已连续 8 轮推测深挖无新证据"系统提醒后才醒悟）、Grep glob 反复空结果改 Bash rg。
- **验证闭环是超长会话的燃料**：build+test+clippy 全套、负向搜索 0 真命中、独立 review agent 兜底——持续产出"进展可见性"，用户因此愿意继续投入。
- **compact 恢复质量高，无"失忆"**：摘要引用用户原话+文件行号+错误历史+明确"下一步"，22 小时流程（019fb6de）与 18.5 小时排查（019fdb17）均无缝接续。
- **但存在"选择性失明"案例**：019fe475 摘要 §2.3 白纸黑字写明 wire 层 `session/create→chat/create`，agent 却按"ACP 域保留"漏改，直到 e2e 验收失败才确认系统性遗漏（#2632），引发雪崩式连带修复——**摘要信息与执行规则冲突时，规则覆盖摘要**。
- 迭代浪费的典型：019f257b 状态 emoji 改 4-5 轮（初版理解与用户审美差距）、019f2a3d 流式闪退同一症状修 4 次（最终定位 unicode 字节切片）——即定量指标中 iterLoop/重复的"人性化表达"，均最终收敛。

### 7.4 与定量数据的交叉验证

| 定量发现 | 人力评估结论 | 一致性 |
| --- | --- | --- |
| 93% assistant 文本结尾、0 error 结尾 | 8 完成+3 部分+1 无验收+1 进行中，零失败 | 互证（幸存者偏差） |
| iterLoop/重复密度低（0.03/100）但存在 | 闪退 4 修、高度 5 轮、emoji 4-5 轮——真实存在且是用户感知的"浪费"主源 | 互证；定性补充了伤害权重 |
| compact 控制上下文（-72%） | 摘要质量高、22h 流程无缝接续，无失忆 | 互证 |
| 超长会话工具调用密度高（47/100） | 验证闭环文化（test/clippy/负向搜索/独立 review）即工具高密度来源 | 互证 |
| 用户参与度低（每 31 条消息一句） | 放权型任务 22 小时零干预；但视觉任务介入极深 | 细化：参与度因任务类型两极分化 |

### 7.5 对产品/机制的建议信号（机制推演，未验证）

1. "声称完成但未生效"是信任杀手 → 完成汇报附最小可验证证据（截图/测试名/命令输出）的机制价值高。
2. 反复打磨类任务（视觉迭代）是超长会话结构性来源 → compact 摘要应保留"用户审美反馈历史"（当前摘要已含，质量高）。
3. 马拉松排查中用户只抱怨慢/挂 → 长测试前确定性处理（--test-threads=1、pkill 前置清理）可避免用户接管。
4. 验证口径错位（wire 术语遗漏存活到 e2e）→ 批量变更前先列"四层术语清单"（wire/持久化/日志/前端）可省收尾雪崩。

## 8. Agent 工具派发研究（补充专题）

> 脚本 `src/agent_dispatch_study.ts`，输出 `src/data/agent-dispatch-study.json`。口径：派发记录 = 父会话可见 assistant 消息中的 Agent tool_use；子 agent = threads 表 parent_thread_id 指向父会话的线程（308 个，全部 hidden）。**时间类指标以子 agent 线程创建时间为准（不受消息压缩影响）**。

### 8.1 派发概况

| 指标 | 超长（42） | 基准（3,168） |
| --- | --- | --- |
| 有派发会话 | 30/42（71%） | — |
| 可见派发次数 | 203（平均 4.8/会话，max 23） | 3,317（P50=0） |
| 每 100 消息派发 | 0.78 | 1.93 |
| 后台派发（run_in_background） | 40% | 26% |
| fork 派发 | 0 | 0 |

- **密度反转**：超长会话每 100 消息派发密度**低于**基准（0.78 vs 1.93）——长会话是"低频持久"的派发者（绝对值 4.8 次/会话 vs 基准 P50=0）；基准里大量小会话"一问就派"造成高密度。
- 子 agent 308 个（7.3/会话，max 68）；但可见派发仅 203 次——**105 次派发记录（34%）被 compact 从可见消息中吞掉**；4 个会话有子 agent 但可见派发=0。凡涉及"派发次数"的统计均受压缩低估，子 agent 线程表是完整口径。

### 8.2 派发内容

- description 极短（P50=16 字符，P90=27）——命名式标签；prompt 是主体（P50=965 字符，P90=3,492）。
- subagent_type 分布（长，可见 203 次）：explore 61 > coder 59 > code-reviewer 26 > general-purpose 22 > explorer 20 > verification 5 > plan 3——**探索型（explore+explorer=81）与实现型（coder=59）占 69%**，审查型（code-reviewer+code-review=27）占 13%。
- 基准分布更杂（25 种类型含 task1-impl 等一次性定制名），超长会话类型收敛到 8 种——长会话派发更"纪律化"。

### 8.3 子 agent 工作量与结局

| 指标 | 超长子 agent | 基准子 agent |
| --- | --- | --- |
| 消息数 P50 | 16（avg 30.8） | — |
| 墙钟时长 P50 | 3m | — |
| done | 293（95.1%） | 4,390（95.5%） |
| error | 13（4.2%） | 121（2.6%） |
| cancelled | 2（0.6%） | 8（0.2%） |
| active（进行中） | 0 | 80 |

- 长会话子 agent 错误率略高于基准（4.2% vs 2.6%），但绝对数低；error 子 agent 中 6 个为 0 消息（启动即失败），7 个有实质工作（最多 434 消息的 explorer——任务大且失败）。
- 子 agent 平均 16 条消息 / 3 分钟——典型"短任务单元"。

### 8.4 失败形态（metrics 旁证，143 次 Agent tool.error，31 种消息）

1. `interrupted by user`（用户取消）
2. LLM 网络/流式错误（unity2.ai、opencode.ai 端点失败）
3. `Max iterations exceeded (200)`（子 agent 死循环上限触发）
4. `Maximum 3 concurrent background tasks reached`（后台并发上限 3）
5. `cannot find agent definition 'code-reviewer'`（agent 定义缺失，配置漂移）
6. `missing required parameter prompt`（派发参数不完整）

### 8.5 并行与节奏（时间口径）

- **最大并行度：P50=1.5，max=3**（长会话）；基准 max=8。长会话很少超过 3 个并发——与"后台并发上限 3"一致（metrics 有撞限错误），且长会话以顺序/双路派发为主。
- **派发相位（子 agent 创建时间，308 个，不受压缩影响）**：early（前 33% 时间）=193（63%）、mid=36（12%）、late=79（26%）。
  - **修正前的可见消息口径给出 late=0 的错误结论**——被压缩的后期派发全部丢失；时间口径揭示真实模式：**前期为主（探索+并行实现启动），中期稀疏，后期仍有四分之一派发**（收尾审查/验证）。
- 连续派发间隔：P50=6 分钟、P90=45 分钟（max 903 分钟=隔夜续跑）——派发是"高频脉冲 + 长间隔"节奏。
- 每 100 消息派发 0.78 → 平均每 128 条消息派发一次。

### 8.6 与人力评估的交叉验证

- 人力评估观察到"多人协作流水线"（019fb6de：explorer×2→plan×2→coder×2→reviewer×2→verify）——即 8.2 中 explore/coder/code-reviewer 三型主导的量化镜像；"3 个后台 explorer 并行"（019f9497）与 8.5 并行度 max=3 一致。
- 人力评估中"reviewer 揪出 P1 阻断→修复→再 review"的收敛循环，对应 code-reviewer 在长会话中的高占比（13%，仅次于 explore/coder）。
- 派发后期稀疏（26%）与人力评估"会话后半主 agent 自己收尾打磨、不再派发"互证。

### 8.7 机制信号（推演，未验证）

1. 派发次数统计需以子 agent 线程表为准（消息压缩吞掉 34% 派发记录）——任何基于可见消息的"派发频率"研究都会系统性低估。
2. 后台并发上限 3 与长会话并行度 P50=1.5 匹配，撞限错误存在但低频——上限设置与使用形态自洽。
3. `cannot find agent definition` 错误提示 agent 目录与派发代码存在配置漂移风险（低频，1 类）。

### 9.3 时间点揭示的规律

1. **信任杀手高度聚类在无 compact 时代（7/3-7/4）**：#918/#950/#523 全部发生在 compact 上线前一周内。两种解释并存：① 当时无压缩、上下文裸奔，agent 长程一致性差（改动丢失/理解偏差概率高）；② 7/3 是 TUI 大重构日，4 个超长会话同日并行，任务本身最密集。**证据不足以区分，但时间聚类本身是事实**。
2. **compact 上线（7/21）后，抽样会话中未再出现"声称完成但未生效"级别的信任杀手**——被压缩会话的评估更多是"摘要信息利用不充分"（8/9 选择性失明），而非裸奔时代的"修改丢失"。
3. **马拉松排查（>10 小时）全部出现在 8 月**（8/4、8/7、8/9）——与 compact 时代的 full-compact 主导期重合；8 月也是超长会话占比回升期（W31 1.4% → W32 2.3%）。
4. 消息引文无绝对时间戳是研究限制：事件只能定位到"会话内第 N 条可见消息"，跨会话对比只能到天/小时粒度。
