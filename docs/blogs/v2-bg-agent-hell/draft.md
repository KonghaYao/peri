# Peri 的 Async Agent 并发地狱——三个竞态条件、三个 Issue、一次完整的生命周期修复

> **[Peri Code](https://github.com/konghayao/peri)** — 用 Rust 写的开源 Coding Agent，兼容 Claude Code 生态。<https://github.com/KonghaYao/peri>

用户在 Peri 里输入了一条消息"帮我在 A 分支改 bug，B 分支重构，C 分支写测试"。Agent 分析后在同一轮回复中连续调用了三次 Agent 工具，全部带上 `run_in_background: true`。三个 Async Agent 各自通过异步方式启动——将任务交给独立的异步协程运行——状态栏显示 `· 3 agents` 计数，一切正常。

几分钟后，前两个 Async Agent 的 callback 消息依次出现在消息区——"[后台任务 bg-xxx 已完成] 输出: ..."。用户等着看第三个的结果，但它从不出现。更糟的是，主 Agent 的 loading spinner 永远在转，输入框却仍可输入新消息——界面没有冻死，但这一轮对话永远结束不了。用户只能手动 Esc 退出。

三个 Async Agent 明明都跑完了，Tasks 面板计数正确归零，通知条也闪现了完成提示——但最后一个 callback 消息丢失了，loading 也不会停。

## 三层级的三个独立竞态条件

这个场景暴露的不是一个 bug，而是 Async Agent 并发运行时的三个独立竞态条件。它们发生在不同的层级、不同的时间窗口、由不同的设计决策引入。

### woken_once 守卫限制 Agent 每会话只醒一次

Peri 的 ReAct 循环——即 Reasoning（推理）和 Acting（执行）交替进行的 Agent 主循环模式——在每轮结束时会检查消息队列是否有新消息。如果有用户输入或 Async Agent 的异步通知，就继续下一轮。队列为空时，主 Agent 进入阻塞等待，直到异步事件触发唤醒信号。这条唤醒链路的路径是固定的——

```
Async Agent 异步启动完成
  → 完成回调被触发 → 路由到对应的结果处理器
  → 将结果消息写入待处理队列 → 触发主循环唤醒信号
```

在单个 Async Agent 场景下，这条路径已经验证通过。三个 Async Agent 同时运行时，每个完成后都会走一遍「完成回调 → 写入队列 → 触发唤醒」。到这里链路仍是通的——事实上前两个 Async Agent 的 callback 消息正常出现了。问题在于 Agent 能否响应第二遍和第三遍唤醒信号。

主 Agent 进入阻塞等待之前有一道叫 `woken_once` 的守卫。它的语义是"Agent 在整个生命周期中最多被唤醒一次"。在单个 Async Agent 场景下这没有任何问题——唤醒一次，处理完结果，继续跑。三个 Async Agent 依次完成时，第一个唤醒了 Agent，Agent 处理完它的结果进入下一轮推理-执行迭代。第二个 Async Agent 完成时也走了完整链路，但此时 Agent 正在跑推理（Reason）阶段，消息已经写入队列，本轮结束（End）阶段正常清空队列消费——第二个 callback 也正常显示了。

第三个 Async Agent 完成时，Agent 恰好跑完第二个 callback 的处理，再次进入结束阶段。队列为空，Agent 准备第三次等待唤醒。但 `woken_once` 守卫拒绝了——Agent 已经醒过一次，不再等待。第三个 Async Agent 的回调数据已经写入了消息队列，但没有人来消费它。Agent 的循环直接返回已完成状态，loading 无人清除，callback 消息永远留在队列里。

修复是移除 `woken_once` 守卫。Agent 在空闲等待判断为真时反复进入阻塞等待，直到所有异步任务完成、空闲等待判断返回假时自然退出。每个 Async Agent 的完成链路都能被正确响应。

### 阻塞等待无超时导致 hung Agent 永久阻塞

移除 `woken_once` 解决了"Callback 不等后续"的问题，但暴露了另一个更严重的问题——阻塞等待本身没有任何超时机制。它是一条纯等待路径——

```
消息队列为空 → 检查活跃任务计数（> 0） → 进入阻塞等待唤醒 → 永远等不到
```

阻塞等待内部是一个持续等待唤醒信号的循环，连取消标记（cancel token）都没有注入。它的唤醒只依赖外部事件——完成回调 → 写入队列 → 触发唤醒。如果所有活跃 Async Agent 都挂死——比如异步任务卡在 LLM 调用、工具执行或中间件 hook 上——完成回调永远不被调用，写入队列永远不触发，唤醒信号永远不发生。

而空闲等待判断检查的是后台任务注册表中活跃任务计数——只要注册表里还有状态为 Running 的任务，这个判断就返回真。一个 hung 的 Async Agent 永远不会被标记为完成，它的状态永远停留在 Running。于是空闲等待判断永远为真，阻塞等待永远卡住，整个 session 永远卡死。

移除 `woken_once` 之前这个问题也被掩盖了——Agent 最多等一次，等到第一次 awake 后就不等了，hung 的后续 Async Agent 只是丢结果而已。移除之后，Agent 会反复等——任何一个 hung Agent 都能导致整条 session 永久阻塞。

检查代码库后发现，现有的防御机制为零——没有 Async Agent 级超时，没有阻塞等待超时，没有心跳检测。唯一退出路径是并发选择机制中的用户取消信号，要求用户手动触达。最大 500 轮迭代限制也无效，因为阻塞等待本身不消耗迭代计数。

针对这个问题，相关 issue 提出了双层超时的推荐方案——Async Agent 级别 600 秒超时（异步超时机制包裹主循环）+ 阻塞等待级别 180 秒 idle 超时（并发选择加超时分支）。第一层在 Agent 层面杀死 hung task，触发完成回调 + 唤醒链路；第二层在所有 Async Agent 都没有产出时兜底退出。该方案目前处于设计阶段，尚未在代码中落地，当前通过用户取消信号和其他机制缓解。

### kill 路径与正常退出的时序竞争

前两个断链在 Agent 生命周期内部。第三个发生在 workflow runner 的进程管理层面。

Workflow 任务管理器的终止方法的职责是终止指定 workflow run——发送 kill 信号给 runner，触发清理流程。一个典型的 workflow runner 内部有两个并发任务——消息循环（消费 Node 进程的 JSON-RPC 消息）和主等待循环（等 kill 信号或消息循环完成）。

kill 路径的流程是——发送 kill 信号 → runner 收到信号 → 向 Node 进程发送 kill 请求 → 终止子进程 → 中止消息循环 → 写 killed 状态文件 → 发送最终 killed 结果。正常退出路径是——Node 进程自己发来完成消息 → 消息循环写状态文件 → 发送最终正常结果 → 主等待循环的消息完成分支匹配。

这两条路径在时间上完全独立。当 kill 信号到达 runner 时，消息循环可能已经自然完成了正常退出流程并即将写状态文件。kill 分支执行中止消息循环试图终止它——但消息循环可能刚好已经写完了自己的状态文件和结果发送。结果取决于执行时序——结果发送用的是观察通道（watch channel），后到的值覆盖先到的值。如果消息循环的 "failed" 结果覆盖了 kill 分支的 "killed" 结果，用户看到的 workflow status 就是错误的。

反过来，kill 分支先执行中止消息循环后自己写状态文件和发送结果。如果消息循环在此之后才开始执行未完成的清理——它检测到 stdout 关闭，以默认 status="failed" 重写了状态文件——同样导致 kill 事实丢失。

当前修复是在 kill 路径写 killed 状态之前显式调用中止消息循环，阻止消息循环检测到 stdout 关闭后以默认 status="failed" 覆写状态文件。由于中止操作不保证同步终止，消息循环可能恰好在中止生效前完成写入，时序竞争仍存在一个小窗口。相关 issue 提出了更彻底的方案——让两条路径共享同一个出口、统一出口路径——该方案处于设计阶段，尚未落地。

Runner 层面还有一个细节——子进程句柄。在任务注册表的 kill 方法中，早先版本会在 kill 后调用强制终止子进程句柄。但这会导致 runner 的清理路径被中断——kill 流程中的清理步骤（终止子进程 → 写状态文件 → 发送结果 → 移除活跃通道 → 回收资源）永远不会执行完整，注册表里的活跃通道泄漏在内存中。修复是移除这里的强制终止，让 runner 自行完成全部清理。

## 三个 Issue 的串联关系

| Issue | 症状 | 根因 | 修复 |
|-------|------|------|------|
| Async Agent 完成后不续跑 | 合成消息不出现，loading 永久转 | 完成回调→写入队列→唤醒信号 的链路未生效 | 阻塞等待下沉到循环内部 |
| 多 Async Agent 最后一个 callback 丢失 | 前 N-1 个正常，第 N 个不出现 | `woken_once` 限制只等一次 | 移除 woken_once 守卫 |
| hung Async Agent 永久阻塞 | 阻塞等待永远不醒来 | 无超时，无心跳，唯一依赖是完成回调→写入队列→唤醒信号 | Async Agent 超时 + idle 超时双层防护（方案设计中） |

每一个修复都改变了系统的行为边界。`woken_once` 的移除让 Agent 能处理多个 Async Agent 的 callback，但也让 hung Agent 能导致整条 session 永久阻塞。双层超时的设计思路堵住了 hung Agent 的漏洞，但超时的阈值设置（600s / 180s）不是拍脑袋的——工具调用有 300s、系统命令有 120s、插件协议有 120s，600s 给 Async Agent 最宽松的空间跑完一组工具调用链。

## 并发根因分析

最初收到用户反馈时，直觉是"多个 Agent 同时完成时，callback 事件在消息队列（MQ）里被覆盖了"。但前两个 callback 正常显示说明消息队列的多生产者单消费者模型是正确的——问题不在数据竞争，而在消费者提前退出。退出的原因是 `woken_once` 守卫只允许一次 wake。允许多次 wake 的风险在于——第一次 wake 后如果 Async Agent hung，Agent 将永久阻塞。

这是一组互相咬合的约束——单次醒 → 丢失 callback → 允许多次醒 → 可能永久阻塞 → 需要超时 → 超时值要覆盖最长合理执行时间。加上 kill 路径的进程管理竞争，Async Agent 的生命周期涉及六层组件跨越（推理-执行循环 / 消息队列 / 后台任务注册表 / 异步任务 / workflow runner / Node 子进程），每一层都有自己的状态机和退出条件，边界条件在并发场景下逐层叠加。并发场景下没有中间态——三条断链任何一条未被覆盖，用户看到的就是 loading 永远在转。开头那个场景——用户等了 5 分钟没等到第三个 callback、loading 永远在转——程序没有挂，Agent 在并发场景下存在三条断链，分别在三个层级上阻断了正确行为。
