# Peri Agent 编辑工具设计复盘——行号和 Diff 为什么不如字符串替换

> **[Peri Code](https://github.com/konghayao/peri)** — 用 Rust 写的开源 Coding Agent，兼容 Claude Code 生态。<https://github.com/KonghaYao/peri>

翻开 Peri 的编辑工具调用日志，284 条失败记录里有超过七成是因为**行号偏移**——模型要改某个文件的第 58 行，实际代码在第 63 行，偏了 5 行，操作报告成功但代码完全没动。

这不是 Peri 独有的问题。[Claude Code](https://github.com/anthropics/claude-code) 和 [Aider](https://github.com/Aider-AI/aider) 的早期版本也在行号和 **diff**（代码差异补丁，描述从 A 到 B 的逐行变化）之间反复调试，最后都不约而同地收敛到字符串替换。Peri 的编辑工具经历了三个版本迭代，每次都加错了东西，直到第三版彻底删掉前两版的设计，只用字符串替换。以下复盘三次迭代的决策节点和错误判断。

## 第一版行号定位，3-5 行偏移是默认结果

最初的设计和大多数代码编辑工具一样——模型输出目标文件的路径和行号范围，框架读取那些行、替换内容、写回。这个方案在短文件里工作正常，文件超过 200 行后行号偏移开始出现。原因有两个：第一，模型在生成编辑指令时依据的是它上一次读取到的文件快照——如果前一轮工具调用修改了文件（如插入或删除了几行），这个快照已经过时；第二，模型输出行号时本身有精度误差，它不擅长把文本内容精确映射回行号，尤其当目标行前后有多行相似代码时。

偏移 3-5 行的后果不是报错而是**静默正确**——替换了错误的行，但工具返回成功。出错未被检测到，Agent 继续下一步，后续工具调用基于被污染的文件状态操作，错误逐步累积并放大。最严重的一次，一个重构任务因为连续三次静默行偏移，最终删掉了一个还在使用的函数，编译失败时 Agent 已无法正确解析自己修改过的文件。

## 第二版加 Diff 校验，错误率下降 40% 但匹配失败翻倍

第二版的思路是在行号定位的基础上加一层 diff 校验。工具在替换前先检查 old_string（期望替换掉的文本）是否与目标行匹配，不匹配就拒绝执行并返回错误。

这层校验确实阻止了大部分静默正确——偏移超过 1 行就会触发不匹配。但新问题出现了：模型在生成 diff 时经常错误估计空白字符（缩进用 tab 还是空格、空行有几个换行符），导致 old_string 与文件内容的差异只在于不可见字符。校验报不匹配，但人类看两段代码完全一样。diff 格式本身对模型不友好——模型需要先理解行号、再匹配内容、再生成差异描述，三个步骤串行，每一步都可能出错。用行号定位的问题没解决，反而多加了一个可能出错的 diff 层。第二版上线后的错误率比第一版下降了约 40%，但剩下的 60% 几乎全是 diff 匹配失败或空白字符不匹配。

## 第三版删掉行号和 Diff，只用原始文本片段做查找替换

第三版的设计思路反转了过来——让模型直接输出要改的那段文本，而不是描述它在哪里。模型输出 old_string（文件中的**原始文本片段**）和 **new_string**（替换后的文本）。框架在文件中查找原始文本片段的精确匹配，找到就替换，找不到就返回错误信息（含附近上下文供模型重新生成）。没有行号、没有 diff 格式、中间状态全部消除。

这个简化解决了前两版的所有问题。行号偏移不存在了——原始文本片段是内容匹配，不依赖行号。diff 格式错误不存在了——根本不需要生成 diff。空白字符问题也大幅减少——模型直接输出文本内容而非描述差异，空白字符就是文本的一部分。唯一的新问题是原始文本片段必须精确匹配文件内容，如果模型微调了空白或注释匹配会失败。实践中的解决方式是工具返回错误时附带目标文件的相关片段（前后各 20 行），模型看了上下文后通常一次就能修正原始文本片段重新提交。

## LSP 符号定位方案被排除：多步串行引入新出错点

讨论中反复出现的一个替代方案是用项目的 **LSP**（语言服务器协议，IDE 中用于跳转定义、补全等服务）来做符号级定位——模型不说改第 58 行，说改 invoke 函数里的第三个参数，LSP 在 **AST**（抽象语法树，代码的结构化表示）上精确定位。这个方案没有采用，原因很实际。

不是所有项目都有 LSP——Peri 的目标用户面对的代码库可能没有配置 language server，或者配置了但启动失败。不能把编辑工具的可靠性绑定在一个可选的辅助服务上。而且 LSP 定位到的是符号（函数名、变量名）而不是文本——模型要改的是参数值或某个表达式，不是整个符号。把 LSP 定位和文本替换拼接起来，又回到了多步串行的问题——每一步都是出错点。字符串替换看似粗糙，反而成了优势——它只有一个出错点（原始文本片段匹配），定位和替换是一步完成，失败时反馈信息足够模型自我修正。

第三版上线后，编辑工具的错误率下降到 7% 以内，且剩下的全是真正的匹配失败——行号偏移、diff 格式问题和静默正确全部消除。Agent 能够检测到编辑失败并重新尝试，这是比不出错更重要的能力。
