场景和边界：

- **tools**：同一 turn 中 12,000 工具，每 10 个切换 assistant message，共 1,200 个 assistant。输入 data 960 ASCII 字节，加 index/path 约 1 KiB；结果 contentText 4 KiB 与 rawOutput.data 4 KiB，总计约 8 KiB。原始参数和结果 JSON 共 **111,050,670 字节**。每个工具 running → completed。投影计时不含生成器与 JSON 字节统计；随后完整编码两个文档，用 V1 冷快照复制到新文档，并逐工具校验参数、结果和终态。
- **view**：重新生成相同 12,000 工具历史，创建 SessionViewStore；再发送 128 次 1 KiB 文本更新，每次 `await Promise.resolve()` 等待独立发布。延迟包含 ACP accept 与视图微任务，检查 128 次发布与 128 KiB 完整文本；同时统计首个未改变工具对象的身份复用。
- **stream**：16,384 × 1 KiB，合计 **16,777,216 字节**。通过基线 SessionDocStream 的真实 JSON/base64 帧路径同步复制至新 Y.Doc，包含初始冷快照、user、完成终态。计数区分 decoded V1 update bytes 与 JSON event body bytes；不含 SSE/HTTP/TCP 头。投影计时包含同步通信计数与 apply，apply 同时独立计时。最终通过公共 `readSessionView` 校验全文长度和 SHA-256。
- **large**：1 个工具，contentText 恰为 1 MiB，rawOutput 为 index/bytes 摘要。参数与结果 JSON 共 **1,049,635 字节**，冷快照复制后精确校验。

## 观察与推断

**观察**：12k 工具首批 1,000 个约 25–27 ms，最后 1,000 个约 293–324 ms；完整快照约为原始参数与结果 JSON 的 1.04 倍。三个 view 样本共 384 次发布，首个未改变工具没有一次保持对象身份。1 MiB 结果几乎完整进入默认冷快照。16 MiB 文本全部精确往返，最快与最慢全场景仅 218–240 ms。

**推断**：随历史增长的工具投影成本与基线 `acceptTool` 每次扫描 entries 的实现一致；视图对象重建与 `readSessionView` 的全量遍历及工具递归复制一致。把大载荷移出热文档、缓存未改变条目、为工具建立直接归属索引，有明确的优化对象。这些推断需要第二轮同生成器验证，不能仅凭实现形态声称收益。

**未支持的假设**：本基线没有观察到 16 MiB Y.Text 追加本身严重变慢，当前数据不支持仅为这个场景新增长文本分片结构。帧数与 JSON/base64 字节可减少，但本实验没有真实 socket、网络延迟或慢客户端，无法由这些数字推导生产吞吐提升。

## 局限与后续

- 内容完全确定；Yjs 自行随机生成 clientID，因此变长整数编码可能带来快照字节的小幅差异。工作量、最终文本及对象数均不依赖随机值。
- RSS 为整个进程峰值，包含 Bun、两份文档、编码缓冲与验证过程。12k tools 的 1.29–1.41 GiB 不能解释成单个长期保留 Y.Doc 的占用。
- 流式生成没有模拟到达间隔，view 场景才逐事件让微任务发布。candidate 的批处理需记录字节阈值、flush 次数及完成 flush，不能把同步合并后的帧数当作任意真实 cadence 的结果。
- 基线 demo 每次连接发送全量快照，没有状态向量 resume、慢消费者限额、版本化按需载荷读取；这些项第一轮为 **不适用**，没有通过包装器补造支持。乱序/重复 Yjs 原语能力也未代替应用桥接契约测试。
- 第二轮使用相同生成器、同一运行时与隔离采样，分别校验热文档引用和按需完整载荷，并由独立验证 agent 审查此报告与 JSON。预算内已完成所有场景，无削减规模。
