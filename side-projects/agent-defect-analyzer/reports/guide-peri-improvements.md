# Peri 超长会话改进指南（Guide）

> 来源：超长会话专题调研（`reports/long-session-study.md`，含定量分析第 1-6 章、人力评估第 7 章、Agent 派发第 8 章）。
> 本指南回答一个问题：**从 42 个超长会话（500~2680 消息）的实证数据里，peri 产品和"人与 AI 协作"能吸收什么？**
> 每条建议标注：证据强度（直接观测 / 机制推演）、落地层面（Prompt / 机制 / TUI）、优先级（P0/P1/P2）。
> 数据均可从 `long-session-study.json` 与 `agent-dispatch-study.json` 复现。

---

## 一、信任与人机交互（最高优先级——所有证据中最痛的伤）

> 时间点参考：以下案例的发生时间与时间线全景见研究报告第 9 章。要点——**信任杀手案例全部聚类在 7/3~7/4（compact 上线前一周）**；8 月的痛点转向"等待与摘要利用"。

### 1.1 完成汇报必须附"最小可验证证据"（P0，Prompt 层）

**证据**：人力评估中"声称完成但实际未生效"是信任杀手第一名——`019f259c` 用户抓包发现"example 一点都没有改到"（[#918]）、"继续，没有生效"（[#950]）；`019f2a3d` 用户对未生效的修改质问"你为何不遵守"（[#523]）。这些时刻用户被迫自行验证，信任单次消耗最大。

**建议**：完成类回复（尤其"我改好了/修复了/完成了"）强制附带可验证的最小证据之一：具体测试名+通过输出、关键 diff 摘要、运行命令与退出码。空口"完成"视为不合格输出。落地于 agent prompt/输出规范，TUI 可在完成汇报时提示补充证据。

**反例确认**：`019fb6de`（22 小时重构）中"负向搜索 0 真命中""lefthook 超时后重试"等量化证据是用户继续放权的基础——证据文化已被证明有效，需要的是制度化。

### 1.2 同一症状重复失败时，主动升级而不是继续试（P0，机制层）

**证据**：`019f2a3d` 流式 example 闪退同一症状修 4 次（use_future→tokio::spawn→手动键盘→字符级切片，最终才定位 unicode 切片）；`019f259c` 高度问题拉锯 5+ 轮；`019f257b` emoji 状态改 4-5 轮。定量指标 iterLoop/重复密度虽低（0.03/100 消息），但人力评估显示**这类浪费是用户感知的主要"无效时间"来源**，且常导致用户自己给出方案（"要不先让我进入, 然后再流式输出?"）——这是用户从验收者退化为协作者的信号。

**建议**：agent 侧检测"同工具+同错误信号第 N 次重试"（N=3 足够，可参考 metrics 已有 trap 机制扩展 `trap.retry_same_error`），触发时强制切换策略：换工具、缩小范围、或明确询问用户。当前仅 `Max iterations exceeded (200)` 兜底，太晚。

### 1.3 用户对"慢/挂"的容忍度低于对"错"（P0，TUI/机制层）

**证据**：C 组三个马拉松排查会话（10.5~18.5 小时）中，用户全部抱怨针对等待与挂起（"你的 test 特别慢应该是有问题了"、"卡死了"），无一针对修复方向；用户行为升级为手动 kill 进程、kill workflow 接管。定量：长会话墙钟 P50=4h43m，单会话最长 22 小时。

**建议**：
- 长命令/测试执行前，agent 先做确定性处理（pkill 前置清理、`--test-threads=1` 建议、输出落盘）——`019fdb17` 中这些措施是用户情绪曲线回升的直接原因。
- TUI 提供"当前步骤 + 已耗时 + 预期性质（测试/构建/网络）"的进度标识，让等待可预期。
- 交互上：等待超阈值（如 5 分钟无新输出）时主动给"仍在工作"的心跳，而非沉默。

### 1.4 放权型会话需要"节点播报"（P1，机制层）

**证据**：用户参与模式两极：视觉任务手把手（每轮验收），分析/重构/bug 排查全程放权（`019fb6de` 22 小时仅 7 条消息、`019fdb17` 深夜陪跑但只插话收尾）。定量：超长会话 user 消息 P50=16（每 31 条消息一句）。放权型会话中用户唯一介入点是"抱怨慢/挂"或"收尾指令"——中间没有任何信息渠道。

**建议**：检测到用户长时间无输入（如 >30 分钟）时，agent 定期（小时级）输出一行进展播报（完成项/当前项/下一步），供用户回来时快速对齐。`019f9497` 的播报（[#88][#124][#254]）被验证有效，可制度化。

### 1.5 被否后"认错+回滚+重新询问"是信任重建的正确姿势（P1，Prompt 层）

**证据**：`019ea51f` 用户"不对,这个不对"（[#494]）后 agent 立即回滚（[#499]-[#505]）并重新询问方案；`019f1c4e` 误判后"你说得对"（[#434]）——这两处是信任曲线的最低点与回升点。反面：`019f259c` 汇报脱节（[#918]）后用户不再相信"完成了"。

**建议**：明确 prompt 规则：被用户否定时，先回滚/承认，再给根因解释与新方案，禁止辩解式回复。可加"争议处理"模板。

## 二、压缩与记忆（compact）

### 2.1 摘要质量标准保持 + 补"待办 checkbox 状态"（P0，机制层）

**证据**：compact 是超长会话的续命关键（19 个 compact 会话上下文 P50=318KB vs 裸奔 1,130KB，-72%），且人力评估确认摘要质量高（引用用户原话+行号+错误历史+"下一步"）、22 小时流程无缝接续、无"失忆"。

**缺口**：`019fb6de` 中用户问"还有没有没完成的事项"，agent 核查发现 Task 1-6 的 33 个 checkbox 文档滞后——**摘要不含文档状态，靠读文件恢复**。这是文档状态丢失，不是上下文丢失，但会让"是否完成"的答复延迟。

**建议**：compact 摘要模板增加一节"未完成清单状态快照"（来源：TodoWrite/issue checkbox 的最近状态），并在会话恢复时主动核对该快照。

### 2.2 摘要信息与执行规则冲突时的"选择性失明"（P1，机制层）

**证据**：`019fe475` 摘要 §2.3 白纸黑字写"Action wire：session/create→chat/create"，agent 却按"ACP 域保留"漏改，直到 e2e 验收失败才暴露（[#2632]），引发雪崩式连带修复（wire→web 层→outbox 持久化）。

**建议**：批量/机械性变更（改名、迁移）执行前，把变更契约拆成"四层清单"（wire/持久化/日志/前端）逐层验证——`019fe475` 若先列清单可省后半程雪崩。落地：批量变更类任务的 prompt 提示词，或 compact 摘要对"契约条款"加高优先级标记。

### 2.3 派发记录被压缩吞掉 34%——元数据与消息分离（P2，机制层）

**证据**：第 8 章——308 个子 agent 线程 vs 203 次可见派发，105 次（34%）派发记录被 compact 从可见消息吞掉，基于可见消息的"派发时间线"得出"后期零派发"的错误结论（时间口径修正后实际 late=26%）。

**建议**：Agent 派发是**元数据**（谁、何时、什么类型、结果），不应只存在于消息流中。若 peri 要支持"回看历史派发/统计派发"，将派发记录落为结构化元数据（或依赖子 agent 线程表）。对用户：rewind/回溯历史时，被压缩区域的派发也应可查。

## 三、Agent 派发

### 3.1 派发纪律已是优势，保持（P2，无改动）

**证据**：长会话派发类型收敛（8 种 vs 基准 25 种）、description 极短命名化（P50=16 字符）、审查型占比 13%、验证闭环（负向搜索/独立 review/三轮收敛到零阻断）。这是超长会话成功率（8 完成/13，零失败）的结构性来源之一。

### 3.2 派发前校验 agent 定义存在（P1，机制层）

**证据**：metrics 143 次 Agent tool.error 中有一类 `cannot find agent definition 'code-reviewer'`——派发时 agent 目录已无此定义（配置漂移），错误发生在运行时而非派发时。

**建议**：派发前静态校验 agent 定义存在并给出可操作错误（列出可用类型），避免运行时失败 + 用户困惑。

### 3.3 后台并发上限 3 与使用形态自洽（无需改动）

**证据**：长会话最大并行度 P50=1.5、max=3，与"Maximum 3 concurrent background tasks"上限完全吻合，撞限错误低频。当前上限合理。

## 四、结构性认识（不指向具体改动，供设计取舍参考）

1. **幸存者偏差是研究边界，也是产品事实**：能撑到 500+ 条的会话几乎全成功（0 失败）——长会话的"长寿"由任务难度+用户坚持决定，compact 只决定它能不能跑完，不决定它会不会开始。产品上：不要为"救活长会话"投入过度，要为"长会话的质量"投入。

2. **视觉/审美任务天然长**（改-看-再改无法一次命中：emoji 4-5 轮、高度 5+ 轮）——这不是 agent 缺陷，是任务结构。产品机会：**快速预览**（渲染/布局预览、diff 预览）可把每轮"改-看"的往返成本降低，直接压缩此类会话的轮数。

3. **验证闭环是超长会话的燃料**（build+test+clippy、负向搜索、独立 review）——任何削弱验证能力的改动（如为省时跳过测试）都是在拆长会话的地基。

4. **用户是顶级协作者**（贴日志、贴复现命令、给根因假设）——超长会话的质量上限由用户输入的"信噪比"决定。产品应降低用户喂证据的成本：日志一键复制、终端输出自动保留上下文。

## 六、局限

- 本指南基于单用户（konghayao）的单实例数据（3,210 主会话、42 超长），结论的外部效度待多用户数据验证。
- "建议"多数为机制推演——预期收益未实证，落地后需以 metrics/行为数据复验（如 1.2 落地后可测 iterLoop 密度是否下降）。
- 人力评估为 subagent 定性判断，引文可追溯但解读有主观成分。
- 涉及 prompt 层的建议（1.1/1.5）需与 peri-agent 的 frozen prompt 规范（见架构契约）对齐后实施，本指南不替代 spec。
