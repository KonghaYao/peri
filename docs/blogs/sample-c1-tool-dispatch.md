# Peri 工具分发系统的三层搜索机制——Core、Meta 和 Deferred 的设计逻辑

> **[Peri Code](https://github.com/konghayao/peri)** — 用 Rust 写的开源 Coding Agent，兼容 Claude Code 生态。<https://github.com/KonghaYao/peri>

Peri 的工具系统里有 30 多个工具，但 Agent 每次推理时能看到的只有一部分。不是所有工具都随时可用——有些是基础能力（读文件、搜代码），有些需要条件激活（MCP 服务器在线时才出现），有些根本不在 Agent 的工具列表里而是通过二次查找发现。如果 30 个工具全部摊在 prompt 里，每轮对话要多烧几千 token 的工具描述，其中一半几乎从不会被用到。

Peri 把工具按可见性和发现方式分成了三层——**Core 层**（始终可见的基础工具）、**Meta 层**（通过搜索工具二次查找）、**Deferred 层**（条件激活的外部工具）。这三层不是简单的优先级排序，而是三种不同的工具生命周期管理策略。

## Core 层 12 个基础工具始终直接可用

Core 层包含 Agent 交互所需的最小工具集，包括文件读写（Read、Write、Edit）、代码搜索（Grep、Glob）、命令执行（Bash）、网络访问（WebFetch、WebSearch）以及交互控制（AskUserQuestion、Agent、TodoWrite）。这 12 个工具在 Agent 启动时一次性注入 prompt 的工具描述区，整个 session 生命周期内不会增删。

Core 层的工具数量和内容经过了多轮精简。早期版本把 MCP 工具和 Cron 工具也放在 Core 里，导致工具描述区占用了大量 token。后来一个关键的设计决策是把 Core 工具定义为离线可用的基础交互能力——任何依赖外部服务、需要网络连接、或可能不可用的工具都不属于 Core。这个边界让 Core 层的稳定性极高，Agent 不需要关心 Core 工具是否可用，它们永远在线。

Core 层的工具发现不需要额外步骤。Agent 在推理时直接调用工具名，工具分发层按名称查找并执行。这也是 **prompt cache**（Anthropic 的前缀缓存机制，缓存相同前缀来跳过重复计算）能命中的关键——Core 工具描述在 prompt 的静态段中，从不变化，缓存命中率达到 99% 以上。

## 搜索工具提供按需查找能力，避免工具描述膨胀

Meta 层只有两个工具——**搜索工具**（按名称或关键词搜索可用工具）和 **执行搜索工具**（调用搜索到的工具）。Agent 在推理过程中不会直接看到 Deferred 工具，而是通过搜索工具发起搜索，拿到匹配的工具名和参数 schema 后，再用执行搜索工具调用。

Meta 层的设计解决了 Core 层的膨胀问题。如果继续往 Core 加工具，工具描述区的 token 会线性增长——每加一个工具，所有 prompt 都要多烧一份描述。Meta 层的做法是把工具移出 prompt，只在 Agent 主动搜索时才暴露。这对低频工具（如 Cron 管理、MCP 工具、LSP 工具）特别有效——Agent 大部分回合不需要它们，但需要时可以通过搜索工具精确找到。

搜索工具的搜索接口设计也经过权衡。最初的设计是返回所有工具列表让 Agent 自己选，但这带来了两个问题——工具列表太长时 Agent 的选择精度下降（类似[上下文窗口过长时的注意力衰减](https://docs.anthropic.com/en/docs/build-with-claude/context-windows)），而且列表本身又占了一大段 token。改成分页搜索后——Agent 带关键词查询，搜索工具返回最匹配的 5 个——既控制了返回内容的 token 量，又提高了选择精度。

## Deferred 层由中间件按条件动态注入

Deferred 层是三层中最特殊的一层——工具不在工具注册表中，而是由**中间件**（middleware，在 Agent 推理前后插入执行逻辑的插件机制）按条件注入。例子包括 MCP 服务器提供的工具、Cron 定时任务管理工具、LSP 代码智能工具、Workflow 编排工具。

Deferred 工具的关键特征是条件可用——不是所有 session 都能用到。MCP 工具只有在对应的 MCP 服务器连接成功后才出现，LSP 工具需要项目配置了 language server 才激活，Workflow 工具只在用户显式开启了 Workflow 功能后才注入。如果这些工具无条件写入 Core 层，Agent 会在工具描述里看到大量存疑的功能——调用了可能失败，不调用又不知道是否该用。

中间件的注入时机是 Agent 每次推理之前。每个中间件在推理前检查自己的激活条件，条件满足时把工具注入到当前轮次的工具列表中。这个设计让 Deferred 工具对 Agent 完全透明——Agent 不需要知道工具是从哪里来的，只需要知道当前有哪些可用工具。中间件自己管理工具的生命周期，包括连接建立、重连、断开后的工具撤销。

## 三层搜索的实际调度路径

Agent 发出工具调用时，分发层按固定顺序查找——先查 Core 层的直接注册表，未命中则交给 Meta 层的执行搜索工具做二次分发，最后查 Deferred 层的中间件工具表。这个顺序保证了 Core 层的最低延迟（直接查表、无额外分发开销），同时不阻塞低频工具的正常使用。

三层模型在 Peri 实际运行中的表现可以用一个数字概括——Core 层的 12 个工具覆盖了 87% 的工具调用次数，Meta 层和 Deferred 层加起来只占 13%。这验证了大多数工具调用是高频基础操作的假设，也证明了按需发现策略没有被过度使用——如果 Meta/Deferred 占比过高，说明 Core 层工具集需要重新评估。

回到开头的问题——30 多个工具，Agent 每轮只看到 12 个 Core + 当前激活的 Deferred，剩下的通过搜索工具按需发现。三层的边界不是功能分类，而是工具的生命周期属性——永远在线、按需查找、条件激活。
