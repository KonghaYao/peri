# Peri #449：插件工具链与 Dynamic MCP 实施计划

状态：实施建议，尚未实施或验证。  
基线：`main@595ea0be056465152b07f91a18cb082d29effbbc`，2026-11-18。

本文将已经确认的 V5 插件工具设计拆成可实施、可验收的工作。工具命名、别名、Dynamic 的基本语义沿用现有权威设计；下文新增的内部接口、结果字段和 PR 划分属于本次实施建议。

## 1. 交付目标与实施判断

完成这条用户路径：**选择插件 → 输入任务 → Agent 调用插件 Loader → 搜索真实工具 → 执行业务 → 返回结果**。

现有代码已经具备 canonical dispatch、会话工具快照、MCP 连接池和按服务器串行化控制。#449 的重点是将这些能力接好，补齐首次显式加载与名称兼容，不需要重写工具系统。

建议分成三个 PR：

| PR | 交付内容 | 独立验收结果 |
| --- | --- | --- |
| A：统一名称与兼容 | ToolSearch / ToolInvoke、旧名 alias、参数归一化、权限与调用绑定 | 模型只看到新代理入口；旧调用仍走同一实现 |
| B：Dynamic 完整运行链 | 配置、跳过首次连接、Loader、并发加载、目录投影、停止与清理 | 无 UI 也能通过 ToolInvoke 显式加载并使用 Dynamic MCP |
| C：用户入口与整体验收 | 插件选择、输入队列、slash 指引、精简 E2E、文档收束 | 用户选择插件并发送任务后，完整链路可用 |

B 内部可以分提交，但配置、Loader 和目录投影必须一起交付，避免发布“接受 `dynamic:true`，却没有可用加载入口”的中间状态。

## 3. 工具名称和参数：一次完成兼容

### 3.1 模型可见契约

```ts
ToolSearch({
  query: string,
  max_results?: number // 默认 5，保留既有搜索行为
})

ToolInvoke({
  name: string,
  arguments: Record<string, unknown>
})
```

ToolSearch 返回精确可调用名称、说明和完整参数 schema。业务工具保持 deferred；搜索和加载均不把它们追加为模型原生 tools。其他既有 direct 工具保持原有配置。

ToolInvoke 的两个字段均必需。无参数调用使用 `arguments: {}`。模型不能通过它传入新的服务器地址、command 或凭证。

### 3.2 兼容矩阵

| 输入 | 处理 |
| --- | --- |
| `ToolSearch({query,max_results})` | canonical 搜索 |
| `SearchExtraTools({query,max_results})` | 同一搜索工具的 alias |
| `ToolInvoke({name,arguments})` | canonical 调用 |
| `ExecuteExtraTool({tool_name,params})` | 归一化后进入同一调用实现 |
| 新旧字段同时出现，值相同 | 接受，归一化为一份值 |
| 新旧字段同时出现，值不同 | 返回参数冲突错误，不执行 |
| name 为空、arguments 缺失或不是对象 | 返回参数错误，不执行 |
| 目标是 ToolInvoke 自身或其 alias | 拒绝递归代理，避免二次解析和审查歧义 |

旧名字保留为 resolver alias，不向模型额外公布旧 schema，不维护两套执行类。不在本 issue 为 alias 设删除日期，符合已经确认的兼容决定。

兼容解析集中在一个函数内：新旧工具名均可使用这套解析器，但模型提示与 schema 只教新字段。旧字段必须先归一化，再进入新参数契约的校验，避免 alias 已解析成功却被新 schema 拒绝。旧 Rust 导出若仍被使用，可暂作兼容转发；它们也不能保留另一套逻辑。

### 3.3 权限、Hooks 与历史配对

执行链固定为：

1. 按当前会话快照识别真实的宿主代理工具。
2. 归一化外层参数，解析并绑定真实目标。
3. 以真实目标身份和实际业务参数执行既有校验、权限、Hooks、取消与结果处理。
4. 执行已经绑定的目标，不在审批后按名称重新查找。

保留 raw tool-call ID 和 raw name，保证旧历史与结果配对。policy_call 使用真实目标及规范参数。外部 MCP 工具即使取名 ToolInvoke，也不能获得宿主代理解包资格。

实施时用 `rg` 检查旧名称、字段常量、`resolve_effective_tool_name`、permission 导出、工具过滤和提示词。旧 allow/deny 配置应匹配宿主工具的 canonical 身份与 alias；不能把同名外部工具误判为宿主入口。

所有新增模型说明、schema description、指引示例使用英文。

## 4. Dynamic 配置与首次初始化

### 4.1 配置契约

```json
{
  "mcpServers": {
    "research": {
      "url": "https://mcp.example.com/mcp",
      "dynamic": true
    }
  }
}
```

URL 只是配置示例，不是 Loader 参数。

| 配置组合 | 行为 |
| --- | --- |
| dynamic 缺失或 false | 完全沿用既有初始化策略 |
| dynamic=true，启用且准入 | 登记配置并提供 Loader，不启动进程或连接 |
| dynamic=true，disabled=true | 不提供可调用 Loader，不连接 |
| dynamic=true，system_mcp=true | 配置校验失败，不能把模型启动前置依赖改为等待模型加载 |
| dynamic=null 或非布尔值 | 显式配置错误，避免模糊默认值 |

建议内部采用带默认值的 bool；必须同时修改 `McpServerConfig`、wire 类型、手写转换及构造点。插件 inline/file 配置、项目/全局配置和覆盖合并不得丢字段。

首次支持已受控配置中的普通 stdio / HTTP MCP。builtin 系统依赖继续按既有启动契约工作。现有 host register 接口保留现有语义，本 issue 不增加模型任意注册服务器的能力。

### 4.2 初始化修改顺序

1. 完成现有配置校验、来源绑定及冻结配置登记。
2. 区分 disabled、eager、dynamic；dynamic 不进入 transport 构建、进程启动、OAuth 首次连接或远端发现。
3. 连接进度的分母只统计实际需要初始化的服务器。
4. System MCP 的 settled 条件继续只由系统依赖决定。
5. 全部服务器都是 Dynamic 时，初始化仍正常结束，模型能够开始 Reason。

ToolSearch、插件列表、会话重建、子 Agent 继承和周期发现均只能读取本地登记信息，不能借“预热”触发首次连接。现有 `ensure_discovery` 的 connected-only 前提必须保留。

## 5. Loader 的定义、身份与返回值

### 5.1 Loader 是一个 deferred 宿主工具

每个获准的 Dynamic MCP 生成 `LoadMCP__<id>`。它由 MCP middleware 提供，经 ToolSearch 发现，再由 ToolInvoke 执行。

```json
{
  "name": "LoadMCP__research_a1b2c3d4",
  "arguments": {}
}
```

名称中的后缀仅为示意。实现使用“规范化配置键 + 非秘密来源身份的稳定摘要”，限制合法字符及长度，并检查大小写折叠后的冲突。来源身份包含配置作用域、插件身份和最终解析的 server key；不得只根据显示名称生成绑定。

Loader 绑定的是内部 `ConfigIdentity + config_revision + pool_scope`，模型只拿到名称。URL、headers、env、cwd 和凭证作用域由受控配置解析。凭证内容既不进入工具名，也不进入搜索文本。

参数 schema 是空对象，禁止额外字段。Loader 不能接受 URL、command、server_name、config 或 force 等参数来改变目标。

### 5.2 目录来源和 wire 身份分开

建议复用现有 BaseTool 的两个身份方法：

- `mcp_server_name()`：Loader 返回其受控配置来源，供 MCP owner 过滤、目录更新和撤销使用。
- `mcp_tool_name()`：Loader 返回 None，因为它没有远端 wire 工具名。
- `builtin_mcp_instance()`：普通 Dynamic Loader 返回 None。
- `is_direct()`：false。

同步明确 `mcp_server_name` 的文档：它表示 MCP 来源绑定，单独存在不等于远端 tools/call 目标。需要远端调用身份的入口必须同时验证 wire name；补一条“Loader 不能冒充 MCP App 业务工具”的契约测试。

这样 Loader 可以进入现有 PoolCatalog，并随同一来源消失，无需新建 Loader 注册中心。若 #443 最终已经引入更明确的 typed provenance，就直接使用该事实源，不并存两套身份模型。

### 5.3 返回结果

建议成功结果包含：

```json
{
  "status": "ready",
  "server": "research",
  "reused": false,
  "catalog_generation": 42,
  "available_tool_count": 3
}
```

generation 是宿主目录版本，供诊断与一致性检查，不是模型下一次调用的必填参数。结果不重复返回整套工具 schema。

失败保留原始原因链和既有错误语义。可以附加阶段，例如 connect、initialize、tools_list、catalog，但不能把真实失败统一改写成“加载失败，请重试”。需要 OAuth 时沿用当前授权流程和状态，不报告 ready，不无限等待。

## 6. 加载状态机与并发

### 6.1 复用现有 ServerSlot

不增加数据库表，也不持久化可重放的加载任务。使用现有 pool、ServerSlot、受管任务、operation 锁及 call gate。

逻辑状态如下；这是运行时行为模型，不要求一比一新增 ACP 状态枚举。

| 状态 | 搜索可见 | 新的显式 Loader 调用 |
| --- | --- | --- |
| 未加载 | Loader | 发起一次加载 |
| 加载中 | Loader | 加入同一 attempt |
| 已就绪 | Loader、当前准入的业务工具 | 复用连接，确认当前会话目录 |
| 加载失败 | Loader、失败状态 | 发起下一次显式 attempt |
| 已断连 | Loader、断连状态 | 按既有合法重连策略恢复 |
| 已禁用、停止或关闭 | 不提供可用能力 | 拒绝，不自行重新启用 |

如现有状态没有 unloaded/loading，可在展示投影中根据 dynamic 配置及 slot attempt 得出，不急于扩大所有协议枚举。

### 6.2 单次加载合并规则

在 ServerSlot 内最小化增加“正在进行的加载 attempt”状态，复用现有 task spawner 管理任务：

- 键必须受现有 pool scope、server identity 和配置版本约束。
- 同一 attempt 的调用者共享结果。第一个失败后，已经在等待的调用者收到同一个失败，不能排队逐个重新建连接。
- 新的显式调用才可以开始下一次失败重试。
- 已 ready 时不关闭连接、不重复 initialize。
- 不持有同步目录锁等待网络；连接操作继续使用已有异步串行化约束。
- 单个调用者取消，只取消自己的等待。全部等待者退出时取消尚未完成的首次加载，并在受管任务中收尾。
- 停止服务器、关闭 owner 或关闭 pool 时，取消 attempt，禁止迟到结果提交。

需要区分连接 epoch、加载 attempt 和 catalog generation：前两者防止旧连接提交，后者表示目录更新；不能用一个布尔值替代。

### 6.3 连接代码的复用方式

当前 `reconnect_managed` 会先关闭已有连接，不能直接当作 `ensure_loaded` 调用。

建议从 initialize / reconnect 提取已有“根据受控配置建立并验证连接”的共同逻辑。首次加载、初始化、重连共用 transport / OAuth / discovery / commit；关闭旧连接、首次显式加载和重连资格仍由各自调用场景决定。

在连接提交前再次检查：

1. pool 和 server 仍可用；
2. attempt 与配置版本仍匹配；
3. 当前结果没有被取消或被更晚操作取代；
4. connection gate、discovery evidence 与目录内容作为一组发布。

不满足条件时关闭新获得的资源，不能把旧加载结果重新挂回已经停止的服务器。

对于未激活的 Dynamic MCP，通用重连和预热不能替代 Loader。现有 UI 若有首次“启动”操作，应复用插件加载意图进入 ToolInvoke；不得另开一条首次连接路径。已经激活的服务器继续保留既有重连和显式 restart 语义。

## 7. Loader 何时可以报告成功

“连接成功”和“当前会话可以使用工具”要分别检查。

成功至少满足：

1. 对应配置的连接有效，initialize 与本次必需的 tools/list 成功。
2. 新目录已按来源发布到 pool catalog，且有新的 generation。
3. 当前会话按相同 owner、过滤与碰撞规则，可以构造后续请求要使用的目录。

Dynamic 首次加载建议执行一次 live tools/list；不要直接把另一个连接时期的持久缓存当成就绪证明。可选 resources/skills 等发现继续走现有通道，不能因不相关的可选发现无限阻塞 Loader。系统依赖的启动门禁不挪到 Dynamic 中复用。

### 7.1 当前会话目录验证的落点

当前 ToolContext 有会话身份和 canonical dispatcher，但没有“验证下一轮目录”的端口。建议增加一个很薄的只读准备端口：

- trait 放在现有协议/port 层，返回 generation 和按来源统计的已准入能力。
- 实现在 `peri-agent::SessionToolCatalog`，复用同一个候选目录构建、过滤与冲突处理函数。
- canonical dispatch 把该端口放进 ToolContext；MCP Loader 在连接提交后调用。
- 此操作只验证候选快照，不替换当前 Act 的工作目录，不改变权限。
- 使用 Weak 引用或按调用生命周期持有，防止 catalog → Loader → catalog 的 Arc 环。

该端口不维护新工具表、不保存独立 allow/deny、不触发连接。若 #443 已提供等价的候选目录准备能力，直接复用。

连接成功但当前会话目录构造失败时，Loader 返回目录阶段错误。底层连接是否保留由现有 pool 所有权决定；不能为一个会话的过滤失败关闭其他合法使用者的连接。

如果服务器本身提供零个工具，成功结果可以是零；如果服务器有工具但全部被本会话策略过滤，必须明确说明当前没有可调用工具，不能暗示业务能力可用。

## 8. 请求快照：加载后在下一轮生效

现有 Reason 路径已经执行：

`refresh → working tools → before_reason_catalog → before_model → pin`

本次沿用该顺序：

1. 第 N 轮固定目录 G；模型通过 ToolInvoke 调用 Loader。
2. Loader 完成连接并提交目录 G+1，验证下一轮目录可构造。
3. 第 N+1 轮刷新并重新绑定 ToolSearch 索引、ToolInvoke resolver。
4. 搜索和业务执行使用这一轮固定的同一份视图。

**不能承诺同一条模型消息中并列的“Loader + ToolSearch / 业务调用”立即看到新工具。** 它们仍属于原先固定的 Act 视图。提示词应要求首次加载完成后，在后续模型轮次搜索和调用；不在一次 Act 中途刷新目录来迁就这种调用顺序。

准备快照之后仍可能断连或停止。旧快照里的工具对象通过已有 call gate 拒绝失效调用，不能仅依赖“搜索中已经隐藏了工具”。目录刷新失败应显式进入已有错误通道，避免在刚报告加载成功后静默继续使用错误旧目录。

工具搜索始终只是本会话目录查询，不连接 MCP、不提升权限、不重写 frozen system prompt。

## 9. 插件选择、输入队列与 slash

### 9.1 UI 与 Host 分工

用户只需要看见已选插件标签、任务输入、加载进度或失败、最终结果。

| 时点 | TUI / 客户端 | Host / Agent |
| --- | --- | --- |
| 选择插件 | 保存插件身份并显示标签 | 只提供本地元数据，不连接 |
| 提交任务 | 文本、附件和插件选择作为同一输入提交 | 验证选择确属当前会话可用插件 |
| 准备 Reason | 不额外操作连接 | 从受控元数据生成插件指引和绑定 Loader 名称 |
| Agent 使用插件 | 展示正常工具进度 | ToolInvoke 调用 Loader，再搜索和调用 |
| 失败后继续 | 保留清晰状态，允许用户继续指示 | 新的显式调用重试，不自动重放业务操作 |

客户端只提交插件 ID；不提交“可信指引”、URL、凭证或自行拼出的 Loader 绑定。选择表达使用意图，不能修改权限。

### 9.2 必须覆盖现有输入队列

建议增加可选 `pluginSelections` 字段，默认空，并贯穿：

- `SubmitRequest::AgentText`、composer 待提交状态；
- `EnqueueUserInputRequest`、`UserInput`；
- `UserInputQueueItem`、snapshot / receipt；
- 撤回后恢复编辑器、重新入队、Host 最终 dispatch；
- 仍支持的旧 prompt 提交路径。

选择随 input_id 走，不能存成 Host 读取时的“当前全局已选插件”。两个排队任务可以选择不同插件；编辑下一个任务不能改变上一个任务的选择。

当前 EnqueueUserInputRequest 拒绝未知字段，因此客户端应在能力协商确认支持后发送新字段。未支持时提示该入口不可用，保留草稿与选择，不能静默丢弃插件标签并照常提交。

若队列或输入记录已有 JSON payload，复用其序列化扩展；本 issue 不创建新表或临时列。

### 9.3 Slash 与提示词

插件 slash 解析为同一种插件使用上下文，再由 Agent 发起 ToolInvoke。命令处理器不能直接连接 MCP。

指引由当前请求携带，保持 frozen system prompt 稳定。示例：

> The selected plugin is Research. To use its MCP capabilities, call ToolInvoke with name "LoadMCP__research_a1b2c3d4" and arguments {}. After loading succeeds, use ToolSearch in a subsequent model step to find the tools needed for the task.

直接知道有效 Loader 名称时无需先搜索 Loader。已知且有效的业务工具也无需每次重复搜索。

本次只做现有插件入口所需的选择与反馈，不以插件市场或视觉改版作为交付前提。

## 10. #443、会话作用域与资源关闭

#449 消费 #443 的控制事实，不再建立一份 owner enabled map。ToolSearch 负责目录检索，McpMiddleware 负责 Loader 与 MCP 生命周期，Agent 负责请求快照和 canonical dispatch。

同一服务器显示名称不能成为跨会话连接复用依据。只有既有 scope、配置身份、cwd/凭证上下文和会话准入均匹配，才可以复用连接。

子 Agent、fork 和 workflow 沿用各自既有的冻结配置和目录过滤：

- 继承配置不触发首次加载。
- 已经连接的能力能否复用，由既有会话准入决定；Loader 成功不产生额外授权。
- 不在本 issue 改变 Subagent 的内部实现或执行模式。

普通配置文件变化不自动热更新已有会话。已有显式停止、卸载、owner 关闭和会话关闭操作，则必须同时处理：

| 对象 | 收尾动作 |
| --- | --- |
| 当前目录及搜索索引 | 下一次投影不再提供已撤销能力 |
| 已绑定的旧工具对象 | call gate / lifecycle 检查拒绝执行 |
| 正在加载的 attempt | 取消并防止迟到提交 |
| 进程、HTTP client、OAuth、订阅 | 交由既有资源所有者统一释放 |
| skills、commands、resources 投影 | 沿用对应 registry 的撤销流程 |

关闭某个会话只释放它自己的引用和任务；共享连接由其合法 pool owner 管理。

## 11. 内存与模块边界

本次不增加新的常驻总目录、无限加载日志或持久任务表。

- 每个 server slot 最多保存一个活动 attempt、必要的完成状态和当前连接引用。
- attempt 完成后释放 waiters、通知器、临时结果及失败连接；失败诊断保持有界。
- 新目录替换旧 Arc；旧快照仅由仍在执行的请求持有，结束后释放。
- Loader 不持有完整会话历史；目录准备端口避免形成循环引用。
- pool 关闭后不留下 OAuth watcher、订阅或未登记的 tokio 任务。
- 用资源计数和 drop/cleanup 事件验证释放，不用精确 RSS 数字作为单测断言。

建议新增 `mcp/dynamic/` 小模块，按职责放置 Loader、激活协调与就绪判断；复用连接建立代码。不要将所有逻辑继续堆进当前已较大的 `initialize.rs`、`reconnect.rs`、`control.rs`。

按现有 Rust 与仓库标准执行格式、错误类型、异步锁和模块规则。文件大小上限属于仓库规则，不应称为 Google Style 的通用规定；本 issue 也不进行全仓重新格式化。

## 13. 验证计划：E2E 精简，契约覆盖风险

### 13.1 局部与契约测试

| 主题 | 必须证明的行为 | 主要落点 |
| --- | --- | --- |
| 新旧工具兼容 | 同一实现、同一审查；冲突字段不执行 | tool_search 单测、canonical_tool_invocation_contract |
| 外部同名工具 | 不能冒充代理或 Loader 身份 | invocation / MCP host policy 契约 |
| 配置兼容 | 缺省 eager；dynamic 严格解析；system 冲突拒绝 | acp-types 配置测试 |
| 零隐式连接 | 启动、选择、搜索、会话重建均不触发首次连接 | MCP lifecycle 契约 |
| 并发合并 | 多个同时调用只建立一次；失败共享而非连环重试 | 动态加载状态测试 |
| 可控取消 | 单人取消不影响其他等待者；全部取消和 stop 能收尾 | MCP lifecycle 契约 |
| 快照一致性 | Loader 更新后下一轮可用；当前 Act 保持原快照 | tool_catalog / Reason 契约 |
| 关闭与晚到提交 | stop 后旧目标不可执行，迟到连接不能复活 | call gate / control 契约 |
| 会话隔离 | 同名不同 scope 不串用；加载不扩大权限 | host policy 契约 |
| 输入完整性 | 两条队列输入各保留插件选择；撤回重新提交不丢失 | user_input / TUI 提交契约 |
| 资源释放 | 重复加载/关闭后句柄和任务无累积 | 运行时资源计数测试 |

测试按风险分组，不为每个 getter、展示文案或第五级细节功能创建独立用例。新增 _test.rs 必须实际挂载，过滤命令必须命中非零用例。

### 13.2 一个完整用户 E2E

在独立 `peri-e2e` 仓库实现一条“选择插件完成任务”的测试：

1. 使用临时配置注册一个 Dynamic HTTP MCP；本地测试服务记录连接、initialize、tools/list 和业务调用计数。
2. 打开会话、选择插件、显示标签，确认尚未连接。
3. 提交确定性任务，模型回放只使用 ToolSearch / ToolInvoke。
4. Loader 成功后，下一个 Reason 搜索到获准工具及完整 schema。
5. 调用一次测试业务工具，核对真实结果和调用计数。
6. 同会话继续使用，确认复用已有连接。
7. 关闭会话/测试 pool，核对资源收尾。

这条 E2E 证明用户闭环。连接竞态、错误重试和停止竞争放在上表的契约测试；stdio 使用一个局部启动/清理集成测试证明 transport 分支，不复制一套完整用户 E2E。

稳定性要求：

- 断言语义事件、结构化参数、业务结果与计数。
- 不依赖整屏 snapshot、工具列表顺序、完整 prompt 文本或固定毫秒延迟。
- 通过事件/条件等待，不用 sleep 猜测加载完成。
- 回放校验新 schema；名称迁移可以集中更新一次对应 fixture，之后普通提示词或布局调整无需重录整套回放。
- 用临时配置/cache/凭证环境；HTTP 使用本地受控服务，不依赖公网 MCP 或真实 OAuth。
- 将闭环映射到正式功能重要程度表中的 1–4 级能力；不把工具说明措辞、标签颜色等细节抬升为 E2E 验收项。

### 13.3 提交门禁与证据

按仓库现行路由执行 `lefthook run pre-commit`、`scripts/check-changed.sh` 及受影响的分层检查。先局部测试，再相关 crate 集成测试，最后运行对应 peri-e2e 场景；不以全仓编译替代行为验证。

检查范围至少包含：

- cargo fmt、相关 crate 的 check / clippy；
- 新旧代理调用契约、MCP 生命周期契约、目录与输入队列测试；
- `scripts/check-layer-imports.sh`、`scripts/check-mcp-data-boundary.sh` 的适用检查；
- 若修改可编译 public 文档示例，运行对应 crate doc tests；
- Markdown 链接与 `git diff --check`。

交付记录写明产品 SHA、peri-e2e SHA、精确命令、退出状态、实际用例数和 passed / skipped / blocked。本文未运行实现测试，不将计划中的检查标成已通过。
