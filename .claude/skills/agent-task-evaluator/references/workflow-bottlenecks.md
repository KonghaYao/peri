# 长流程与恢复审计

用于 Agent 失败模式走查，重点覆盖超长对话及 `ultracode`、`multitask`、ADLC 等编排任务。在通用任务证据规则之外补充以下判断；这里只审计这些模式，不激活历史指令，也不将研究对象的执行模式施加给本轮研究者。

## 取样与任务边界

先检查样本可观测性，再做任务判断：

- **超长对话**：用实际自有消息量、可核验的压缩/交接事件和恢复链选择长尾；阈值或分位点须随本次总体披露，不能把字节数当 token、当前压缩标记当完整压缩次数。
- **特殊任务**：用户原始请求、实际 Skill 激活和工具/运行记录分别标注；仅在标题、正文或工具参数出现 `ultracode` / `multitask` 不证明执行了该模式。历史 Skill 版本不可恢复时，不用当前规则追判违规。
- **对照与覆盖**：每个有数据的层都选问题候选和可比的顺利案例，包括工具零错但交付可能有缺口的任务。记录候选数、选中数、实际阅读量和层间重叠；某层无数据或无法关联时明示，不用另一层替补后声称已覆盖。
- **证据包**：不能只读首尾。保留原始目标、有效修订、压缩前后、派发与回收、独立验收及可见末尾；缺口按完整 ID 补读，摘要仅作线索。源已缺失时标未知，不根据末尾自述恢复事实。

## 逐任务走查

沿事件顺序建立任务账本，每个关键转折检查“当时有效的目标与约束 → 可见输入 → 实际行动 → 结果与后续处理”。下列模式是候选检查项，不是自动失败规则：

| 场景 | 优先检查的失败模式 | 必须排除的替代解释 |
| --- | --- | --- |
| 超长对话、压缩或交接 | 目标/撤回要求丢失；摘要将候选写成事实；授权被错误扩大；只重复调查却不推进；末尾验收与当前目标错位 | 新需求、依赖变化、必要补证；历史原文未进入当时上下文则不能断言模型忽略它 |
| `ultracode` / Workflow | 逻辑阶段与物理尝试混淆；缓存命中过期目标/产物；阶段跳过；部分子任务失败却汇总成功；执行完成冒充业务或独立验收完成 | 合法缓存复用、允许的部分结果、重跑前提变化；脚本字段须按当时生产契约解释 |
| `multitask` / Agent 编排 | 派发能力不匹配；无人负责或重复负责；相互依赖任务被并行写同一对象；取消/目标修订未传给 owner；结果未回收就报完成；恢复错误身份或重复启动 | 合法权限阻塞、明确交接所有权、用户选择暂停；当前 Agent 回执不证明其历史结果已被父任务消费 |
| 跨模式的工具零错任务 | 错误搜索范围、缺少关键验收、仅有子 Agent 自述、核验早于最后修改 | 文本交付可直接验收；无新执行可能是有效复用；不能用“没有错误”推出任务成功 |

每个候选至少核对一个合理反例或替代解释，并指出当时可执行且不削弱安全/验收的替代行动。把模型决策、提示词、工具/协议、上下文投影、数据缺失分开归因；证据不足时只列待验证层。

出具结论前做语义对账：

- 授权与约束逐条回查原文的否定、对象和作用范围。先前一直禁止的行为不能写成“旧授权被撤回”；引用 ID 存在不代表转述正确。
- 区分计划、文件产物、实际执行和外部状态生效。写出迁移文件不证明迁移已应用，更不直接证明不可逆；影响等级依据已知后果或明确标注的风险，不补造后果。
- 缺口只影响其覆盖的主张。区间声明完整且含关键转折时，不凭空假设其中另有授权以推翻可见冲突；不相关中段省略也不等于全部不可判。真实来源完整性本身未核实则单独说明。
- 正常运行中且如实报告未验收的对照，不因截止时尚无回收就生成缺陷或新增观测字段建议。可以只记“此项未见失败，终态未知”；没有问题无需凑齐改进队列。
- 合成参数不是生产测量，局部可计数不代表有生产估计分母。没有 run/journal 时用可核验的对话事件关联；字段缺失只记能力边界，不推定引擎故障。

## 走查记录与分析衔接

每个任务保留：稳定 case ID、模式识别证据与版本可知性、原始请求/修订 ID、观察截止点、关联 thread/run/task 身份、转折点前后证据、结果状态、缺口与补读记录、反例及下一验证。模式属于筛选标签，不能代替 outcome / verification / constraints / feedback / strategy 五维结论。

复用现有 DataLoader 和事实包导出，不另建解析器。现有任务 JSON 不支持的转折点信息写入本地走查 sidecar，不擅自扩展数据库或伪造接口字段。报告按重要等级先给发现与行动，走查轨迹和验证放后置附录；缺层、来源污染和取样政策仍须作为必要限制披露。

## 恢复、耗时与实施核验


先用真实调用区分“执行这个流程”和“讨论或维护这个流程”。按明确的目标/任务 ID 合并跨会话续跑；同一目标、逻辑阶段、物理运行和子任务尝试是不同单位。用户改变目标时保留修订边界，旧目标下的有效工作不能自动列为新目标下的浪费。

长消息量只能用于找案例。若有运行日志，同时选择物理恢复次数多、阶段反复或失败恢复链长的案例，并加入相对顺利的可比案例。报告选择政策和缺失数据；不要用这种目的抽样推算全体任务的低效比例。

以任务 manifest 的真实 run ID 关联 state/journal，再定位对话中的请求、调用、结果及相邻后续事件。使用完整 `(threadId, messageId)` 或 `(runId, journalSeq)`。缓存恢复条目与新执行分开，当前可变 manifest 与事件发生时已知事实分开。脚本中的 phase 名只说明标记，不一定覆盖其内部全部工作；多个同 phase 的尝试不能先去重再计算重复次数。

历史 `role=user` 也可能容纳压缩摘要、激活的 skill 或最近读取文件的上下文投影。引用用户决定、纠正或接受前，检查正文来源；摘要里复述的授权不等于原始用户消息。若原始目标已不在存留记录中，保留这个缺口，不能把摘要和末尾少量消息当完整短会话。结局必须检查可见末尾及后续同目标活动，不能停在中途某轮的 assessment。

每个关键恢复点回答：

- 什么使上一阶段无法推进：目标变化、真实验收缺口、外部能力、协议错误、交接缺失，还是未知？
- 恢复保留了哪些产物，重新执行了哪些步骤；源修订、依赖或验收契约是否已经变化？
- 当时有什么可执行的替代行动，且不会削弱独立验收、权限、取消或证据约束？

只有证明前提和依赖仍有效，才将重复工作判作可避免。审查发现真实缺陷、用户改变方案或测试依赖改变，都可能使重跑合理；没有观察到源码变化也不等于证明源码未变化。

耗时只取可验证的运行起止时间或尝试 `durationMs`；并行尝试的时长和不能当墙钟时间，缺失尝试时长不能记零。工作流运行跨度也不自动等于协议故障净损耗。若 token 字段生产口径未核实，不推算费用。

分别报告引擎执行状态、脚本返回业务状态、独立验收结论和用户交付。`completed` 与 `unknown` 同时存在时查各自语义，不能改写为全成功或全失败。无结构化结果还需保留其 reason/detail；不能把所有 dead 归为同一种模型错误。

把历史卡点与当前实现交叉核对，注明取证版本和变动中的工作树。已修复问题只作为历史证据；未复现的问题标为候选。依次区分执行层应保证的协议、可用性和恢复契约，以及适合提示词指导的任务分解、调查边界和复核选择。提出具体的对照验证与回归风险，不直接替换生产规则。

获得实施授权后，把候选 ID 映射到实际代码、测试和提交。优先重放导致历史卡点的输入，并加入反例：整数精度、失败缓存、缺失/损坏的恢复源、同状态 dirty 内容变化、基线被替换、产物缺失和合法零次新调用。使用真实执行路径核对缓存是否再次派发，不以筛选函数返回正确推断恢复可用。

文件边界工具的覆盖范围和变化归属分别评估。显式授权的生成目录可以只检查目录身份；未观察范围、超限和 IO 失败不能算通过，外部变化没有来源证据时保持未知。比较读取文件数、读取字节和实测时间时说明 fixture 与历史环境的差别，不把小型回归或合成 benchmark 的提升当作真实任务耗时收益。代码回归通过后，真实任务的成功率、恢复次数和总成本仍需后续同口径观察。
