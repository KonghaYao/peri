每一种事实，只由一个角色裁决

分开执行结果、流程结果和持久化结果。这里是已采纳的职责原则，不是已完成的状态协议。

AUTHORITY / 权威状态
EXECUTION

Core → 单次 Run

运行、停止与执行终态。子执行也使用相同契约，不由 Workflow 改写结果。

COOPERATION

SubAgent → 父子关系

受管理的子执行集合、等待、结果回传与取消传播策略，不接管子执行的终态裁决。

ORCHESTRATION

Workflow → 流程状态

节点依赖、流程策略与聚合结果。流程失败不等于所有已完成子任务失败。

PERSISTENCE

Store → Session 与版本

保存 Core 产生的合法状态变化，保证提交一致性；不裁决执行业务成功与否。

TRANSPORT

ACP → 连接与请求关联

传输请求、响应与事件。连接断开不自动等同于 Run 已停止或 Session 已删除。

HOST

TS → 主进程生命周期

创建、配置、关闭主 Agent 进程。只传 Session 引用，不代理状态提交。

子 Run A：成功子 Run B：成功子 Run C：失败→Workflow：失败

A、B 的成功结果与已发生副作用仍然存在。流程层可以决定后续策略，但不能改写 Core 已裁决的子执行事实。

验收
同时报告“副作用已发生”和“提交失败”，不能声称完整成功或自动回滚；冲突不能覆盖历史。

取消不是一个布尔值

三条事实通道，不是强制串行阶段；完成、取消与提交可能竞态发生。

取消已请求
TS / Workflow 发出意图；ACP 送达不等于 Core 已停止。
执行已停止
Core 裁决完成或中止；传播层不提前伪造终态。
结果已持久化
Store 确认提交；存储失败必须与执行结果分开表达。

完成先赢：完成早于取消生效，可以返回成功；不能规定所有取消都覆盖成功。

取消已生效：依已定义规则停止并清理，保持终态唯一。具体仲裁点与提交边界待定。

共享连接 ≠ 共享权限

连接池是通信资源，不是 authority。父子使用同一 MCP transport，也必须保有不同的能力准入范围。

主 Agent：读 + 执行子 A：只读子 B：仅检索

Core 守住调用准入。服务端需要识别调用者时，使用协议已有认证能力或独立连接，不强行追加自定义 MCP 身份字段。

Sandbox 守住执行环境边界。Builtin 不自动豁免，本地 TS 托管能力需要明确部署信任策略；静态资源读取不必一律进入 Sandbox。

查看评审后的架构取舍
  • 采纳：静态依赖反转、权威状态分离、Store 失败显式报告、连接与授权分离。
  • 约束后采纳：协作 port 先复用后新增；取消允许完成先赢；远端身份表达遵守现有协议，不预设新字段。
  • 暂缓：删除 Controller / Runtime、通用 DI、事件溯源平台、完整 Workflow / Cron 跨重启恢复。先证明现有机制无法满足契约，再增加系统复杂度。
  • 仍待裁决：Session 分叉与写入约束、Run 审计／Checkpoint 持久化范围、Cron schedule 的所有者与触发幂等、Workflow 恢复策略。活动 Run 本地化不禁止未来持久化审计。

完整阶段说明与退出规则
  • Receive：消费会话输入、接入待办与工具调用状态；正常队列耗尽的完成判断在这里。
  • Compact：根据上下文压力与策略执行压缩，更新模型可见投影并保持消息与压缩状态一致。
  • Reason：构造会话本轮模型视图，使用 Model 统一协议，消费文本、思考和 tool calls。
  • Act：通过 effective tool dispatch 执行工具与 hook，产出 tool result，随后回到 Receive。
  • 并非所有退出都经过 Receive：循环顶与等待点的 cancel、阶段错误／中断、最大迭代限制也可结束循环；不能把“正常退出判断点”写成“唯一任何退出路径”。

事件往上走，界面不接管执行

内部 v2 EventBus 的三条 lane、ACP wire 输出，以及 TUI 自己的会话路由是不同层次，不应混成一套通道。

EVENT PROJECTION

render

文本与呈现相关事件；通过内部 mpsc 传递，转发顺序需保护流式片段与 turn 边界。

state

执行状态变更；与 render 分 lane，不能把跨通道处理顺序当作天然全序。

observe

观测事件使用 broadcast；消费者需要处理 lag。观测不是一条新的业务控制路径。

EventBus → forwarder / EventPublisher → Controller.publish_event（Runtime stamp）→ subscription / event pump → ACP mapper + sink + caps → transport → client

协议化输出

标准 session/update 承载文本、思考、工具、plan 等；peri/agent_event 等私有扩展按协商能力投递。ExecutorEvent 仍是协议化适配载体，不能据此认定存在两套执行真相。

TUI 的状态投影

pump → acp_notifier → BridgeState → atoms → components。会话切换路由与渲染缓存归前端；TUI 不直接调用 Agent loop 来推进执行。

安全摘要与旁路

Hub / Web 使用 allowlist 的 peri.agentActivity，不能复制含正文的 TUI 私有载荷。Langfuse 的 bridge / tracer 在 Controller，随宿主接线但不改变 RCRA 决策。

此图聚合主要事件路径；部分队列快照与运行开始通知由会话订阅／宿主可靠投递，不应硬塞成模型事件。具体出口以当前 event_pump.rs 为准。

一次前台 prompt 的七个观察点

选择步骤聚焦职责；事件和持久化可以与执行并行。下面不是“先全部执行、再全部回传”的串行网络时序。

REQUEST WALKTHROUGH
  1. 客户端提交输入

    TUI 或外部 ACP client 发出 prompt。当前工作树还提供独立待发送 Mailbox 接口；输入尚未投递时不等于历史消息。

  2. ACP 准备会话与本轮上下文

    分发、定位 SessionManager、复用 frozen、组织权限和能力；随后建立本轮 SessionContext 与 TurnInput。

  3. Controller 登记，Runtime 查句柄

    宿主创建 PromptHandle，register_session 后 run_session；Runtime 登记表定位句柄，调用 run()。

  4. Agent 驱动 RCRA

    PromptHandle 调入 Agent 的 run_session_loop；Receive、Compact、Reason、Act 消费消息并推进执行。

  5. 模型与工具承担具体工作

    Reason 使用 Model adapter；Act 调用 session-local 工具。能力可能来自本地 middleware，也可能由 MCP 远端提供。

  6. 流式事件进入客户端投影

    事件发布、stamp、订阅和 ACP 映射持续发生；TUI 只更新 BridgeState、atoms 与视图，不拥有循环终态。

  7. 结算执行并维护持久状态

    循环结果、事件 drain 和宿主后处理共同收尾；Transcript、frozen、compact 等各有持久化边界，不把 UI 已显示等同于存储事务已提交。

沿用基础结构，明确 4.0 调整点

不是整体替换现有架构。保留执行、控制登记、事件和数据访问的基础语义，收敛能力归属；右列为目标，不倒推为左列已经实现。

宿主与通信 TUI / print 同进程 MPSC；外部 ACP client 使用 stdio，共用 host。 TS 为宿主与编排层，经独立 ACP 管道控制 Peri 进程。
进程粒度 host 持有多个 Session；SubAgent 可在同进程中执行。 一个 Peri 进程对应一个主 Agent，包含进程内 SubAgent；TS 管理主进程，不为每个子执行启动 OS 进程。
Session / Store ACP 热态与 Agent 执行态通过端口共享，ThreadStore 实现落入 SQLite。 Session 是独立状态；TS 只传引用，Peri 经 Resources 数据访问接口直连统一远程 Store；本地实现仍可用于开发。
能力来源 内置 middleware、Skills、工具与外部 MCP 并存。 Cron、文件、Shell 迁入官方 Builtin MCP；Skills 与领域扩展走 MCP。Middleware 仅保留 Core 必要策略，不整体消失。
标准协作 已存在 SubAgent 与 Workflow 能力，子执行复用 Agent 循环。 先保证 Core；SubAgent 是官方进程内协作层；Workflow 基于 SubAgent 构建，不移交 TS 重新实现，也不另造 RCRA。
宿主 MCP 通道 受限 stdio MCP Apps relay；不是通用 MCP over ACP 实现声明。 反向宿主 MCP 能力直接复用 MCP over ACP，不再设计桥接协议。
执行环境 本地工具、运行时与外部 MCP 等多条路径。 MCP Server 后方用 Sandbox 表达执行环境；具体隔离与生命周期待决。

两份稿件都不改变代码契约。4.0 未决项仍包括 Store 引用与提交协议、配置兼容、Skill 映射与 Sandbox 细节。已结束的 TS POC 包已经移除，不再作为可运行交付引用。
