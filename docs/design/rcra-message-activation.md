# RCRA 消息、任务归属与激活权威

> 状态：已批准目标设计，**待重构**（作为代码重构基线）。所有 Agent（含主 Agent、Subagent、Workflow 内 Agent）都是一等公民，适用同一会话、消息和激活契约；本文件不声明这些目标已经实现。
>
> Scope：会话级 Task/MQ 隔离、可靠消息接纳、消息分级、RCRA 消费和执行激活。实施与验收见 [active issue](../../spec/issues/2026-10-05-rcra-message-activation.md)。任务执行与关闭细则见 [Session 异步任务](session-async-tasks.md)。

## 1. 权威范围与替代关系

本文件是消息投递和激活的目标权威。它替代旧规则中的 root 默认投递、仅以 Transcript 存在证明处理完成、以任务类型特判重新启动 loop，以及子会话依附父 runtime 才能接收结果的假设。

消息行为统一收敛到 MQ（§4）：类型由可信生产者在发布时确定，loop 在 Receive 领取时按类型决定行为；生产者不得另设唤醒路径，唤醒信号只是加速通知。

[消息与 Transcript](message-transcript.md) 继续描述现行内容模型与投影实现；其中易失 MQ、Prompt/Defer/Info 是现状，不构成目标可靠性契约。[System Reminder](system-reminder.md) 继续负责内容分类和受众，不拥有执行调度权。[用户待发送队列](user-input-queue.md) 继续负责输入发布前的选择、取回和排序。

权威设计与现状不一致意味着实施缺口，不允许把现有测试的旧期望反写成目标。本文不引入消息代理产品、独立服务数量或 Store 执行租约；物理实现由接口契约和部署验证决定。

## 2. 一等公民会话与所有权

### 2.1 每个 Agent 会话的独立领域

每个 Agent 会话具有稳定的 `session_id`，独立拥有：

- Task 目录：本会话直接发起的任务及其操作入口。
- Durable Inbox：明确发给本会话的投递记录和处理义务。
- Transcript：本会话 canonical 内容；继承上下文只作为冻结输入。
- 激活策略与执行检查点：自然完成、暂停、关闭和恢复分别表达。

这些领域跨 turn 和计算实例存在；内存 TaskManager、MessageQueue、callback 和等待信号只是运行时投影或能力。子会话恢复不以父会话仍在内存或运行中为条件。身份不等于权限，独立性也不绕过工具授权与部署准入。

共享数据库、MCP 连接和执行环境不改变逻辑所有权。共享工具实例不得捕获父会话 Inbox 作为通用回调；每次调用必须从可信执行上下文取得当前会话绑定。不能用进程 ID、临时 Agent 实例 ID、父链或 cwd 代替稳定会话地址。

### 2.2 委托关系不是内部所有权

```text
P 的 Task 目录：委托任务 D，执行者为子会话 C
C 的 Task 目录：工具任务 B，执行者为 MCP owner M

B 完成 → C.Inbox：ToolTaskCompleted(B)
C 的委托 D 完成 → P.Inbox：DelegationCompleted(D)
```

P 不拥有 C 的 Inbox，也不把 B 登记为自己的直接任务。P 可以获得带来源身份的授权聚合视图，但该视图不驱动 P 消费 B 的业务结果。父子关系只定义委托、观察和显式生命周期策略，不是通用消息路由。

一次委托与子会话一生不是同一身份。C 可在完成 D 后继续处理迟到结果或接受新委托；D 的终态不能被重写或重复发布。迟到处理若需报告给 P，必须依据显式后续订阅/委托契约生成独立事件，不能再次伪造 D 完成。并发委托必须经同一会话执行准入，不能创建两个 loop。

委托必须持久记录 `delegation_id`、调用方、子会话、执行关联和状态。`cancel(D)` 只影响 D 关联的执行与任务；已终态 D 的重复或迟到取消不影响 C 的其他委托或当前 attempt。若执行合并多个委托，必须能按关联隔离取消；无法安全隔离时返回明确冲突，不能扩大为会话取消。父会话 Close 对 Independent 委托须显式选择等待或持久 detach/abandon；脱离解除父会话等待与自动接收义务，但不取消子执行。迟到结果由原 owner/委托结算记录保留，关闭收件人返回明确处置；不得重新打开父会话，也不得把原委托误报为正常完成。

### 2.3 scope 的限定用途

任务的直接归属固定为发起会话。MCP scope 必须能隔离和发现该发起会话的任务；可另有执行树/授权域用于批量观察、恢复扫描或显式级联关闭，但它不是 Task 目录 owner、消息收件人或执行唯一性凭证。

root 不可达不阻止子会话对账。树级扫描只是发现优化；发现结果按持久归属分发到各会话，不能写进 root 的直接任务目录。取消后代必须验证显式授权和 Cascade/Independent 策略；父子关系本身不授予跨会话控制权。

## 3. 消息身份、路由与安全

### 3.1 必备逻辑记录

字段名为领域契约，不预设 Rust 类型或表结构。

| 记录 | 必备语义 |
| --- | --- |
| InvocationBinding | `invocation_id`、直接发起 `session_id`、可信 owner 身份、发现 scope、响应地址、委托关联（若有） |
| TaskBinding | 发起会话 + owner 身份 + owner task ID；原始调用身份与可靠结果取回方式 |
| Event | 稳定 `event_id`、生产者、事件类型、因果/关联身份、不可变正文或稳定内容引用 |
| Delivery | `delivery_id`、`event_id`、唯一 `recipient_session_id`、消息类型与激活语义（§4.1）、会话接纳序号、投影与处理状态 |
| ProcessingBatch | 精确 delivery 集合、投影版本、执行关联、检查点及未决副作用 |

一个事件可经授权产生多个独立投递，每个收件人独立确认；不能以一份全局 ACK 代表全部收件人。任务终态事件身份由稳定任务身份与 terminal transition ID 派生，不因重连、状态描述 revision 或重试改变。同一 ID 不同内容必须报冲突，不能覆盖。

### 3.2 绑定必须先于异步执行

可靠任务发起先保存调用意图和发起者绑定，再向 owner 发起调用。调用携带可信 scope/调用关联，响应丢失后仍能发现并关联任务。无此能力的 owner 必须明确 best-effort 限制，不得承诺可靠异步恢复。

业务任务是否已创建与响应是否返回分开记录。超时不得直接重发非幂等创建；优先按调用身份对账，无法判定则保留 `OutcomeUnknown` 并要求显式处理。

发现先到、响应后到、重复订阅和恢复必须收敛到同一个绑定。已知发起者不得降级为未知；不同已知发起者冲突须隔离并告警，不能 last-write-wins。未知归属是 `Unroutable`，不是 root。

### 3.3 无隐式 fallback

收件人停止运行或未加载时仍向其可靠 Inbox 接纳。路由或身份无法恢复时保留原结果/引用及失败证据，重试对账；可向授权观察者发送独立交付异常通知，但该通知不构成原投递成功。

跨会话发送须校验 producer 能力和收件人权限。正文、模型工具参数和服务端自报名称不能指定可信身份；外部 payload 即使包装为可信系统事件，也不升级其内容为系统指令。可见性、执行权限和调度权限分别校验。

## 4. 消息类型与 MQ 消费语义

每个会话（主、子、嵌套、Workflow 内）拥有同构的消息队列：它既是消息通道，也是“是否存在必须消费的消息”这一会话可运行状态的 owner。生产者只发布带类型的消息，不挑选唤醒路径；RCRA 的 Receive 在领取时按类型决定行为；唤醒信号只是加速通知。类型由可信生产者在发布/接纳时确定，消费时不得从正文推断。

### 4.1 类型属性

类型、严重程度、受众、激活与可靠性分别表达。`severity=Info` 的成功结果可以要求处理，`severity=Error` 的诊断也可以只展示。

| 属性 | 取值 | 作用 |
| --- | --- | --- |
| 投影/受众 | 模型、UI、诊断（可多选） | 决定是否进入模型上下文或展示层 |
| 消费要求 | required / optional | required 未消费即构成会话可运行状态；optional 不单独触发执行 |
| 激活 | Passive / ContinueCurrentRun / EnsureProcessing | required 消息在空闲或挂起时的执行许可，叠加会话生命周期状态生效 |
| 合并与可靠性 | 合并键、durable / best-effort | required 必须持久至被消费；进度类只有声明可合并时才按稳定键合并 |

`ContinueCurrentRun` 必须绑定具体 run/attempt，不能让迟到 steering 误入后续不相关执行；激活取值不得由消息文字推断。适用消息在原执行结束后的处置是显式 `Suppressed`，不是已处理。

### 4.2 消费矩阵

Receive 按会话接纳序号有界领取批次，逐条按类型处理：

| 类型行为 | 领取时 | 批次之后 |
| --- | --- | --- |
| required（EnsureProcessing） | 纳入本批 | 仍有 required 则进入下一轮；无活跃执行且会话允许时创建新执行；禁止时保留阻塞义务 |
| required（ContinueCurrentRun） | 纳入绑定的当前 run/attempt | 原执行已结束则显式 Suppressed，不创建新执行 |
| optional / Passive | 投影或记录，不单独触发 Reason | 不激活 |
| 控制命令 | 由独立控制入口即时校验执行，不经模型 | 展示镜像可入 MQ |

批次结束时若无 required 且无未完成阶段责任，会话可以挂起或结束。默认映射示例：正式发布的用户请求、需要分析的异步任务终态和约定的 Cron 请求为 EnsureProcessing；截断恢复等当前执行指令为 ContinueCurrentRun；普通进度、能力变化和展示通知为 Passive；仅 UI/诊断受众的事件不因接纳而调用模型。普通消息按会话接纳序号有界批处理，不按 UUID 时间或全局时钟推断顺序；业务因果依赖必须显式记录，优先级不能破坏依赖或导致结果饥饿。UI 筛选不取消可靠投递或待处理义务。

Cancel、Pause、Close、审批决定等为 typed 控制命令，在各自控制入口校验和提交，不排队等模型理解；控制结果可以另行生成展示消息。用户待发区不是已发布 Inbox：入队草稿、发送选择、取回的准入规则保持不变，只有获得发布授权的输入才创建可靠投递，不能为统一 MQ 而把全部待发输入自动启动。

### 4.3 运行资格与唤醒

会话可运行的唯一源真相是 MQ 可运行状态：存在 required 未消费，或存在未完成执行检查点/阶段续接。主、子、嵌套与 Workflow 内 Agent 同构——各自拥有 MQ、任务目录与唤醒绑定；收件人在入站时绑定，恢复只回放事实、不重新路由。

唤醒信号（Notify、续跑通知）只是加速通知：丢失不改变正确性，等待者和调度入口依据可运行状态兜底。消息与可消费状态必须跨 loop 退出和进程重启存活到被消费；一次无锁的“退出前最后检查队列”不构成交接（§6.2）。

### 4.4 类型确定与安全

类型由可信生产者在发布/接纳时确定并校验权限；不得在消费时按正文猜测，否则被误标为 Passive 的子任务结果会永久不执行。required 不得静默降级为可合并、可丢弃或 best-effort；容量到顶时拒绝接纳并保留生产者重试责任，不丢 required；Passive 不得耗尽驱动消息所需的接纳资源（§5.4）。

类型表保持小而稳定，属于消息协议；“类型到行为”的映射集中在消费策略（Receive），生产者不得自定义调度或唤醒路径。

## 5. 可靠接纳与存储

### 5.1 接纳事务

一次成功的 `publish` 必须可靠保存消息/内容引用、收件人投递记录，以及该策略要求的处理义务。它们在同一存储事务内提交；跨存储边界采用可恢复 outbox/inbox 协议，不能先确认再靠易失 callback 补写。本设计以可靠连接为前提：链路重试按稳定事件身份去重，不产生重复逻辑投递；真实发生的重复执行按至少一次语义容忍（§8.6）。

大结果可引用 owner 产物，但 Accepted 前必须确保引用的访问权限和保留契约覆盖重试/消费期；否则先可靠转存或明确拒绝可靠接纳。不能用随后被删除的本地临时路径冒充持久消息。生产者只有在接收端承担可靠责任后才释放投递责任，执行终态与投递待确认状态分别保存。

提交后发出的 Notify、watch 或调度事件只是低延迟提示。提示失败不撤销已提交接纳，也不丢义务；调度入口必须在启动、重连及有界重试/对账时重新扫描可执行义务。重试有退避、限额及可见失败原因，不用模型 loop 轮询投递状态。

### 5.2 状态与回执

```text
可靠接纳 Accepted
  → Receive 幂等投影 Projected
  → 绑定处理批次 Pending / InProgress
  → 执行检查点提交 Satisfied
```

这是逻辑阶段而非要求一次顺序更新四张表。Passive 在 Projected 后没有模型执行义务。自动执行暂停、权限不足、owner 失联或执行环境不可用时标记 Blocked 并保留恢复条件；原 run 失效、显式放弃等使用 Suppressed/Abandoned 并记录理由，不伪造 Satisfied。

Accepted 只证明可靠接纳；Projected 只证明 canonical 内容存在；Satisfied 只证明本次处理义务已有可恢复的执行检查点，不证明整个用户任务完成。界面与 API 必须区分这些承诺。

Transcript 与 Inbox 共享稳定内容身份或不可变引用，禁止各维护一份可变正文。投影去重与义务去重相互独立：消息已经存在，不能因此清除 Pending。重复 publish 必须返回原回执，不重新创建已履行义务，也不能覆盖未履行状态。

### 5.3 Receive 与执行恢复

Receive 是普通模型输入的唯一领取入口。它按有限批量取得精确 delivery 集合，幂等追加 canonical 投影并记录批次；投影与批次记录必须原子提交或通过稳定身份安全重放。领取不能破坏性删除唯一消息事实；领取后的去留按 §4.2 消费矩阵裁决。

Reason 请求和成功响应绑定批次身份。只有响应及其后续动作意图/执行检查点可靠提交后，才能履行这批输入的义务；有工具调用时，未完成 Act 工作必须有独立可恢复责任，不能因输入 Satisfied 而丢失。模型失败、取消或响应未提交时义务仍未完成，或显式阻塞。

输入转为 Satisfied 与创建后续持久执行责任必须原子提交。未完成 Act、工具结果提交后待运行的 Reason、恢复中的阶段续接都是可调度工作，不依赖新 Inbox 消息。每个检查点须明确无后续工作，或把责任原子移交给下一阶段；恢复先完成已有阶段责任，再按准入规则合并新输入，不重复执行已提交步骤。

恢复先检查批次、响应、工具调用及其结果的检查点，不得从头重放有副作用的任务。工具已执行但结果提交不确定时进入 OutcomeUnknown，查询 owner/幂等键或要求人工确认；不得宣称 exactly-once。目标保证至少一次交付、幂等接纳/投影以及可恢复责任，不保证任意外部副作用恰好一次。

Compact 不能让未履行的输入失去可处理内容：Pending/InProgress 内容或满足其语义的明确投影必须保留，处理批次记录所用投影版本；不能因 excluded 标记就认定已处理。fork 只复制上下文，不复制 Inbox、TaskBinding、处理 ACK 或自动执行权限。rewind 不自动重跑历史副作用；涉及未履行义务时必须显式保留、阻塞或放弃并记录。

### 5.4 容量与保留

可靠 Inbox 满载时返回可重试拒绝，生产者保留责任；不得丢弃终态消息或驱动义务。进度事件只有声明可合并时才可按稳定键合并。TTL 到期必须产生可见 Expired/Abandoned 处置，不静默删未决消息。

Passive 不得耗尽处理驱动消息所需的全部接纳资源。容量准入必须采用独立配额/保留容量或等价进展机制，使仅 Passive 的闲置会话仍能接纳驱动排空的消息；不能靠自动丢消息或违反 Passive 语义调用模型解除死锁。全局存储耗尽必须明确拒绝并报告资源阻塞，恢复资源后可重试；不保证在无限输入或永久资源故障下持续接纳。

正文清理必须晚于所需投影/处理和保留期。去重依据须覆盖生产者重试、断线重放、owner 全量发现和备份恢复的所有重现窗口，不仅是最后一次 ACK。清理去重记录必须有不可再重放的事件退休水位或等价持久拒绝证据；owner 仍可能返回旧终态时必须保留相应去重依据。恢复旧备份后须先对齐退休/处理水位，无法证明不重放时阻塞相关自动执行。无限重现窗口不能配有限去重窗口而仍声称不会重复处理。删除会话后保留适用的关闭/tombstone 证据，迟到投递返回明确关闭结果，不创建同 ID 新会话。

## 6. 激活与生命周期

### 6.1 单一领域判定，SDK 唯一执行者

会话领域统一判断：MQ 可运行状态（存在 required 未消费或未完成阶段责任，§4.3）+ 类型激活语义 + 会话生命周期许可。持久阶段责任继承明确的运行与暂停策略，不因原输入已经 Satisfied 就失去调度资格。所有生产者只发布消息，不直接启动 loop，不按 Shell/Subagent/Workflow 类型设置 continuation 开关。

SDK 负责唯一执行者、部署实例和恢复调度；Peri 提供可枚举的工作义务、会话准入结果及 RCRA 执行入口。ACP 只适配协议，不拥有第二套业务激活规则。内存通知和持久扫描走同一准入路径；没有可用 SDK/宿主调度者时保持可观测 pending，不声称已启动。不得为此新增 Agent/Store 执行 owner lease 或 fencing。

### 6.2 运行与退出交接

- 正在 Reason/Act：普通消息不抢占；下一个 Receive 接收。控制命令按取消/审批契约执行。
- 空闲/挂起：MQ 具备运行资格时通知本会话等待者回 Receive；等待信号与内存队列同 owner，通知丢失由运行资格兜底。
- 无活跃执行：EnsureProcessing 经统一准入创建执行；不得依赖旧 callback 持有 runtime。
- 正在退出：以工作 revision 或等价原子交接协议裁决，消息要么属于当前执行的后续批次，要么保留给下一次激活。一次无锁的“最后检查队列”不构成交接。
- 重启：恢复生命周期和未决批次，再对账任务与可执行义务；不能只加载 Transcript 后认为无事可做。

同会话多个消息合并激活，但批次只履行实际包含的 delivery；执行期间新到消息不能被批量 ACK 吞掉。调度重复不会形成并发 loop，执行失败不会丢失义务。运行资格唯一来源为 §4.3，各生产者不得维护自己的唤醒路径。

### 6.3 自然结束、Stop 与 Close

自然结束仅结束当前执行，不删除会话 Inbox。EnsureProcessing 可以再次激活主/子会话；ContinueCurrentRun 不可跨 run。委托完成后的报告关系遵守 §2.2。

显式用户 Stop 携带稳定 command ID、目标 `(session_id, turn_id, attempt_id)` 和预期 lifecycle revision；同一次领域裁决原子决定目标取消及本会话自动激活暂停。重复命令返回原回执；旧 attempt 或旧 revision 的 Stop 不得暂停 Resume 后的新执行。显式会话级 Pause 是独立命令，不以过期 attempt Stop 冒充。迟到回调继续可靠接收但不得偷偷复活。

取消执行、级联范围和暂停自动激活是不同控制语义。级联 Stop 必须可靠记录经授权的目标集合及每目标动作；默认 Cascade 对目标执行取消，并按目标生命周期协议处置——子会话的停止走关闭协议（用户可直接发起，主 Agent 对自己发起的子会话在授权范围内同样发起），关闭级联终止其持有的后台执行资源（如 bg shell），资源终止并结算后才向发起者返回消息；不能仅 cancel 后被迟到结果立即复活，也不采用留下暂停子会话、任由所属后台进程继续运行的语义。暂停只作用于明确命中的会话目标并持久保存；自然 attempt 切换不使其失效，重试时重新核对并应用。新委托不会自动解除既有暂停；恢复暂停的工作必须显式 Resume。每次实际取消仍精确定位 attempt，不能取消无关执行。控制尚未完成时返回可恢复的 Pending/Incomplete，不谎称全树已停；重试按关联收敛而非因自然换 attempt 永久放弃。Independent 子会话不因父会话 Stop 自动暂停，除非控制请求明确授权并包含它。取消某个工具任务或委托也不等同于暂停整个会话。

显式 Resume 或有明确恢复语义的新用户发送可解除暂停，并按用户输入准入规则合并处理待办；重连、打开历史和收到 callback 都不是恢复授权。关闭会话则阻止新业务准入与自动激活；关闭子会话还须级联终止其持有的后台执行资源（如 bg shell），资源终止并结算后才向发起者返回消息，不允许所属后台进程在关闭后继续运行并迟到投递；关闭排空仍可接纳已有任务的结算证据，不触发模型。需要模型处理的遗留义务必须显式放弃/交接后才完成关闭，不能无限等待已被禁止的执行。

预算耗尽、错误或审批等待不伪装自然成功；义务保留为可恢复/阻塞状态，按有界策略重试或等待授权，避免消息导致无限自动重启。

## 7. 可观测性与契约验证

P0 审查与证据账本见 [active issue](../../spec/issues/2026-10-05-rcra-message-activation.md)。用户已裁决 best-effort 默认允许、重复执行可接受，且不引入控制域合并政策；实施仍须逐项满足本文件契约。

诊断链路必须可按 invocation、task、event、delivery、session、batch 和 attempt 关联，记录各阶段时间、重试次数、路由证据、阻塞/放弃原因；不记录凭证或默认暴露完整消息正文。展示成功与模型处理成功独立。

必须验证：

- 主/子/嵌套/Workflow Agent 使用同一套契约；父 runtime 消失后子会话仍可收件和恢复。
- 子会话发起工具结果只进入其 Inbox；父会话只收到对应委托事件或显式订阅事件。
- 发现与响应任意乱序、重复、重连都不改变归属；未知目标不 fallback。
- Reliable publish 在提交前后崩溃、通知丢失、ACK 丢失和重复回调下保持责任可追溯。
- Projected 之后 Reason 之前崩溃仍须处理；响应提交与工具副作用各断点不盲目重放。
- 消息在 Reason、Act、idle、退出交接、退出后和重启时到达均按 §4 消费矩阵与激活语义处理。
- Stop 与投递/调度并发时不自动复活；关闭只接纳结算，不新增执行。
- 去重、Compact、fork、rewind、容量、TTL、结果引用过期不静默丢失未决义务。
- 多消息合并激活不越界 ACK，SDK 保证同会话唯一执行者。
- 类型在发布时确定并驱动消费行为；required 不降级、不丢；Passive 不阻塞 required 接纳。

## 8. 跨边界可靠性与执行准入

### 8.1 逻辑投递与生命周期身份

逻辑投递唯一键由可信 producer namespace、event ID、收件人会话及接纳生命周期、delivery purpose 组成；delivery ID 必须映射到这个唯一键。重试、发现和恢复不得通过生成新 delivery ID 重开相同义务。purpose 来自受控协议，不得由重试方任意改变以逃避去重。

InvocationBinding、TaskBinding、Delivery 和 owner 创建请求必须绑定接纳生命周期 epoch。关闭/重开不能让旧创建、旧结果或旧控制命令成为新生命周期的工作。owner 在创建接纳点原子校验 scope epoch 与 closing gate；关闭必须对账未决创建意图，不仅查询已有 task。旧生命周期终态只可按原处置归档/结算或明确拒绝，不自动激活新生命周期。显式重新处理旧结果必须是新的授权操作，保留原事件因果身份及授权记录，不能伪装生产者重试。

会话恢复描述至少保留授权主体/域、可信 owner 路由、凭证引用和工具权限上限；恢复时重新授权。不得持久复用过期 bearer token、用 session ID 代替授权或扩大为新宿主权限。材料缺失、权限撤销或执行环境不匹配则 Blocked，不回退父会话身份。

### 8.2 持久 mutation 与副作用屏障

publish、撤回、批次领取、处理检查点、阶段责任转移及控制命令使用稳定 mutation ID。存储结果区分 NotApplied、Applied 和 Unknown，支持按 mutation ID 查询持久回执；传输错误或暂时查不到回执都不是 NotApplied。NotApplied 必须具有服务端持久拒绝/终结或等价最终性证据，保证该原命令以后也不可能提交；迟到请求须服从终结裁决。Unknown 期间仅按同一 mutation 身份查询或幂等重试，不创建替代模型响应。Unknown 时冻结相关热态、批次推进和调度，先回读/恢复，禁止重新 Reason、重新 dispatch 或自行反向补偿。相同命令重试必须复用身份和参数；冲突返回错误。

这些原子操作由 SessionResources 或等价领域行为端口提供；调用方不得拼多次写入冒充事务。跨后端必须遵守同一故障契约，后端缺少能力时拒绝准入，不用易失状态降级可靠承诺。

任何有副作用的工具 dispatch 前，必须可靠提交所属模型响应、稳定 tool invocation ID、参数完整性证据、工作关联及授权关联。并行 Act 的每个调用均受屏障约束；未提交或提交 Unknown 的响应绝不能执行。恢复查询旧调用身份，不以重新 Reason 获得新 ID 的方式重试已可能发生的副作用。

### 8.3 SDK 交接与单会话执行

SDK 的实例持有唯一性和会话内可推进 attempt 唯一性是两项保证。用户发送、Inbox 扫描、恢复阶段和定时触发必须通过同一个原子会话准入；已运行时合并/排队，不额外启动 loop。唯一实例内部也必须覆盖并发入口，不能以实例 claim 代替 attempt 准入。

激活请求携带生命周期、控制代际和工作关联；排队时取得的允许决定不是可永久使用的执行授权。实际执行入口重新校验，并登记可恢复的准入交接，保证 Pause 能识别已排队、交接中和运行中的工作。普通模型批次领取、阶段续接和副作用 dispatch 都须检查相应控制资格，不能只在 scheduler 检查一次。

控制意图接纳与实际静止分开确认。已接纳 Pause/Stop 撤销未生效激活，已派发动作按取消/对账收敛；无法证明静止时返回 Pending/Incomplete。与控制并发且已越过 dispatch 接纳点的远端调用可能继续执行，不能声称持久 Pause 瞬间撤销外部副作用。调用进入 dispatch 与控制意图提交须有明确领域排序点；未知状态保留责任，不绕过 SDK 执行唯一性，也不引入 Peri 执行租约。

Pause、Resume、Close、Reopen 及带恢复语义的用户发送均采用稳定 command ID、预期生命周期/控制代际和持久回执；重放只返回原结果，不重新改变状态。旧 Resume 不得解除较新的 Stop；Close/Reopen 不接受前一生命周期命令。重置预算同样需要显式授权和幂等命令。

重试、模型恢复和自动激活预算绑定稳定工作义务/执行关联并持久累计；attempt 换代、重启或通知重放不能重置。预算耗尽转为可观测 Blocked，不能通过新 attempt 获得无限续跑预算。

### 8.4 循环数据分离与投递资格

循环间数据隔离（Task/Inbox/Transcript/唤醒目标）是本权威的核心要求；循环内消息按 §4 的 MQ 消费语义正常流转。用户裁决（2026-10-05）：主 Agent resume 子 Agent 属正常 MQ 流程，不引入"控制域合并"政策；投递准确性以发起会话归属为准，恢复不得改道 root（见 §8.1）。未授权内容不得因共享 Transcript 成为当前可行动输入；该原则用于保证分级准确，不额外定义委托级控制域。

### 8.5 用户输入撤回与重发

稳定 input ID 表示用户输入身份，发布代际表示一次发布意图；二者不能与永久唯一的 delivery ID 混为一体。撤回与 Receive 领取须通过持久原子裁决：成功撤回将该发布代际及处理义务置为不可执行，之后才能返回待发区；已领取则拒绝撤回，按取消契约处理。只从内存 MQ 移除不构成撤回。

重新发送创建新的授权发布代际，用户输入 event ID 由 `(input_id, publication_generation)` 唯一确定并参与逻辑投递键；不能直接以跨代际不变的 input ID 作为 event ID。重复发送命令复用原代际及 event ID；旧代际重试返回已撤回回执，不能复活旧义务。领取时持久记录 input/发布关联并据此生成 canonical 投影，避免先写 Transcript 再丢失撤回依据。Stop 的未领取回收同样遵守该裁决，回执 Unknown 时不能让界面同时当作已撤回和可重新发送。

### 8.6 故障域、owner 能力与版本准入

Accepted 的持久保证必须声明部署故障域和 RPO。本文要求在声明覆盖的进程崩溃/重启域内不丢已接纳责任；不自动承诺任意磁盘丢失或接纳前备份回退后的 RPO=0。若部署要求覆盖备份回退，接纳依赖不可随该恢复回退的日志/副本，或 owner 保留至双方确认的恢复安全水位。超出声明故障域的数据丢失必须报告 Disaster/DataLoss；仅阻塞执行不能冒充仍有可恢复消息。去重退休规则与此独立，防止丢数据和防止重复副作用都需证明。

owner 能力按实际支持的调用关联/幂等、发现、结果保留、取消及关闭 barrier 声明。用户裁决（2026-10-05）：best-effort 后台默认允许，重复执行可接受（至少一次语义）；但这不改变诚实报告要求——未知创建结果为 OutcomeUnknown，无法证明排空返回 Incomplete，不得把"可能已执行"报告为完成或已取消。停止本地执行、放弃追踪和证明外部资源已停止仍是三种不同结果；显式放弃不伪造 clean close。

持久格式和执行协议必须版本化。升级不能从旧 Transcript 有无消息猜测 Pending/Satisfied：缺少处理证据的旧记录隔离为 LegacyUnknown，等待可核对恢复证据或显式裁决，禁止自动重跑。切换前 SDK 停止旧写/执行路径，排空或显式接管 pending；新义务存在时旧版本不得执行该会话。回滚先完成责任迁移及格式准入验证，不能仅回退二进制。迁移期间只有一个消息/处理权威，不新增双写兼容层。
