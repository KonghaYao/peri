# 验收与主张核对

当准备给出有据交付、发现评审分歧或提炼提示词候选时使用。五维标签是索引，不能代替逐项验收。

对每个焦点任务列出：验收条件、直接证据 ID、证据实际证明的范围、尚缺内容。再核对产物中的关键事实主张：支持、反证、只有自述，或无法判断。可作为评审理由或独立裁决附件，不必新增生产事件字段。

- 区分阶段：发送工具请求、工具返回成功、产物可检查、符合用户验收是不同状态。提交请求和“准备提交”不等于提交成功；子 agent 被派发不等于其结论已经接收、核查或整合。
- 区分环境：本机测试、目标平台检查和生产症状复现各自说明环境与范围。直接验证可以存在，但仍不足以支持整个任务 delivered。
- 区分解释与改动：修复方案合理不证明报告中的所有根因或平台说法正确。需要时做安全的小反例实验；它只证明实测环境，不冒充历史初始状态重放。
- 保留用户 steering：同目标新增的提交、对抗检查和交付约束纳入验收；不能因为已完成其中一段，就把未完成要求划成新任务。用户把后来异常归因于上次修复，是反馈证据；技术因果仍需独立核查。
- 核对证据生产者：`role=tool` 只说明消息容器，Agent 工具返回的“测试已通过”仍可能是子 agent 自述。测试主张应定位实际命令结果；解释或文本转换的正文则可以直接作为产物验证。
- 核对多层裁剪：包的截断标记不能覆盖工具自身的文字裁剪。长结果中的通过计数、退出码、完整输出引用分别核对；缺失终态保留未知，不从正常工具返回或结果开头的若干 passed 推出全量通过。
- 检查引用含义：文件列表、diff 统计、成功退出与子 agent 自述不能独自证明正文满足所有要求。引用 ID 存在但不支持主张，属于语义错误，机械校验不会发现。

有部分直接成果但已知验收条件尚未覆盖时保留 partial；缺失材料导致无法判断则 unknown。若任务目标本身是调查和记录未知，允许研究交付完成且底层问题仍未解决。明确说明完成的究竟是什么，不把问题状态和研究任务状态混成一项。

修订方法后先冻结新方法 hash，在新的评审记录中重评受影响案例或新的合成场景；标明是同 reviewer 复查还是新 reviewer 盲评，旧标签和旧方法继续保留。不要用新解释偷偷改写已发布分布。
