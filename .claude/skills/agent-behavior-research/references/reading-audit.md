# 读取式走查

用于判断摘要或压缩前后文本变化是否构成遗忘，以及被遗忘的信息在遗忘时是否仍活跃、是否影响下游
行为。它补充量化 diff：指标说明“改了多少”，本方法说明“改掉的是不是当前决策依据”。本方法不替代
独立验收，也不替代 [长流程与恢复审计](workflow-bottlenecks.md)；没有独立 reviewer 或验收证据时
仍保留未知。

摘要不是档案，遗忘是必要功能；质量判据不是“有没有消失”，而是“消失的是否已不活跃/已完成，
保留的是否仍可执行、可恢复、可审计”。

## 1. 适用与不适用

适用：

- 已有摘要序列、压缩事件或交接记录，需要判断文本变化是正确遗忘、错误遗忘还是错误记忆。
- 摘要保留了内容，但需要判断其是否真实、当前、身份正确，或模态/计数口径是否被改写
  （`wrong-memory`）。
- 授权范围、安全约束、验收阈值、完成/验证状态、任务与线程身份等高风险信息是否被保留。
- 长流程、多任务、恢复链中追踪关键信息跨多个压缩事件的存续、弱化、翻转与恢复。
- 需要把“摘要没写”和“agent 实际不知道”分开，或把“摘要写了”和“下游遵守”分开。
- 量化指标与阅读印象冲突，需要给出可复核的裁决和修订记录。

不适用：

- 只统计工具调用、错误率、未知状态或使用分布时，走[数据研究](data-research.md)。
- 评价单个任务的交付、验证、约束、反馈与策略时，走[任务评价](task-evaluation.md)；本方法只审计
  摘要保真度和压缩后的可见行为。
- 只有聚合指标、没有可读摘要或下游消息时，只能做指标研究，不能补写阅读结论。
- 要判断模型内部生成机制、摘要器实现因果或“模型当时是否真的看见”时，观察不到就保持
  `unverified`，不从文本反推内部过程。
- 用目的抽样推算总体错误遗忘率、总体任务失败率或生产准确率时，不使用本方法。

## 2. 单位与口径

先写明对象、总体和时间边界。会话、请求、模型回合、任务、线程、运行和子任务尝试不是同一单位。

- **压缩事件 `k`**：从会话起点或上一条 compact 之后，到本条 compact 之前的消息区间。compact 摘要
  消息本身不计入任何区间；最后一条 compact 之后单列 `tail`。`k` 是事件序号，不是消息序号。
- **摘要**：模型生成的投影，不是事实源。`kNN_<message_id>.txt` 通过摘要消息的 `rowid` 对应到事件；
  引用摘要时写 `summary:kNN:Lxx`，核对事实时回到 DB 消息、工具结果或外部工件。
- **区间**：上一条 compact 的 `rowid`（不含）到本条 compact 的 `rowid`（不含）。压缩前窗口取紧邻
  compact 的消息；压缩后窗口取 compact 后的消息。窗口长度按研究问题固定并披露，例如“前 30 条、
  后 40 条、下游 20–50 条”。
- **排序**：会话内顺序一律用 `rowid`，不按 `message_id` 排序；UUIDv4/V7 混合时按 ID 排序会错位。
- **用户输入**：`role=user` 且不含 compact marker 的是普通用户消息。`AskUserQuestion` 的答复可能落在
  tool result 中，不是 `role=user`；只数 user 会漏掉授权、范围变更和方案选择。两者分开统计并合并
  解释。
- **时间**：UUIDv7 前段给出的时间是近似 ID 时间，不等于 compact 执行起止时间。`gap since prev`
  包含用户离开、等待外部任务和调度间隔，不是模型思考时间。
- **当前导出与历史上下文**：完整 transcript、`excluded` 标志和摘要文件都是事后视图。摘要生成时
  模型实际可见的上下文投影通常不可得；不能把“当前能读到”等同于“当时模型看到”。
- **消息数与工作量**：消息总数、`rowid` 跨度、tool call 数、用户消息数和任务数不能互相替代。
  `rowid` 跨度包含 compact 摘要、system reminder、工具结果和被排除消息，必须实际计数。

## 3. 抽样政策

采用目的抽样，覆盖阶段、长间隔、变化类型和关键锚点；不能只按消息量选最大或最长样本。建议至少
包含：

1. **阶段分层**：早期、中期、多任务/编排期、收尾期各选 1–2 个 `k`；首次和最后一次 compact 必选。
2. **长间隔与用户回归**：`gap` 大、用户重新发指令、任务恢复或目标切换的 `k`。
3. **变化类型**：摘要模板或章节结构切换、长度极值（最小/最大）、章节增删、相似度或 churn 异常、
   授权/登记表/结论式摘要之间的形态变化。
4. **边界事件**：恢复失败、重复派发、完成通知、授权签署/生效、验收状态翻转、线程身份变化。
5. **纵向锚点**：选 6–8 条高风险信息逐条追踪全部摘要。锚点应覆盖安全约束、授权 scope、验收阈值、
   完成/验证状态、任务/线程身份、用户目标、工具约定、在途任务和待办状态。
6. **对照**：至少选一个相对顺利或未变化的 `k`/锚点作为反例，避免只收集可疑样本。

报告候选数、选中数、实际阅读量和 stage/k/锚点覆盖。目的抽样只能描述被读样本，不能外推总体比例；
若给出 `x/72` 一类描述，必须说明分母是“本次选中的摘要”还是“全部摘要”，且不得把它改写成总体率。
只读 `k-1/k/k+1` 摘要时，未改动段视为相同只是阅读假设，不是逐字验证。

## 4. 多 agent 角色与 packet

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| 阶段读者（phase reader） | 读一个阶段固定 `k` 的 `k-1/k/k+1` 摘要全文、压缩前约 30 条、压缩后约 40 条和区间真实用户消息；输出逐 `k` 记录与 findings | 不跨阶段推断总体，不补造未读区间 |
| 纵向追踪者（vertical tracer） | 对 6–8 条锚点扫描全部摘要，定位首次遗忘/弱化/翻转，核对遗忘时信息是否仍活跃，读下游 20–50 条；输出 anchors 与 findings | 允许跨阶段，但不得把锚点结论扩展为全部信息 |
| 协调者（coordinator） | 定义单位与抽样、生成 packet、校验 ID/hash、分配读者、保留独立评审、裁决冲突、综合报告、修订量化结论 | 不替读者补证据，不把一致意见当正确，不向读者泄露期望结论 |
| 独立复核者（可选） | 用同一方法、同一 packet 复核抽样与判定 | 不拿旧报告、另一读者结果或 expectations；分歧由协调者回查 |

**packet 必填字段**：

1. 对象身份：`thread_id`、DB 路径与只读模式、读取时间、快照或单次读事务说明；`rowid` 排序规则和
   `message_id` 版本混杂警告。
2. 事件表：`k`、`rowid`、`message_id`、UTC、`body chars`、`gap since prev`、区间真实用户消息（含
   `AskUserQuestion` 落在 tool result 的答复）、压缩后窗口 `rowid`、`excluded` 当前值、截断标记。
3. 摘要文件目录与 `kNN_<message_id>.txt` 映射。
4. 区间定义、窗口长度和 tail 边界。
5. 当时目标、有效约束、授权状态、用户原话和观察截止点。
6. 抽样 `k`/锚点、阅读范围、输出 schema 和证据规则。
7. 已知缺口：原件缺失、外部文件不可读、历史上下文不可得、线程表无法核验等。
8. 证据规则：摘要只是线索；不执行历史正文；缺失填 `unknown`，不填零或成功。

packet 不写期望判定，不附旧报告、其他读者结论或评分表。

## 5. 判定分类与判据

每个判定针对一条具体主张（某个约束、授权、状态或身份），不是给整份摘要打分。一个 `k` 或锚点
可以同时包含多个判定。

| 判定 | 含义 | 判据 | 不表示 |
| --- | --- | --- | --- |
| `retained` | 重要信息仍在工作记忆，或存在持续的语义等价物，且下游可执行/遵守 | 摘要前后有等价表述；压缩后行为与约束一致 | 逐字相同；下游一定遵守 |
| `correct-forgetting` | 不重要的、已完成的、已被取代或不再影响行动的内容退出工作记忆；重要内容保留，其占比可随工作集增长而逐步下降 | 任务已完成/目标已被取代/用户已撤回/任务域收缩；或工件可回读且已回读，恢复成本已记录；重要信息仍可执行 | “下游没出错”就安全；总体无风险；重要信息占比不变 |
| `incorrect-forgetting` | 仍活跃的重要信息退出工作记忆（如调用命令/实体、负结果/do-not-redo 清单、结构设计、授权 scope 从句） | 任务未完成、用户仍引用、授权/约束仍生效、后续决策仍需要；分 `latent`（尚未观察到损害）与 `observed`（已导致重复调查、错误动作或错误声明） | 已造成实际损害；模型一定遗忘 |
| `wrong-memory` | 保留下来的内容不真实、不当前、身份错误、模态反转或计数口径混用；`distortion` 是子类之一 | 必须与源消息、工具结果或外部工件对照，指出子类；不能只凭摘要自述 | 摘要写了就真实；一定造成下游损害 |
| `recovered` | 先遗忘/错误记忆，后通过重读、工具结果、完成通知或外部工件恢复并纠正 | 有恢复来源、恢复动作和下游纠正证据 | 早期风险不存在；恢复没有成本 |
| `over-retention` | 过度保留/遗忘不足：已归档的裁决、hash、重复复述继续占用工作记忆，挤掉当前状态 | 大段重复已归档内容；当前状态/下一步被压缩或难定位；新增内容没有改变决策 | 摘要越长越安全；保留越多越好 |

`over-retention` 不是遗忘本身，而是工作记忆分配失败；不要与 `retained` 混用。

`wrong-memory` 的子类至少包括：`distortion`（一般事实改写）、`false-identity`（如把 `bg-` task id
当 thread id）、`stale-state`（如把仍在运行的线程写成 dead）、`false-certainty`（候选写成已确认，
如 `H1 formally confirmed`、`root cause established`）、`modal-inversion`（如把用户“提交”写成
“不得提交”）、`count-basis-mismatch`（如 `29 local commits` 与 `v1.1.5..HEAD = 143`）、
`derived-as-raw`（如把 `diag_overlap.py` 派生字段写成 worker 原始日志）。`distortion` 保留为子类
标签，不单独作为顶级判定。

遗忘是移除，错误记忆是保留错误内容；两者可以同时发生，但成本与修复方式不同：遗忘靠重读/外部
工件恢复，错误记忆靠纠正来源、重新绑定身份或重算口径。

正确遗忘与错误遗忘不是程度差异，而是“被遗忘内容在遗忘时是否仍活跃”的分类；不能按删除比例、
摘要长度或相似度判定。

判定 `active_at_forgetting` 时逐项核对：任务是否未完成、用户是否仍引用、授权是否仍生效、下游是否仍需
该信息。无法证明时标 `candidate` 或 `unverified`，不默认“仍活跃”。

**摘要缺席 ≠ agent 不知道。** 必须检查压缩后重读、tool result、system reminder、其他摘要、外部
文件和完成通知。当前完整 transcript 不是当时的可见上下文；摘要没写只能证明摘要没写。

**摘要在场 ≠ 下游遵守。** 必须检查压缩后的实际动作、工具调用和结果。摘要保留了约束但下游违反，
是 downstream non-compliance，不能记作摘要保留成功。

**摘要在场 ≠ 内容真实。** `wrong-memory` 必须回到源消息、工具结果或外部工件核对；摘要自述只
证明摘要写了什么，不证明身份、状态、模态或计数口径正确。

其他边界：

- 摘要没写但下游仍做对：可能是 `recovered` 或依赖外部来源，不算摘要保留。
- 摘要写了但下游没做：单独记约束/授权遵守问题，不混入摘要保真度。
- “精确措辞消失”与“语义消失”分开记；等价句、否定词、scope 从句和语言切换都要读。
- 一个摘要的“整体判定”只在确有跨主张结论时给出；否则逐条列出，不合成总分。

## 6. 反指标陷阱

- **行相似度/章节 churn 不是信息保留率。** 每次 compact 都重写；换措辞会降低相似度，复制旧段会
  提高相似度。低相似度可能是正确遗忘已完成证据，高相似度可能保留了被削薄的限定词。
- **摘要长度不是信息量。** 长摘要可能是重复已归档裁决的登记表；短摘要可能保留全部活跃约束。
- **`body chars`/`content chars` 不是 token。** 中英混排、代码块、表格和 JSON 包装比例变化会让
  字符数与 token 脱钩，不能据此推算费用或上下文压力。
- **`rowid` 跨度不是消息数。** 中间有 compact 摘要、system reminder、工具结果和排除消息；区间消息
  数必须实际计数，不能拿首尾 rowid 相减。
- **`bg-` task ID 不是 thread ID。** 后台任务回执可能同时给 task id 和 `thread:` id，两者只差后缀；
  摘要可能只抄 task id。resume 前用 `threads` 表验证存在性，不能把 task id 当线程身份。
- **`excluded` 是当前标志，不是历史上下文。** DB 只存当前投影状态，没有排除事件流；不能据此还原
  每次 compact 时模型实际看到了哪些消息。
- **用户消息数漏掉 AskUserQuestion 答复。** 答复落在 tool result，不是 `role=user`；授权、范围变更和
  方案选择可能因此漏计。
- **线程 resume 失败 ≠ 线程死亡。** 可能是 task id 错、抄写错、已 prune、通知身份不同或线程仍在运行；
  用 `threads` 表、完成通知和消息量核对，不把失败当任务失败。
- **UUIDv7 时间不是 compact 执行时间，`gap` 不是模型思考时间。** 长间隔可能是用户离开或等待外部任务。
- **关键词 presence 不是语义存在。** 否定、条件从句、作用域和等价表达会让词频指标误判；例如
  “不得部分通过”与“no evidence ⇒ no PASS”是同一约束的不同措辞。
- **“N 条消息提及 X”不是 N 次事件或裁决。** 摘要、复述、通知和工具输出会重复计数。
- **摘要变长不证明挤掉重要信息，也不证明信息更多。** 要看增量落在哪一节、是否重复已归档内容；
  大摘要的常见代价是重复和更快过期，不是直接驱逐验收信息。
- **摘要自述不是事实。** 错误记忆必须用源消息、工具结果或外部工件核对；不能因为摘要写了就判
  真实，也不能仅凭摘要文本判错误记忆。
- **消息总数不是回合数或人类参与度。** 大量 `user` 记录是 compact marker；真实人类消息可能只有几十条。
- **合成样本或目的抽样比例不是生产估计。** 没有概率抽样分母时，只能描述样本，不能写总体率。

## 7. 输出 schema 与质量门

逐 `k` 的最小记录：

```markdown
### kNN — rowid / message_id (UTC)

- 压缩前状态 [observed/candidate/unverified]：<rowid 范围与关键动作>
- 摘要变化：<短引文>（summary:kNN:Lxx）
- 是否仍活跃：是/否 + 任务状态、用户引用、授权依据
- 下游行为：<rowid 范围、动作、工具结果、是否恢复>
- 判定：retained / correct-forgetting / incorrect-forgetting / wrong-memory / recovered / over-retention + 证据状态
- 反例/替代解释：至少一条
- 证据 ID：rowid / message_id / summary 行
```

`findings.json` 每个对象至少包含：

```json
{
  "id": "RA-01",
  "k": 12,
  "claim": "具体信息主张，不是摘要整体评价",
  "category": "constraint | authorization | completion | identity | metric | state | task",
  "verdict": "retained | correct-forgetting | incorrect-forgetting | wrong-memory | recovered | over-retention",
  "wrong_memory_subtype": "distortion | false-identity | stale-state | false-certainty | modal-inversion | count-basis-mismatch | derived-as-raw | null",
  "status": "observed | candidate | unverified",
  "active_at_forgetting": true,
  "first_forgetting_k": 12,
  "evidence_ids": ["rowid:123", "message_id:...", "summary:k12:L34"],
  "quotes": [{"source": "summary:k12:L34", "text": "短引文"}],
  "downstream_effect": "下游动作或未观察到影响",
  "downstream_cost": "重复派发/OBJECT_CHANGED/漏掉 lever/错误调查方向/发版口径纠正，或 null",
  "recovery": {"source": "外部工件/重读/通知", "cost": "延迟或重复工作"},
  "counterexample": "至少一条替代解释或反例",
  "limitation": "影响该判定的缺口"
}
```

质量门：

- 每个判定有短引文和可解析的 `message_id`/`rowid`/summary 行；引用不存在的 ID 不能通过。
- 每条发现有至少一个反例或替代解释，并写明它为什么不足以推翻判定。
- `observed`/`candidate`/`unverified` 与 P0/P1/P2 分开；重要性不能升级证据强度。
- 明确检查“摘要缺席是否可由重读/工件解释”和“摘要在场是否真的被下游遵守”。
- 遗忘类判定写明恢复来源、是否恢复以及恢复成本；未恢复时不得用“后续没出错”代替恢复证据。
- `wrong-memory` 必须与源消息、工具结果或外部工件对照并指出子类；至少给出下游成本，或明确标
  `latent`；不得仅凭“摘要写了”判错误记忆。
- `active_at_forgetting` 有任务状态或用户引用依据；没有依据时降级，不默认活跃。
- 阶段覆盖、锚点覆盖、实际阅读量和未读缺口写入附录；目的抽样不外推。
- 至少一部分判定经过独立复核或协调者回查；一致意见不算正确性证据。
- 报告区分“摘要保真度”“下游遵守”“任务结果”“独立验收”，不互相替代。

## 8. 修订既有量化结论

先冻结原量化结论：原句、分母、口径、生成脚本和产物位置。阅读后逐条标记修订状态，不能静默替换
旧数字：

| 原结论类型 | 阅读发现 | 修订状态 | 写法 |
| --- | --- | --- | --- |
| 低相似度/大幅缩短 = 错误遗忘 | 删除的是已完成证据，活跃约束都在 | 降级 | 改称文本变化或 `correct-forgetting`，不称错误遗忘 |
| 高相似度/长度不变 = 摘要保留 | 限定词、否定或 scope 从句被删 | 升级 | 改判 `incorrect-forgetting` 或 `wrong-memory`（如 `distortion` 子类）；高相似度不能支持 `retained` |
| 摘要变长 = 信息更多 | 增量主要是重复已归档裁决 | 收窄 | 只说登记表变宽或重复增加，不说信息量增加 |
| `N/72` 摘要包含 X = 总体比例 | 分母是选中摘要或字符串命中 | 降级 | 改为描述性计数；说明未做概率抽样 |
| `29 local commits` = 发版提交数 | 实际 `v1.1.5..HEAD = 143` | 撤销/降级 | 标 `count-basis-mismatch`，重算口径 |
| 消息总数 = 回合数/参与度 | 大量消息是 compact marker/提醒 | 降级 | 拆分 role 和真实用户消息 |
| resume 失败 = 线程死亡 | 失败 id 是 task id 或线程仍在运行 | 撤销/降级 | 标 `wrong-memory`/`false-identity` 或 `candidate`，附线程表证据 |
| 摘要没写 X = agent 不知道 X | 下游重读或工件提供了 X | 撤销 | 改为 `recovered` 或“摘要不自足” |

修订记录至少包含：原结论、原分母与口径、阅读证据、修订状态（confirmed / narrowed / downgraded /
upgraded / refuted / unchanged）、反例和限制。若阅读只能说明“指标测的是另一件事”，优先收窄指标
适用范围，不直接否定原数字。证据不足时保留原结论并标 `unverified`，不补造新数。

## 9. 报告骨架与限制

1. **结果摘要**：1–3 条，直接回答最重要的正确遗忘、错误遗忘或错误记忆、影响和建议行动。
2. **正确遗忘与错误遗忘**：逐条写稳定 ID、判定、证据状态、结果、影响、建议行动和必要限定；
   恢复成本（如 Astra 调用方式重建）归入本节。节内按 P0/P1/P2 排列。
3. **错误记忆：失真、假状态、假身份**：按 `wrong-memory` 子类分组，写源事实对照、下游影响和
   限定；节内按 P0/P1/P2 排列。
4. **错误记忆导致的运行成本**：重复派发、`OBJECT_CHANGED`、漏掉 lever、错误调查方向、发版口径
   纠正等；只写成本，不重复第 3 节的原因分析。
5. **行动顺序**：先验证还是先修复，说明可观察的改进结果。
6. **附录 A**：口径、抽样、packet、覆盖、实际阅读量、未读缺口。
7. **附录 B**：逐 `k`/逐锚点证据、短引文、下游行为和反例。
8. **附录 C**：量化结论修订表。
9. **附录 D**：限制与未验证项。

跨样本趋势和顺利对照放在第 1 节或第 2–4 节末尾，不单独压过结果。

限制必须写明：目的抽样不能外推；摘要生成时的可见上下文不可得；当前 DB 是完整 transcript，
`excluded` 是当前标志；外部原件可能缺失；下游窗口只是观察窗，不是因果证明；合成 eval 只校准
判据，不代表生产准确率。
