# Peri v2 重构复盘——把执行循环、事件和渲染状态拆开

> **[Peri Code](https://github.com/konghayao/peri)** —— 用 Rust 写的开源 Coding Agent，兼容 Claude Code 生态。<https://github.com/KonghaYao/peri>

v2 重构共计 290 个 commit，deepseek-v4-pro 和 glm-5.1 完成了主要编码工作。随着提交不断累积，后续改动是否仍能落在既定模块边界内，成了主要风险。

重构开始前，`executor.rs` 已经超过千行。上下文压缩排在 19 个中间件的第 12 位，TUI 新增一种消息要穿过多条渲染路径补字段。每个改动都能单独工作，下一次修改却很难判断该落在循环、中间件还是界面层。

## 执行循环、压缩时机和渲染状态没有独立边界

v1 的交付过程围绕当前任务运转。prompt 说明要改什么，review 检查当前 diff，二者都能发现局部错误。模块归属、跨层依赖和旧路径是否该退出，通常不在这轮检查里。

ReAct 循环负责接收消息、生成决策、调用工具和返回结果。v1 把上下文压缩、工具分发和事件发送放进同一个 `executor.rs`。新增一个事件时，循环控制和输出逻辑往往一起改，文件越长，改动范围越难收住。

`CompactMiddleware` 当时位于 19 个中间件的第 12 位，前后分别是定时任务和目标追踪。压缩本应在固定的循环时点执行，却依赖一条无关中间件链的相对顺序。排查一次压缩问题，先得还原整条链的执行过程。

TUI 也有类似的边界问题。事件经过 `render_bridge`、`bubbles` 和 `view_render` 三层后才进入界面，同一种消息在多个位置都有中间表示。字段少转一次，编译未必报错，界面却可能丢掉一部分状态。问题分别涉及循环时序、事件边界和渲染状态，单靠一次局部 review 很难同时看清。

## 五阶段循环与事件边界

v2 将 ReAct 循环拆成 Compact、Receive、Reason、Act、End 五个阶段，分别处理上下文压缩、消息接收、模型决策、工具执行和结束检查。共享的运行时资源集中声明在 `StageContext`，控制流则分配到对应的阶段模块。

压缩因此从中间件链移到循环中的独立阶段。中间件继续处理 hook、权限和插件这类横切行为，不再承担核心循环的时序。调试压缩时，可以先检查阶段输入、上下文预算和输出；涉及 hook、取消或插件时，再沿相应的中间件和回调路径排查。

Agent 引擎将执行事件汇总为 `ExecutorEvent`。ACP 按事件类别把它分流为标准的 `SessionUpdate` 或 TUI 专用的 `AcpEvent`，TUI bridge 再将收到的事件归一处理并更新 ViewModel。DTO 是跨边界传输的数据类型，ViewModel 只保留界面渲染需要的数据。事件变更仍然需要更新映射和测试，但终端界面不再直接依赖 Agent 的内部类型。

`VIEW_MODELS` 是 TUI 的渲染快照。ACP bridge 把已完成消息和当前轮的渲染单元合并后写入它，`message_area` 直接读取这份快照。布局、换行和高亮仍然可以缓存，但缓存不再保存另一份业务状态。

## handoff 文件保存变更范围和验证结果

v2 第一轮迁移完成后，我们把这类重构的执行方式整理成了 [start-devflow](https://github.com/konghayao/peri/blob/main/.claude/skills/start-devflow/SKILL.md)。它把一次改动拆成上下文记录、只读调研、计划、编码、审查和验证。风险较高的任务会在编码前增加计划审查。

每个阶段结束时都会写 handoff 文件，记录目标、范围、相关文件、已确认的决策、执行过的命令和未解决的问题。下一个 agent 接手时，依赖原始目标和这份交接记录，而不依赖上一段对话还剩多少上下文。handoff 记录下一阶段需要的调用链、改动范围、当前 diff、验证结果和未决问题。跨 crate、跨执行阶段的改动仍需先定好架构边界，handoff 的作用是把这些前提留在可复查的位置。

## 旧路径退出后，迁移才算完成

事件边界明确后，迁移还要确认旧管线是否仍在读写同一份状态。

上下文压缩已经从中间件链移入循环阶段。TUI 后续删除了 `render_bridge`、`bubbles` 和 `view_render` 这条旧渲染管线，`message_area` 直接读取 `VIEW_MODELS`。旧的 `runtime`、`event` 和 `state_machine` 目录也在后续迁移中逐步退出。

如果兼容路径仍参与状态更新或渲染，新功能往往需要维护两套逻辑，状态也可能再次分叉。这里的退出标准是，新路径覆盖现有行为，旧路径不再持有或更新业务状态。

重构开始时，新增消息往往需要沿多条路径追踪。现在新增事件、阶段或面板时，先明确它的所有者和涉及的边界，再决定修改位置。
