# auto-issue-fixer: Issue 全生命周期管理

单入口技能，覆盖 issue 的创建 → 修复 → 验证 → 归档全流程。你根据用户输入**自动判断阶段**并执行对应操作。

---

## 阶段分发

收到用户输入后，**先判断阶段，再执行**：

| 用户输入特征 | 阶段 | 动作 |
|-------------|------|------|
| 描述 bug/异常/性能/重构需求，无明确 issue 路径 | **创建** | 访谈 → 生成 issue 文档 |
| 给出 `spec/issues/xxx.md` 路径或 issue 标题 + "修"/"fix" | **修复** | 读 issue → 改代码 → 更新文档 |
| "验证"/"verify"/"好了"/"还是不行" + issue 引用 | **验证** | 定位 issue → 问反馈 → 更新状态 |
| "归档"/"archive" + 可选 issue 引用 | **归档** | 扫描终态 issue → 移动 → 提炼认知 |

**优先级**：如果用户输入同时匹配多个阶段（如 "修一下 xxx issue 然后验证"），按 创建→修复→验证→归档 的顺序逐一执行，每阶段完成后自动进入下一阶段。

---

## 阶段一：创建（Create）

### 核心原则

你是记录员，不是诊断员。产出是**症状文档**，不包含根因分析。

| 允许 | 禁止 |
|------|------|
| 读用户提到的文件来理解术语 | 追踪数据流跨多个文件找 bug 源头 |
| 记录用户观察到的现象 | 写"根因总结"或"问题本质" |
| 搜索函数名确认其存在 | 搜索函数的所有调用点来验证假设 |
| 阅读 ≤ 5 个文件 | 阅读第 6 个文件（越界了） |

### 1.0 历史 Issue 检查

收到用户描述后，**在提问之前**用 Grep 在 `spec/issues/` 中搜索相关关键词。找到匹配时告知用户，让其选择更新已有 issue 还是新建。

如果是更新已有 issue：追加新现象到「症状详情」，更新状态变更记录（Fixed→Reopen, etc.），不覆盖原有内容。

### 1.1 理解初始描述

分析用户输入，提取提到的文件/模块/函数/错误信息。只读用户**提到**的文件来理解术语。

**第一个问题**：从描述中找最关键的一个模糊点，给出 2-4 个具体选项。不要问"能不能详细说说？"。

### 1.2 场景还原

根据问题类型，只问**用户能直接观察到**的维度：

- **Bug**：复现频率、触发步骤、期望 vs 实际行为、环境
- **重构/技术债**：当前代码问题、期望改进方向
- **性能**：规模/负载条件、具体数据
- **安全**：风险描述、影响范围

每个 AskUserQuestion 一次一问，2-4 个选项。

### 1.3 补充细节

- 根据前两轮反馈，补充提问遗漏的现象细节
- 如果用户提到新文件，去读那个文件理解术语
- 不问代码能直接回答的问题（文件有多少行等）

### 1.4 自动定性与评级

自动判定，不询问用户：

| 类型 | 条件 |
|------|------|
| Bug | 异常行为、错误信息、崩溃、与预期不符 |
| 安全 | 数据泄露、注入、权限绕过等 |
| 性能 | 耗时、吞吐量、内存、卡顿 |
| 重构 | 结构性改进目标（拆分、解耦、迁移） |
| 技术债 | 职责混乱、重复代码、文件过大 |
| 文档 | 缺失/过时文档 |

| 优先级 | 条件 |
|--------|------|
| 高 | 数据丢失/崩溃/功能不可用；安全漏洞可被利用 |
| 中 | 部分场景影响但有 workaround；增加修改成本 |
| 低 | 代码质量改进；非阻塞优化 |

### 1.5 生成文档

按 `references/issue-template.md` 格式生成 issue，保存到 `spec/issues/YYYY-MM-DD-<slug>.md`。

slug 从标题生成，kebab-case，描述现象。`spec/issues/` 不存在时先创建目录。

**输出后**：

```
✅ Issue 已创建 → spec/issues/YYYY-MM-DD-<slug>.md

类型：[Bug/重构/...] | 优先级：[高/中/低]
标题：[issue 标题]
涉及文件：N 个
```

### 1.6 询问是否立即修复

创建完成后，用 AskUserQuestion 询问用户：

> "Issue 已创建。是否需要立即开始修复？"
> - A) 是，开始修复
> - B) 先不修复，后续再说

用户选 A → 进入阶段二（修复），将刚创建的 issue 路径作为输入。

## 阶段二：修复（Fix）

### 2.0 定位 Issue

- 用户给了明确路径（如 `spec/issues/xxx.md`）→ 直接 Read
- 用户给了模糊引用 → Grep 在 `spec/issues/` 中搜索匹配
- 找不到 → 告知用户，建议先创建

### 2.1 理解问题

读 issue 文档，提取：问题现象、涉及文件、复现条件。基于「问题描述」和「症状详情」理解用户遇到了什么，而不是基于代码猜测根因。

### 2.2 定位相关代码

1. 读「涉及文件」中列出的文件
2. 如果不确定代码位置，用 Grep 搜索 issue 中提到的函数名/错误信息
3. 需要广泛搜索时，用 explorer subagent

### 2.3 评估修复复杂度

| 简单 | 中等 | 复杂 |
|------|------|------|
| 单文件，逻辑清晰 | 2-5 文件，耦合低 | 5+ 文件；多模块耦合；需求模糊 |

复杂 issue → 向用户汇报分析结果和可能的修复方向，等用户决定后再动手。

### 2.4 执行修复

- 遵循项目编码规范（参考 CLAUDE.md）
- 保持最小修改范围——只改需要的
- 每处 Edit 前先 Read 确认当前文件状态
- 超过 3 处修改用 Write 整体重写

### 2.5 验证修复

```bash
cargo build --workspace 2>&1 | tail -20
```

编译通过后跑相关测试：

```bash
cargo test -p <涉及 crate> --lib 2>&1 | tail -30
```

**最多重试 2 次**（总计 3 次尝试）。2 次后仍失败，汇报失败原因和已尝试方案。

### 2.6 自动更新 Issue 文档

修复成功后，自动更新 issue 文件：

**步骤 1**：将 `**状态**：Open` 改为 `**状态**：Fixed`（或其他当前状态 → Fixed）

**步骤 2**：在「状态变更记录」表格末尾追加：

```
| YYYY-MM-DD | Open | Fixed | agent | 修复：[简述] |
```

**步骤 3**：如果「修复记录」段是空的占位文字（`（由...追加，创建时留空）`），替换为首条修复记录。否则在已有记录后追加：

```markdown
### 修复 #N（YYYY-MM-DD）

- **操作人**：agent
- **用户原意**：[从 issue 问题描述中提取]
- **修复内容**：[改了什么文件，做了什么]
- **涉及 commit**：[如有]
- **验证状态**：待验证
```

### 2.7 报告

```
✅ 修复完成 → spec/issues/YYYY-MM-DD-<slug>.md

状态：Open → Fixed
涉及文件：N 个
验证：cargo build 通过 / cargo test 通过
```

## 阶段三：验证（Verify）

### 3.0 定位 Issue

和 2.0 一样的逻辑：明确路径、模糊引用、找不到。

### 3.1 确认验证意图

基于用户输入推断目标状态：

| 用户反馈 | 目标状态 |
|---------|---------|
| "好了"/"修好了"/"验证通过" | Verified |
| "还是不行"/"没修好"/"又出现了" | Reopen |
| "部分好了"/"XX 修了但 YY 还有" | Partial |
| "不用修了"/"关了吧" | Closed |

用 AskUserQuestion 确认推断：

> "我理解你想把 `spec/issues/xxx.md` 标记为 [目标状态]，对吗？"

### 3.2 收集验证详情

根据目标状态收集信息（用 AskUserQuestion）：

- **→ Verified**：期望效果是否达到？有无新问题？
- **→ Reopen**：当前表现？是否特定条件才复现？
- **→ Partial**：哪部分修好了？残留问题是什么？
- **→ Closed**：关闭原因？

### 3.3 更新 Issue 文档

**步骤 1**：更新 `**状态**` 为新的目标状态

**步骤 2**：追加状态变更记录

**步骤 3**：追加验证反馈到「症状详情」末尾：

```markdown
### 验证 #N（YYYY-MM-DD）—— [结果]

[用户反馈详情]
```

**步骤 4**：如果是 Verified 且有修复记录中验证状态为「待验证」，更新为「已验证」。

### 3.4 报告

```
✅ Issue 状态已更新 → spec/issues/xxx.md

状态：[旧] → [新]
验证结果：[简述]
```

## 阶段四：归档（Archive）

**仅当用户明确说"归档"/"archive"时触发**，不会自动执行。

### 4.0 扫描可归档 Issue

用 Grep 在 `spec/issues/` 中搜索 `**状态**` 行，筛选终态 issue：

| 状态 | 归档 |
|------|------|
| Verified | 是 |
| Closed | 是 |
| Fixed | 是（含 Fixed + Verify 等变体） |
| Done/已完成/Resolved | 是（旧格式兼容） |
| Open/Partial/Reopen | 否 |

如果无可归档 issue，直接报告并结束。

### 4.1 提炼领域认知

逐个 Read 可归档 issue，提取：

- **所属领域**（agent/tui/mcp/compact/storage/langfuse/message-pipeline 等）
- **2-4 个关键词**
- **问题本质**（这类问题的根因）
- **通用模式**（以后遇到类似问题如何思考）
- **架构影响**（对整体架构的启示，可选）
- **涉及文件**

将提炼结果写入临时文件 `/tmp/issue-archive-learnings-<timestamp>.md`，按领域分组。纯 UI 小 bug（错位、样式）标注"无可提炼认知"。

### 4.2 移动文件

用 Bash `mv` 将归档 issue 移到 `spec/archive-issues/`，并在文件顶部插入：

```
> 归档于 YYYY-MM-DD，原路径 spec/issues/<filename>
```

### 4.3 更新 Domain 文件

用 Agent subagent 更新各领域文件（`spec/global/domains/<domain>.md`）：
- 在「Issue 经验附录」段追加提炼内容（去重）
- 更新 `spec/global/problems.md` 关键词索引

### 4.4 更新 CLAUDE.md

对本阶段中「CLAUDE.md 链接: true」的 issue，在 CLAUDE.md 的「陷阱速查」对应条目追加内联链接。

### 4.5 报告

```
✅ Issue 归档完成

归档数量：N 个
归档位置：spec/archive-issues/
Domain 更新：<domain>: N 条新增
问题索引更新：N 个关键词
```

## 状态机

```
Open ──→ Fixed ──→ Verified（终态）
  │         │         │
  │         │         └──→ Reopen ──→ Fixed ──→ ...
  │         │
  │         └──→ Reopen ──→ Fixed ──→ ...
  │
  └──→ Partial ──→ Fixed ──→ ...
  │
  └──→ Closed（终态）

任何状态均可 → Closed
```

合法转换：Open→Fixed/Partial/Closed；Fixed→Verified/Reopen/Partial/Closed；Partial→Fixed/Reopen/Closed；Reopen→Fixed/Closed；Verified→Reopen（回归）；Closed→Reopen。

---

## 跨阶段规则

- **所有面向用户的文本使用中文**
- **状态变更记录**：追加到表格末尾，不覆盖历史
- **修复记录**：每次修复独立 `### 修复 #N`，多次修复保留完整历史
- **验证反馈**：追加到「症状详情」末尾，`### 验证 #N`
- **更新已有 issue**：不创建新文件，在原文件追加新内容
- **Issue 未找到**：告知用户，建议先进入创建阶段
