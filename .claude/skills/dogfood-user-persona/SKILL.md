# Dogfood User Persona

验收问题不是“实现对不对”，而是“一个只拿到发布物的新用户，照文档能不能真的把事做完”。这个证据只在**信息隔离**下成立：协调者知道修复上下文，一旦把它带进 user agent 的提示词、或代替 user agent 读文档并总结，验收就退化为自证。

## 何时使用

适用：

- 需要验收一个包或交付物的发布表面：安装、README quickstart、exports、随包文档是否自洽可用。
- 用户要求“像新用户一样用一遍”“拿 subagent 当用户”“按文档能不能真正用起来”。
- 发布前的 dogfood，或修复后需要独立复验用户路径。

不适用：

- 已知目标文件与失败原因的内部缺陷：直接写复现测试，不要包装成盲测。
- 只需运行既有测试套件：按仓库测试命令执行，无需 persona。
- 需要评审实现设计：走代码审查，不是用户验收。

## 角色与隔离

| 角色 | 职责 | 禁止 |
| --- | --- | --- |
| 协调者 | 固定发布物、派发盲测、收集报告、组织修复、判定终局 | 派发前先读实现细节并据此设计验收；向 user agent 泄露已知问题、内部文件路径或实现说明；替 user agent 总结 README |
| user agent（第一轮） | 只凭发布表面从零完成真实任务，记录全部证据 | 读仓库源码、仓库内部文档（`docs/code-index/**`、`docs/design/**`）、内部计划与既有报告；修改包本身；复用已有会话 |
| 执行 agent | 按第一轮发现修复代码/测试/文档 | 兼任 user agent；用“文档已经写了”结案 |
| user agent（第二轮） | 用同一份 README 从零复验，逐条判定 PASS/FAIL/PARTIAL | 读源码或第一轮报告；复用第一轮 agent 或它的临时目录 |

- 两个 user agent 必须是**两个独立的全新实例**，不得是同一个 agent 的两次调用，不得 resume 第一轮会话。
- 协调者可以把第一轮报告转写成重放清单，但清单只保留用户级步骤与预期观察，不带根因、修复说明或“已知问题”提示。
- 派发第一轮前，协调者只准备发布物与提示词，不预判用户会在哪里卡住。

## 流程

### 1. 固定发布表面

1. 记录验收基线：仓库 commit、打包命令、tarball 路径与 digest、平台与运行时版本。
2. 只把发布表面交给 user agent：tarball、解包后的 README、`package.json` 的 exports/engines、随包文档。
3. 优先用 tarball 安装；`file:` 仅在 tarball 可安装性已另行验证后作为退路：不得向 user agent 暴露仓库路径，且仍禁止读 `src`。
4. 第一轮提示词中不得出现仓库内部路径、实现细节、历史问题或修复意向。

**完成标准**：tarball 可安装，digest 与打包命令已记录；若改用 `file:`，须附 tarball 安装验证证据；提示词检查后不含内部信息。

### 2. 第一轮盲测

user agent 的任务提示必须包含：

- 身份：你是第一次使用该包的开发者。
- 输入边界：只能看发布表面；安装优先用 tarball，若必须用 `file:` 本地安装，不得暴露仓库路径，且仍禁读 `src`；禁止读仓库源码、仓库内部文档（`docs/code-index/**`、`docs/design/**`）、内部计划与既有报告；不得自行修包。
- 任务：在全新临时目录创建自己的项目，完成一个**真实且非平凡**的用户任务，不是只 `import` 成功。
- 记录：逐条写下执行的命令与观察结果、耗时、阻塞点、文档与行为不符之处、困惑点；给出可复现命令。
- 遇到问题时先记录再绕过；若必须绕过，写清绕法与为什么需要它。

任务示例（按实际包替换，不要硬编码）：用 `@peri-code/sdk` 做一个 ChatGPT 风格的 Web 前端，包含输入框、消息列表、流式回复、刷新后保留历史。示例的价值是覆盖安装、API 使用、运行时行为和持久化，而不是覆盖某个函数。

**完成标准**：报告足以让第三人逐条重放每条命令并看到相同结果；没有“理论上应该可以”式结论。

### 3. 修复

- 修复交给**单独的执行 agent**，不得由协调者顺手改，也不得由任一 user agent 改。
- 每条发现先分类，再决定落点：产品缺陷（代码 + 测试）、文档缺陷（README/示例）、环境阻塞（不修包，记录证据）。
- 不得用“文档里已经写了”结案，除非能给出证据证明用户路径本来就是对的：文档原文、实际可重放步骤，以及第一轮为何偏离。
- 修复清单逐条对应发现：finding → 改动文件与验证命令 → 结果。是否提交由用户决定，本流程不自行提交或推送。
- 修复后重新打包，记录新的 tarball digest。

### 4. 第二轮独立复验

- 另一个全新 user agent，全新临时目录，重新打包/安装，使用同一份 README。
- 协调者提供第一轮路径的重放清单（仅用户级步骤与预期观察）。
- 逐条按本 skill 的判定口径给出结论，并附证据（命令、输出、日志/截图路径）：
  - `PASS`：照 README 步骤得到预期观察，证据完整。
  - `FAIL`：用户路径无法完成或结果错误。
  - `PARTIAL`：路径可完成但有缺口，写明缺了什么。
- 允许报告第一轮未出现的新问题；同样禁止读源码与前一轮报告。

**完成标准**：第一轮每条路径都有判定与证据，没有“未提及即通过”的条目。

### 5. 循环、结论与产物

- 循环有界：修复 → 全新 agent 复验，直到全部 `PASS`，最多两轮修复 + 复验；达到上限仍有未通过项时，剩余项按现有证据标为 `unverified` 或 `FAIL` 并交用户裁决，不得默认通过。每次复验都重新打包并使用新临时目录。
- 仍无法验证的项显式列为 `unverified`，写清原因与所需前置条件（缺工具链、缺凭据、缺平台）。不得默认通过，不得把“本轮未复现”当作通过。
- 验收报告写到 `.peri/plans/dogfood-report-<date>.md`。`.peri/*` 已被 `.gitignore` 忽略，属工作区产物，不是仓库长期事实源；稳定结论再回写到对应 issue 或文档。
- 报告至少包含：环境与输入（commit、tarball digest、运行时版本）、第一轮命令与观察、问题分类、修复清单、第二轮重放判定表、`unverified` 项与残余风险。

## 仓库示例：peri-sandbox

```bash
# 从全新 clone 开始
cd npm-packages/peri-sandbox
bun install
bun run build
npm pack --pack-destination /tmp/peri-sandbox-pack   # prepack 会重建 dist；只生成本地 tarball，不发布
```

- 在全新临时项目里安装该 tarball，按 README 启动 CLI / MCP server；文档写错或缺失本身就是发现项。
- 早期 `peri-rivet` 与 `agent-builder` 已移除，不得作为演练对象。
- 禁止 `npm publish`，禁止 `git push`。

## 卫生与边界

- 每轮结束释放自己创建的临时目录、后台进程和端口，并在报告中记录释放了什么。
- 不得杀用户端口上的进程，包括 `6420`、`8787`、`8788`、`5173`、`6437`。`6420`（Rivet engine，peri-swarm 本地开发）与 `8787`（artifact 示例）当前文档有出处；`8788` 仅历史文档有出处（peri-cf Lab 已移除）；`5173`、`6437` 随 agent-builder 移除不再使用。实际端口以当前环境配置为准。端口被占用时换端口或记为阻塞，不要清场。
- 环境缺失归为**环境阻塞**而非产品缺陷：如 Emscripten 未安装、Python 版本不符、磁盘空间不足、registry 缺包。记录命令、输出和版本证据，修复清单不收录。
- 环境阻塞若可由用户环境补齐，不影响其余路径的判定；相关路径标为 `unverified`，不要标 `FAIL`。

## 反模式

1. 协调者先读代码再设计验收，把自己的实现知识当成用户视角。
2. 把已知问题、内部路径或实现细节写进 user agent 提示词。
3. 同一个 agent 既当用户又当修复者，或第二轮复用第一轮实例/目录。
4. 用“理论上应该可以”“按代码看没问题”代替真实执行与观察。
5. 把环境问题当产品 bug 修复，或反过来把产品缺陷归为环境。
6. 验收报告只写结论，不附命令、输出与耗时。
7. 用“文档里已经写了”打发反馈；用户按文档操作失败，本身就是文档或产品的缺陷证据。
