装配入口不是新业务服务或第二套 Runtime。优先复用现有能力接口，不足时才定义窄 port；具体接入契约仍待验证。

三条不同的通路，不共享所有权

引用走 ACP，状态直达 Store；能力走 MCP，执行进入 Sandbox。TS 不搬运 Session，Core 不内置业务能力，MCP Server 不等同于执行环境。关闭 Agent 不删除 Session，也不自动销毁外部 Sandbox。

实体职责：谁持有什么，谁不应越界

“拥有”区分生命周期、运行裁决和数据存储；不以类的嵌套关系代替所有权。

配置告诉 Agent 怎么运行

systemPrompt、cwd、模型与 MCP 连接属于运行配置。配置可能需要记录来源以便恢复，但不应与对话状态混成同一个可变对象。

Session 记录运行留下什么

Agent 可先后处理多个 Session；Session 可先后由不同 Agent 使用，这是目标关系的推论，而非无条件恢复承诺。兼容检查和写入规则需要另外确定。

  4. 能力执行：外部 MCP Server 按配置由 Peri 直连； TS Server 经 ACP 管道中的 MCP over ACP 调用，复用既有协议。 Server 将需环境的操作派发到 Sandbox；静态 Skill / 资源可不进入环境。

TS 反向注入能力，不反向接管循环

同一个 TS 进程可以同时充当 ACP 宿主和 MCP Server；它作为能力服务方不等于 Sandbox。

MCP REVERSE INJECTION
Peri MCP Client⇄ 调用 / 结果ACP 管道 · MCP over ACP⇄TS 官方 McpServer

MCP over ACP（复用既有协议能力）：Peri 经现有 ACP 管道反向调用 TS 托管的 MCP Server，不额外设计 HTTP endpoint 或桥接协议。 业务数据、内存对象或跨 Agent 协作可以由 TS 提供；外部 MCP Server 仍按配置由 Peri 直接连接，不经 ACP。MCP 能力语义与 ACP 控制语义不同， 但宿主能力共享同一通信管道；工具与 Skill 不是宿主配置入口。

Peri MCP Client⇄ MCPMCP Server⇄ 执行派发 / 结果Sandbox

Sandbox 在 Server 后方代表执行环境；不是每次静态资源或 Skill 读取都需要进入它。Core 负责工具准入，Sandbox 承担环境资源边界。环境形态与隔离实现待定；建议生命周期由 MCP 部署 / 环境提供方管理，不默认跟随 TS Agent 回收。

避免自等待死锁：当前 Run 正在等待 MCP 工具返回时，该工具不能再等待同一个 Run 完成。跨主 Agent 业务关系由 TS 编排；进程内 SubAgent 与基于它的 Workflow 由 Peri 标准协作层管理。

DECISION LEDGER
已明确方向

架构支点

  • 一个 Peri 进程对应一个宿主管理的主 Agent，包含进程内 SubAgent；TS 管理主进程与跨主 Agent 业务。
  • 先保证 Core；官方 SubAgent 复用 Core，Workflow 基于 SubAgent 构建。
  • Cron、文件、Shell 作为 Builtin MCP；Middleware 收敛而非整体删除。
  • Resources 支持远程统一数据访问；Peri 直读 Store，活动运行资源留在本地。
  • Peri 是 RCRA Core，持有 MCP Client 执行面。
  • MCP JSON 直接交 Peri；所有外扩能力由 MCP Server 提供。
  • TS 托管的 MCP Server 通过 MCP over ACP 反向提供能力，复用同一通信管道。
  • Session 是独立状态，不依赖 Agent 生命周期。
  • TS ↔ Peri 通信使用 ACP；TS 对 Session 只提供引用。
  • Peri 直接读写 Session Store；TS 不代理快照或提交。
  • Sandbox 是 MCP Server 后方的执行环境。
建议方案

值得保留的结构

  • Core 负责上下文组织、预算、取消终态与执行准入。
  • Run 使用明确的 Session 版本，产生合法状态变化。
  • Session 状态包含消息、工具结果、压缩与 Skill 引用。
  • Sandbox 生命周期由 MCP 部署或环境提供方管理；不默认随 Agent 回收。
  • 同 Session 单写者或版本校验，避免两套执行事实。

  • 单写者、CAS、提交边界、失败与取消后保存什么？

  • Skills 的发现、加载和激活如何映射 MCP？

设计来源与实现现状，不应混读

已结束的 TS POC（源码包已移除）曾验证 ACP 调用、流式句柄与 MCP 接入， 当时 Session 与 Agent 绑定、cwd 使用临时目录，宿主 MCP 采用 HTTP bridge 和 Client 代理。它完成了接口探索使命，仅保留这份生态稿。

Peri 4.0 的 sessionRef / storeRef、独立状态访问、单 Agent 进程与统一能力边界 是目标讨论，不是现有实现声明。当前 Rust 系统的分层、持有关系及受限 MCP Apps relay， 见 现有 Peri 内部分层设计； MCP Apps relay 不应等同于本稿引用的完整 MCP over ACP 接入方向。

协议引用：MCP over ACP（复用既有协议能力）。本稿按协议名称引用， 具体版本与规范链接待核对；不在此定义新的消息格式或承载机制。
