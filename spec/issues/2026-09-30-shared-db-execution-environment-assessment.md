# 共享数据库与执行环境身份：架构会议评估

状态：2026-09-30，两个 subagent 分别从多用户授权、执行环境生命周期进行首轮评估与交叉质询；以下为待批准提案，不是现行多用户能力声明。未修改运行时代码、未运行远端实验。

## 目标与结论

目标是一个后端数据库供 N 个用户共用，数据可按权限隔离或共享，路径明确归属执行环境，而非仅让 N 个客户端使用同一份数据库凭据。

**可以不做全面 URI/VFS，采用稳定 execution_environment_id + 环境内原生路径。但环境 ID 只解决定位归属，单独增加它不满足多用户共享。** 还须有认证主体、资源授权、受信执行环境和全局执行所有权。

插件体系与 MCP 缓存继续落盘并暂缓迁移；SQLite 后端免整改不意味着现有元数据与授权契约已经满足多用户目标。

## 现行事实

- `docs/design/session-workspace-identity.md` 第 2 节将身份范围限定为同机同库；跨机器身份传播不在现行设计范围。
- `peri-resources/src/sessions/canonical.rs::CREATE_TABLES` 中线程、工作区及 binding 没有用户/授权/环境归属字段；binding 已保存 workspace 身份与相对 cwd，可复用。
- `peri-resources/src/sessions/remote/session_sql.rs::SELECT_SESSION_SQL` 按会话 ID 查询，`SELECT_PAGE_SQL` 按项目/工作区/目录过滤，没有认证主体过滤；目录筛选不构成授权。
- `peri-resources/src/sessions/remote/mod.rs` 说明远端 projects/workspaces 当前为空，执行事实留在本机；`remote/composition.rs::open_remote` 组合远端会话数据与本机执行面。因此不能把远端数据 adapter 当成现成的多用户执行控制面。
- `peri-resources/src/sessions/sqlite_store/execution.rs::lock_execution` 使用本机 sidecar 文件锁；它不是跨机器全局执行仲裁。

这些是源码观察，不是对生产环境已发生数据越权或重复执行的指控。

## 会议角色与交叉质询

| 参与者 | 关注点 | 首轮判断 |
| --- | --- | --- |
| A：多用户数据与授权 | principal、共享规则、可信访问入口 | 环境 ID 不能当用户 ID 或权限；共享全库凭据时客户端过滤不可作为隔离 |
| B：执行环境与生命周期 | 身份、地址、实例代次、路径及接管 | 一期固定工作区归属单个环境即可；不需要多位置映射或全面 URI |

A 质询环境身份由谁证明、跨机执行权如何仲裁；B 建议控制面登记并绑定环境凭据，跨机执行按根 session 原子仲裁，但明确 fencing 不能停止已经启动的 shell。B 反问失联时谁证明旧执行已停止；会议建议证据由受信执行 authority 的排空/隔离机制提供，缺少证据时只读或拒绝接管，不能靠 TTL 宣称安全。

无原则性分歧。共同限制：数据库写入被 fencing 不等于所有工具副作用被 fencing；这不是可用性优化能够绕过的约束。

## 最小领域划分（提案）

| 概念 | 职责 | 不承担什么 |
| --- | --- | --- |
| Principal | 经认证的用户或服务主体 | 不由客户端自报 owner 字段建立 |
| Owner / Grant | 资源所属及明确的 read/write/execute/manage 权限 | 项目相同、路径相同不自动授予访问权 |
| ExecutionEnvironment | 持久执行环境身份与受信执行 authority | 不是用户身份、路由地址或运行代次 |
| Workspace | 一份实际文件树，一期固定属于一个环境 | 不代表多个机器上的 clone 已自动同步 |
| Session binding | 不可变工作区身份及相对执行目录 | 不因打开会话的客户端位置而改写 |
| Execution owner | 根 session 当前执行者及单调代次 | 不等于会话创建者，也不由 active 状态推断 |

machine_id 仅可作为设备描述；同机用户、容器等可能有不同执行环境。默认部署可一台机器一个环境，不必先建设复杂环境平台。身份属于驻留工具环境，而不是短命计算实例。

一期不强制 tenant：owner + 显式 grant 可以支持个人与协作者。若有组织管理员、统一成员撤权、配额或更强隔离，再明确组织/tenant 模型，不能借用环境 ID 表达。

## 推荐宏观架构（逻辑职责，不强制独立进程）

```text
用户客户端
  → ACP 业务入口：认证主体与请求上下文
  → 可信应用服务：资源授权、会话生命周期与执行控制
      → 数据能力（内部 MCP）：单个后端 DB
      → 执行能力（内部 MCP）：按环境 ID 选择受信 authority
          → 环境内工作区、原生路径与工具
```

认证可以由受信入口或部署身份层提供，但应用服务必须验证可信上下文；MCP/ACP 协议名称本身不提供认证授权。普通用户不持能绕过策略的全库凭据；若必须直接访问数据库，则隔离须由数据库强制提供等价保障，而非终端约定过滤。

共享 DB 保存资源归属/授权、环境登记与工作区关联、会话历史/绑定及全局执行控制事实；环境保存真实路径校验与实际进程生命周期。共享登记是控制事实，实际文件存在、目录对象和执行状态须由受信环境侧验证。

建议字段关系不是最终 DDL：

```text
workspace: workspace_id → execution_environment_id + root + root_identity
session:   owner_principal_id + workspace_id + relative_cwd
grant:     resource + principal + permitted_actions
execution: root_session_id → owner_instance + generation + state
```

字段归属可随既有接口细化；不要求每条消息、每个路径重复保存环境 ID。环境 root 的唯一性与发现键须纳入环境作用域；本机对象证据不能直接跨环境比较。环境 ID、可变 endpoint、环境实例代次、session 执行代次必须区分。旧 `threads.cwd` 可保留历史展示，但不能成为跨环境执行依据。

Project 现行含义仍是一个本地仓库实例；同 remote 的跨机 clone 不应自动合并身份。N 人可通过显式授权共享会话，不要求先重定义 Project。团队跨 clone 的业务聚合若需要，另行设计，不以同名路径或 Git remote 偷换身份。

## 必须覆盖的场景与失败规则

1. 同机两用户：相同环境或路径不授予互读历史；授权覆盖列表、消息、快照、fork、子任务、删除与恢复。
2. 两机同路径：分别登记环境，不在当前机器 canonicalize 另一环境的路径，不自动本机回落。
3. 容器重建/机器克隆：默认新环境身份；延续旧身份须显式重新登记、撤销旧凭据与重新验证。复制凭据可冒充环境，UUID 本身不能阻止。
4. 共享会话：历史可见性与工作区访问权分开；读取已共享历史不自动授予工具执行权，历史可能含文件内容，应明确共享授权后果。
5. 跨机竞争：全局 owner 按根 session 仲裁，不按环境各自授予。子任务继承受控执行权；持久化与执行入口拒绝旧代次。本机锁作为第二道保护。
6. 断网旧 owner：租约过期不证明进程停止；不能排空/隔离旧执行则拒绝接管。撤权也需处理在途运行。
7. 同工作区不同 session：session 排他不能避免两个会话改同一文件；共享写入须显式协调或使用独立 worktree，本方案不宣称自动解决文件冲突。
8. 旧库迁移：来源明确的本机登记才能认领为当前环境；导入共享库不能把所有历史路径批量标成当前机器。授权归属未知的数据不得默认向所有用户开放。

## 分阶段收敛

1. **多用户数据面**：可信认证上下文、owner/grant、全入口授权；将共享数据权限与执行权限分开。此阶段不承诺跨机执行。
2. **环境归属与原环境执行**：稳定环境身份与受信登记，workspace 固定环境，地址按环境解析；异环境历史可按授权读取，执行明确拒绝或路由至已批准的原环境。
3. **全局执行所有权**：在任何可跨机器竞争的执行开放前，建立根 session 原子仲裁、代次守卫、旧执行处置与关闭排空。缺失则保持只读/拒绝接管；不自动迁移文件树。
4. **按真实用例扩展**：只有确需跨环境续作、共享文件树、多位置选择时才扩展模型；全面 URI/VFS、插件及缓存迁移均非前置条件。

DB schema 形状本地/远端共用，元数据与契约演进须同步 adapters，不换 SQLite 后端。验收至少覆盖两用户互不可见、显式共享、直接按 ID 访问拒绝、权限撤回、同路径不同环境、双机竞争、旧代写入拒绝和失联不安全接管拒绝。

## 待用户裁决

- 共用 DB 是个人默认私有、按需共享，还是一个全员可见的受信团队空间？建议前者作为默认。
- 一期是否接受仅原环境执行，跨机迁移/失联自动接管暂不承诺？建议接受。
- 是否有组织管理与成员撤权需求？没有则不预先强加 tenant 模型。

以上是宏观可行性与风险评估，不是已完成实现或完整工期估算。
